# 调度计划

## task 与 worker 调度单元

现有任务系统是唯一持久真相源，T1、T2、T3 分别保持独立 task。旧版调度合同以单个 task 为 worker assignment：每次分派包含一个任务编号、允许写入范围、聚焦测试和返回合同；worker 不更新任务状态。

## 分组决定

登录锁定涉及认证安全边界，按 Strict 控制。三个 task 都修改同一认证模块、共享同一 fixture，写入和测试证据不能隔离，因此禁止并行。旧版没有独立的多 task 场景组调度单元，故采用三个 bounded task 串行执行，而不是并行：

1. worker-T1：仅处理失败测试，allowed writes 限定到认证测试与 fixture 的必要范围；返回 RED 命令和失败原因。
2. worker-T2：在 T1 经协调者验收并更新状态后启动，仅实现计数器；返回实现 diff 与聚焦测试结果。
3. worker-T3：在 T2 经协调者验收并更新状态后启动，仅补充审计事件断言；返回断言 diff 与完整场景测试结果。

## 组内顺序

不存在跨 task 的 worker 场景组。调度顺序为 T1 → 协调者验收 → T2 → 协调者验收 → T3 → 协调者验收。每个 worker 都使用各自 task 的 assignment 合同；依赖未由真实状态证明完成前，不启动下一任务。

## 验收与状态更新

每个 worker 返回后，协调者分别核对实际 diff 是否在 allowed writes 内、是否覆盖既有改动、聚焦测试的真实命令与结果，以及该 task 的需求和范围。证据支持 `DONE` 后，才在唯一任务系统中更新对应 task；worker 摘要不能直接驱动状态变更。

由于 T1、T2、T3 共用 fixture 和认证模块，每次交接还需重新读取真实 task 状态、当前 diff 和聚焦测试，避免依赖历史 worker 消息推断完成度。最终再运行整条登录锁定场景的项目原生验证。
