# 调度计划（auto-code-generator v4.2）

## 是否合组

不把 T1、T2、T3 因“同属企业用户开通”无条件合并。当前形成三个临时场景组：

- `G1-migration`：T1 数据库迁移与回滚脚本。独立审批、数据风险、回滚和迁移专项验证构成不可跨越的边界。
- `G2-permission`：T2 权限策略收紧。独立安全审批、权限回退和越权专项验证构成另一条边界。
- `G3-admin-ui`：T3 后台 UI 展示。它有独立的写入与 UI 验证范围；和迁移或权限合组不会增加可独立验收价值，反而会混淆失败归因。

T1、T2、T3 仍是权威 tracker 中的持久状态和逐项验收单元；G1、G2、G3 只是当前波次的临时 worker 调度视图。这里恰好一个组对应一个 task，是边界判断的结果，不是固定“每 task 一个 worker”的规则。

## 成本收益判断

合组可能节省企业开通上下文、环境准备、fixture 和重复集成测试的成本；但本例会损失可用并行度，并把数据库、授权策略和 UI 的失败爆炸半径绑在一起，同时增加审批协调、证据归属和局部回滚成本。

门禁是：只有“合组节省的重复上下文、环境准备和重复测试成本”大于“损失的并行度、失败爆炸半径、协调成本与回滚成本”时才合组。本例中 T1、T2 的独立审批、回滚、风险与专项验证已使后者占优；T3 又具备可隔离写入和验证，因此三个任务保持独立。

## 依赖与串并行

“服务同一用户场景”不是实现依赖。调度前从权威任务与设计中确认真实的生产者/消费者关系，不按任务数量决定串并行：

1. G1、G2 只有在各自审批和前置条件满足后才可调度。若能证明写入/生成物不重叠、不竞争独占资源、不同时演进同一公共契约或 manifest、互不消费未落地行为，且测试证据可分别归属，则可以并行；任一条件无法证明就串行。
2. G3 只等待它真实消费的已验收结果。例如 UI 若依赖 T2 的新权限契约，必须在协调者验收 T2 后进入下一波；若还依赖 T1 的新字段，则同时等待 T1。若它不依赖二者且隔离条件成立，则可独立并行。
3. 每组返回后由协调者核对真实 diff、允许写入范围与聚焦测试，逐项更新底层 task；一个组完成或一个并行波次结束不会自动完成其他 task。

## 验证边界

- G1：迁移前后 schema/数据不变量、正向迁移、回滚脚本、兼容性与失败恢复；证据和审批只归 T1。
- G2：角色/主体的允许与拒绝矩阵、越权与权限提升防护、策略回退及安全专项审查；证据和审批只归 T2。
- G3：后台展示的状态、角色可见性、错误/空态和 UI/浏览器测试；不得以 UI 展示结果替代权限策略验证。
- 三组分别验收后，再执行企业开通端到端场景验证。任一组失败只冻结并恢复该组；只有证据表明已验收上游契约错误时，才重新打开相应依赖，而不自动回退其他已验收组。
