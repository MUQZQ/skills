# 调度计划（auto-code-generator v4.1 快照）

## 是否合组

该变更同时涉及持久化迁移和权限安全，按 Strict 档位处理。旧版工作合同不定义跨 task 的场景组合并；按照“每个 Strict 实施任务使用上下文全新、输入受限的 worker”，分别委派：

- T1：迁移与回滚 worker；
- T2：权限策略 worker；
- T3：后台 UI worker。

因此不会仅凭三项属于同一企业开通场景就交给同一个 worker。T1、T2 的独立审批、回滚和专项验证也要求保持独立任务边界；T3 单独执行以保留 UI 证据归属。

## 成本收益判断

分别委派会增加三次上下文加载、环境准备和测试启动成本，但迁移与权限的高风险、独立审批和独立回滚使隔离收益高于这部分调度开销；T3 独立后也更容易归属 UI diff 与测试证据。旧版规则没有跨 task 合组的量化或显式门禁，主要依据 Strict 风险档位和任务级 bounded worker 合同作出该决定。

## 依赖与串并行

先从权威 tracker 读取真实依赖。题面只说明同一用户场景，不能据此推断生产者/消费者关系：

1. 如果 T3 消费 T2 的新权限策略或 T1 的新字段，必须等待相应任务完成并由协调者验收后再执行。
2. 若 T1、T2 之间没有真实依赖，只有在实际写入和生成输出不重叠、不竞争独占资源、不同时演进公共契约/migration/manifest、不消费对方未落地行为，且测试证据可分别归属时才可并行。
3. 任一隔离条件无法证明时，使用独立 worker 串行执行；不因为任务处于同一 DAG 层就直接并行。

## 验证边界

- T1：正向迁移、数据不变量、回滚脚本、兼容性和迁移专项验证。
- T2：允许/拒绝权限矩阵、越权防护、策略回退和权限专项验证。
- T3：后台展示、角色可见性、错误/空态及 UI 测试，不以展示结果替代授权验证。

每个 worker 返回后，协调者分别核对实际 diff、允许写入范围、测试命令和结果，证据支持 `DONE` 后才更新对应任务状态。最终再按企业开通场景运行跨任务验证。
