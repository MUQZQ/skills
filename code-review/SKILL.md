# 代码审查协调器

## 职责与启动边界

- 用户明确请求审查时启动；独立审查未指定深度默认全量，明确要求快速则单轮聚焦。
- 不得把“用户请求 commit”本身当作自动触发条件。提交前由 `code-review-before-commit` 选择“1. 快速 / 2. 不做 / 3. 全量”；选择不做时不启动本 Skill。
- 本 Skill 拥有代码级发现、证据、覆盖、独立审查和复审规则；提交闸门拥有是否提交及修复循环。独立审查只报告，不自动修复或执行 Git 写操作。
- `coding-standards` 是通用编码质量条款的唯一来源；专项 Skill 提供检查线索。本文件定义发现的成立条件，不能把风格偏好或条目命中直接判为缺陷。
- 代码级发现成立、修复验证完成、系统验收通过分别报告。只有任务要求完整测试/修复/实机验收闭环时才执行 `evidence-driven-dev` 的完整流程；引用证据纪律不扩大任务授权。
- 项目特定审查规则由目标项目提供；共享协调器不内置具体项目的测试层级、目录或门禁命令。更严格的项目必要门禁继续适用。

## 1. 固定范围与快照

前置条件：用户指定的 commit/range/diff 可解析，或存在待审工作树变更；所有必要规则可读取。

- 提交前审查只使用 `git diff --cached --name-only` 和 `git diff --cached` 确定变更；同时记录基线 HEAD、目标暂存树（可用 `git write-tree`）、模式和授权范围。
- 独立审查按指定 commit/range/diff 执行；未指定范围时明确选择已暂存或未暂存范围。同一轮不得混用暂存与未暂存 diff。只有暂存变更时不能用空的 `git diff` 宣称无变更。
- 指定 diff 是发现入口，还需读取目标版本的必要上下文、调用者、测试和配置；不能把工作树中另一版本的文件当作目标源码。暂存文件可用 `git show :路径`，历史版本用 `git show <目标>:<路径>`。
- 只读历史 commit/range 审查和精确暂存快照审查不要求工作区清洁；不为审查擅自 stash、reset、暂存其他修改或创建工作树。确需创建/切换分支或工作树时服从用户及 `branch-manager` 授权规则。

### 运行证据绑定

记录目标源码、相关测试/配置/依赖、构建产物、运行环境、命令和结果。树哈希只标识目标，不能证明测试实际运行了它。

1. 先确认测试读取的相关源码、测试与配置等于目标版本；部分暂存、未跟踪依赖和旧构建产物都可能造成偏差。
2. 有相关工作树差异时，使用已获授权、能复现目标内容的隔离验证路径；无法做到则将必要验证标记未完成。无关工作树差异无需清理，但要确认不影响验证输入。
3. 源码、测试、配置、依赖、构建输入或环境变化时，重跑受影响验证，或逐项证明旧证据仍适用；不能仅因命令相同复用结果。
4. 报告绑定最终审查快照；提交资格还需由提交闸门紧邻提交再次核对。

## 2. 覆盖维度与规则路由

快速与全量采用相同事实标准和严重程度定义；深度不同。按每个维度记录适用/不适用及依据，缺少证据不是 N/A。全量覆盖本次变更全部适用维度和受影响范围。

| 维度 | 快速 | 全量 |
|---|---|---|
| 行为正确性与回归 | 变更意图、主要路径、明显边界 | 受影响调用链、契约、关键边界与跨模块回归 |
| 安全 | 输入、权限、敏感数据等适用风险 | 命中风险的绕过路径、防护有效性与信任边界 |
| 可靠性与可用性 | 错误处理、超时、资源释放 | 适用的并发、取消、恢复、幂等、生命周期与生产装配 |
| 效率与资源消耗 | 重复 IO、无界工作、资源泄漏 | 风险路径的规模、复杂度，必要时实测 |
| 可维护性 | 局部职责、重复实现、不必要复杂度 | 受影响模块职责、依赖与扩展影响；SOLID/坏味道辅助判断 |
| 语言与通用编码规范 | 匹配条款，复用有效工具结果 | 全部适用条款及工具不能判断的语义 |
| 可移植性与兼容性 | 涉及平台、版本、路径、编码、接口时检查 | 受影响目标环境、数据/接口兼容与迁移契约 |

安全与通用编码规范在两种模式均应用。格式、类型等机械检查交给项目工具，复用结果须满足快照绑定；工具全绿不替代语义检查。行数和文件数不能单独决定低风险。

从当前 Agent 的根注册表 `skills/skill-domain-mapping.yaml` 解析规范名称，再完整加载匹配 Skill。已完整加载且版本未变的内容可复用；不能只用摘要代替必需规则。

| 变更或风险 | 匹配规则 |
|---|---|
| `*.py` / `*.go` | `lang-python` / `lang-go` |
| `*.js`、`*.mjs` / `*.ts`、`*.tsx` | `lang-js` / `lang-ts` |
| `web/`、`*.jsx`、`*.tsx` | `lang-react`；结合项目技术栈判断适用条目 |
| `*.yaml`、`*.yml` | `yaml-format` |
| `openspec/changes/`、Markdown 设计文档 | `design`；OpenSpec 变更另加 `openspec-docs` |
| 权限、角色、认证 | `permissions-review` |
| 数据管道、指标或匹配异常 | `deep-analysis`，只在相应诊断场景适用 |
| 快速与全量 | `security-review`、`coding-standards` |
| 全量；快速涉及架构设计或结构重构 | `solid-principles` |
| 全量；快速涉及坏味道治理或结构重构 | `code-smells` |

SOLID、坏味道合入可维护性维度；全量始终加载这两份清单并判断条目适用性。快速模式追加 `solid-principles` 的唯一条件：变更明确涉及架构设计或结构重构。
快速模式追加 `code-smells` 的唯一条件：变更明确涉及坏味道治理或结构重构。条款没有实际影响的命中只作建议，不强迫新增抽象。
未匹配专项时报告路由盲区，主审继续检查适用的通用维度；必要领域能力缺失时结果为 `INCOMPLETE`。

## 3. 独立主审与按风险调度

- 快速模式使用一个聚焦 Agent：合并匹配规则，单轮检查，不自动修复或循环复审。
- 全量使用一个独立主审负责完整覆盖。专项只承担明确风险或可隔离的影响范围，检查维度不与 Agent 数量一一对应。
- 主审必须未参与本轮实施/修复；协调者负责调度、核验与汇总，不得内联替代独立审查。主审参与修复后，修复部分交另一个未参与者复核；零发现也不能由实施方给自己判通过。
- 全量命中鉴权/信任边界、不可逆数据迁移、并发一致性/取消、跨模块公共契约或生产装配变更时，主审列出具体触发位置和必要验证，追加一次对应范围的独立专项复核。多个风险可由具备所需规则的同一专项会话合并；主审保留整体覆盖责任。
- 默认最多同时运行 3 个审查 Agent（1 主审 + 2 专项），不为占满卡槽拆分；资源不足时排队。快速命中同类风险时仍由单个主审验证，无法在单轮内完成必要验证则报告 `INCOMPLETE`，不静默升级全量。
- 派发前约定范围、规则、快照、只读权限、输出和验证预算。默认每个审查工作项 10 分钟；用户/项目明确预算优先。临近预算先报告缺口，到期输出未完成，不以时间耗尽判通过。必要专项不可为省时跳过。
- 同源模型的独立会话只提供角色分离，不构成第二份独立实测来源；报告说明此限制。专项只回传发现与证据，主审统一去重。

任务卡最小字段：目标/快照、覆盖维度、允许读取范围、禁止写入、必要规则、验证预算、输出（发现、覆盖、证据、缺口）。子 Agent 不自行扩大修复或 Git 授权。

## 4. 发现、验证与证据状态

本节是代码审查发现及证据状态的共享规则；完整系统验收由 `evidence-driven-dev` 补充。

每个候选发现记录：稳定编号、预期依据（需求/契约/项目条款）、具体位置、可达触发条件、行为/影响、证据来源与对应快照、证据状态、严重程度、处理状态、下一步验证或修复建议。

| 证据状态 | 判定 |
|---|---|
| 已确认 | 证据足以支持所声称的缺陷及影响；静态确定性证明、测试或实测均可，按问题选择 |
| 已排除 | 有反证说明触发条件不可达或行为符合契约；记录反证，不能直接删除历史候选 |
| 待验证 | 有具体代码位置、可达触发条件和可能影响，但关键事实未闭合；写明缺口 |

泛泛猜测先作检查线索，不能自动阻断；严重程度与证据状态独立。禁止用主观置信分数当作校准概率或用低置信直接删除具体高风险线索。

验证按结论选择最小充分证据：
- 静态错误：契约与完整必要路径，或编译/静态检查结果；确认缺陷不要求先启动完整系统。
- 业务逻辑：针对性输入输出、最小复现或现有测试，断言锁住预期行为。
- 并发、取消、生命周期、生产装配：覆盖相应条件的集成验证或实际运行记录，不能用脱离生产接线的组件测试代替。
- 高风险候选：优先核实触发可达性及防护层，必要时独立复核或隔离环境复现；没有运行权限或环境时报告缺口，不越权取证。

证据比较看相关性、覆盖范围、可重复性和独立性，不作“实机必然优于测试”的排序。同一日志的两个摘要、两个 Agent 阅读同一段源码都不是两个独立证据源。每条证据只能支持其覆盖的结论；一次点击成功不证明全部边界。

修复状态另记未修复/待复核/已验证修复/保留。代码改动完成只能先记待复核；修复结论需要原场景与受影响范围的验证，系统验收结论另报。

## 5. 严重程度与完成状态

首版保持原有实质缺陷的阻断范围，先减少重复工作和无依据报告，不以重标等级改变提交资格。

| 级别 | 判据 | 示例 |
|---|---|---|
| P0 | 原有实质阻断缺陷：已证实的功能错误、有效的安全漏洞、目标工具链类型错误、违反明确架构契约并产生实质影响 | 越权、错误返回、破坏调用方契约 |
| P1 | 重要的性能、设计一致性、测试保护或维护风险，有具体影响但不属于上述 P0 | 关键回归缺少保护、增长后明显资源瓶颈 |
| P2 | 不影响已约定行为或安全的风格、命名、一般重构与结构偏好 | 局部命名、无实质影响的 SOLID 建议 |

不能把原 P0 实质缺陷改标 P1 后在快速模式自动放行。后续改变分类时必须同步提交政策、新旧放行对照用例和用户约定。待验证候选的级别表示可能影响，不冒充已确认缺陷。

| 审查状态 | 条件 | 提交含义 |
|---|---|---|
| COMPLETE | 本模式适用范围已覆盖，必要验证完成，具体高风险候选已闭合 | 仅表示审查完成；提交闸门再按已确认 P0/P1 与授权判定 |
| INCOMPLETE | 必要覆盖/验证缺失、具体高风险候选待验证、证据失效、必要 Agent/工具失败或预算耗尽 | 快速与全量均不能宣称通过或提交 |

具体高风险候选指：已有可达线索且可能涉及安全边界、数据损坏/丢失、核心功能失效或原 P0 实质阻断缺陷。一般非阻断待验证建议可以随 COMPLETE 报告，但不能据此强迫修复；不得把缺失的必要检查归为普通建议。
先判断完成度，再应用门槛：快速已确认 P0 阻断；全量已确认 P0/P1 阻断。完成不等于无缺陷，更不等于已授权提交或系统验收通过。不存在发现时，仍交付覆盖和必要验证证据。

## 6. 增量复审与最终组合验证

首轮检查完整目标差异；后续仅减少重复阅读，保留全部未决问题与必要验证义务。

1. 对比上次审查目标与新目标，记录修复差异、未决编号、影响路径和证据失效项。
2. 检查修改的定义、未修改的消费者、测试接线、配置，以及多次修复之间的相互作用；公共契约包含行为语义，不只包含签名。
3. 基线、公共契约、重要配置/依赖/环境、规则或审查范围改变时扩大复审；无法可靠判断影响范围时重新检查完整变更，不能沿用旧通过结论。
4. 最终组合快照须具备仍有效的全量覆盖和项目相关验证；共享路径的修复组合需验证共同场景。不能拼接不同快照上的局部成功替代最终结果。
5. 用根因、触发条件与修复义务去重，保留所有受影响位置；同一行的 SSRF 与缺少超时分别报告。验证修复后才关闭编号，重复报告不算新发现。

循环次数与停止由提交闸门管理；本 Skill 的增量机制不授权独立审查自动修复。

## 7. 报告与问题记录

```text
目标：基线 / 目标树或差异标识 / 模式 / 授权范围
审查状态：COMPLETE 或 INCOMPLETE；缺口与必要下一步
覆盖：维度 / 适用理由或 N/A 理由 / 检查范围 / 证据
发现：编号 / 级别 / 证据状态 / 位置 / 触发与影响 / 证据 / 修复状态
验证：目标输入与环境 / 命令或推导 / 结果 / 有效范围
复审：本轮差异 / 影响路径 / 失效证据 / 未决问题
边界：代码发现、修复验证、系统验收各自状态；同源会话限制
```

发现记录到 `<project-root>/.opencode/skills/code-review/review-issues.md`，复用该文件，不新增账本；禁止暂存或提交过程记录。独立方案讨论可直接在对话报告，不创建代码问题记录。
没有发现也报告覆盖与缺口，不写“零问题所以必然安全”。缺少耗时/Token 测量时不声称提速；计量覆盖全部主审、专项、验证与重试。

准备推送 PR 分支时追加：新增测试进入 CI、测试锁住生产装配、文档与实现一致、无冗余能力、历史未决问题已处置、相关包验证有效。项目命令从目标项目读取。

## 错误处理与铁律

| 情况 | 处理 |
|---|---|
| 空差异或目标不可解析 | 核对目标与暂存/未暂存范围，不伪造审查完成 |
| 必需规则缺失、Agent/工具失败 | 瞬时错误在预算内最多重试 2 次；确定性失败先查原因，不原样重复。仍失败将本轮标记为 `INCOMPLETE` |
| 预算不足、环境不可用 | 输出已确认发现、待验证项和缺失范围，不静默缩减必要覆盖 |
| 修复越权或快照漂移 | 停止相关动作，保留用户修改，交还范围/授权决策 |
| 专项结论冲突 | 核对契约和原始证据，无法闭合时保留待验证；不按多数票判事实 |

| 规则 | 内容 | 违反后果 |
|---|---|---|
| R0 | 入口、模式和授权分开；快速单轮，不做不审查 | 意外扩大工作与授权 |
| R1 | 每种模式均有独立主审，安全与通用规范适用性检查不可省略 | 自审假通过或漏检 |
| R2 | 证据绑定实际目标输入；快照编号不替代验证 | 部分暂存或旧产物假绿 |
| R3 | 完成度、严重程度、证据状态与修复状态分开 | 未验证问题被清零 |
| R4 | 先判完成度，再按提交闸门决定；不重标放行 | 实质缺陷绕过原门槛 |
| R5 | 增量复审仍覆盖最终组合及受影响消费者 | 修复组合回归逃逸 |

## 验证本 Skill 的升级

使用 `evals/evals.json` 的冻结场景检查授权、证据、快照、独立性、增量和停止条件。静态契约测试只证明规则连接，不能替代 Agent 场景执行。
实际提效验收另选已裁定严重缺陷和正常对照的真实历史快照；固定模型、工具与环境，对照旧版。先要求必测严重缺陷不漏报、授权不越界、无效证据不产生通过结论，再比较总耗时/Token、误报/错误阻断、未完成率及修复轮数。少量模拟场景不证明真实项目提速。
