# TDD 安全重构

## 核心原则

重构不改行为。但改架构时容易无意中改变行为。本流程的核心思路是：**用测试把旧行为锁死，新实现在旁路完成后才切流量**。这样任何退化都能被测试立刻捕获，出问题也能立刻回退到最后一条调用点。

## 流程概览

```
Phase 0   分析        识别范围、调用点、行为规约、语言/运行时
Phase 0.5 工作区检查   检查 git 状态、创建分支、建立 checkpoint
Phase 1   特征测试     为旧行为写测试（基线保护）
Phase 2   实现新方法   旁路实现，零影响现有代码
Phase 3   测试新方法   复制特征测试改调用目标跑一遍，确认行为一致
Phase 4   替换调用点   逐个切换，每切一个跑受影响测试
Phase 5   删除旧方法   确认零引用后清理，处理特征测试去留
Phase 5.5 代码审查     引用 merge-review 审查变更
Phase 6   清理验证     全量门禁 + 命名确认 + 测试守卫
```

## Phase 0: 分析

明确以下四项后进入 Phase 0.5：

### 1. 重构范围

哪些类/函数/模块是目标？写出文件路径和符号名。

### 2. 语言与运行时识别

确定目标代码的语言和运行时：

| 语言 | 调用点搜索 | 测试运行命令 | 额外注意 |
|------|-----------|-------------|---------|
| Python | `rg "func_name" --type py` | `uv run pytest tests/` | 异步代码需 `@pytest.mark.asyncio` |
| TypeScript/JavaScript | `rg "funcName" --type ts --type tsx` | `pnpm vitest run` | 前端组件涉及样式、路由 |
| QML | `rg "funcName" --type qml` | 依赖 PCB 环境 | 需通过 PCB 上下文验证 |

**多语言项目**：对每种语言分别执行调用点搜索，分别跑对应测试套件。

### 3. 所有调用点

全仓搜索旧方法的每个引用，输出 `文件:行号 — 调用上下文`：

- 搜索范围覆盖：`.py`、`.ts`、`.tsx`、`.js`、`.json`、`.md`（文档中的引用）
- `rg` 是推荐工具，不可用时使用 `grep -rn`
- 对函数调用，使用模式 `func_name\s*\(` 提高精度

### 4. 行为规约

用一句话描述旧方法的输入输出契约（类型、边界条件、副作用）。如果说不清楚，先读代码直到能说清楚。

### 5. 公共 API 识别

判断目标函数是否为公共 API：

- Python：是否在 `__all__` 中、是否通过 `__init__.py` 导出
- MCP tool：是否通过 `@register_pcb_tool` 装饰器注册 — 如果是，额外搜索所有可能调用该 tool 的 Agent skill 文件和文档
- TypeScript：是否从模块 `index.ts` 导出、是否在路由/对外接口中使用

如果是公共 API 且行为有变，评估是否需要 deprecation warning 过渡期。

### 6. 已知缺陷记录

如果分析过程中发现旧方法有 bug，记录在输出清单中（标记为"已知缺陷：xxx"），在 Phase 2 实现新方法时明确决定是否修复该 bug。

**输出**：一个 markdown 清单，含以上六项。

## Phase 0.5: 工作区检查

在执行任何代码变更前，调用 `branch-manager` skill 确保工作区安全：

1. **工作区状态检查** — 引用 `branch-manager` 的"分支命名与创建 → 工作区检查与分支创建"
2. **创建临时分支** — 引用 `branch-manager` 创建 `refactor/<目标名称>` 分支
3. **建立 checkpoint 机制** — 每完成一个 Phase 后做一次 `git commit` 作为回退点（见 `branch-manager` 的"Checkpoint"章节）。建议 commit message：
   - Phase 1 后: `WIP: characterization tests passed`
   - Phase 2+3 后: `WIP: new implementation with tests`
   - Phase 4 后: `WIP: callers switched`
   - Phase 5 后: `WIP: old code removed`

**关键约束**：不得在有未提交变更的脏工作区中执行 Phase 4（替换调用点）。

## Phase 1: 特征测试（锁定旧行为）

**特征测试（Characterization Tests）= 通过记录代码当前实际行为（而非正确行为）来锁定基线的测试。目的是防止退化，不是验证正确性。**

为旧方法写测试，覆盖：

- 正常路径（happy path）
- 边界条件（空输入、极值、特殊字符、nil/null）
- 已知的异常路径（如果有）

**异步代码专项**：
- 使用 `pytest-asyncio` 标记（`@pytest.mark.asyncio`）
- 对异步上下文管理器、异步生成器、`await` 路径分别写测试
- 覆盖超时、取消（`CancelledError`）等边界条件
- 对 `asyncio.create_task` 的并发场景进行测试

**关键约束**：
- 不修改旧代码，只加测试
- 用旧方法的当前行为作断言依据（即使它看起来"不对"——有 bug 已在 Phase 0 中记录）
- 写完跑一次，确认全绿

**测试范围**：跑新增的特征测试 + 相关模块的 L3 单元测试。

**输出**：`git diff` 确认只新增了测试文件。

## Phase 2: 实现新方法（旁路）

在旧方法旁边并行实现新方法：

- **优先使用最终方法名**。如果旧方法名已被占用，使用 `_new` 后缀（如 `method_new`），在 Phase 6 统一重命名
- 新方法完全不依赖旧方法的内部实现细节
- 如果涉及多个函数，先实现叶子节点再实现组合节点
- 如果 Phase 0 记录了已知缺陷，此时明确决定是否修复：修复则在 Phase 3 中说明理由

**关键约束**：不修改旧代码，不修改任何调用方，不删除任何东西。

**输出**：`git diff` 确认只有新增代码，零行删除/修改原有逻辑。

## Phase 3: 测试新方法

为新方法写测试：

1. 对照 Phase 0 的行为规约，逐条验证
2. **首选操作方式**：将 Phase 1 的特征测试复制一份，把调用目标从旧方法改为新方法，断言保持不变。如果全部通过，则行为一致
3. 如果新方法签名变化无法直接替换，则说明差异点并手动验证每个用例
4. 跑全量测试，确认新增测试和旧测试全绿

**测试范围**：新方法测试 + Phase 1 特征测试（对照）。

**输出**：新增测试文件 + 全量测试通过。

## Phase 4: 替换调用点（逐个切换）

根据 Phase 0 的调用点清单，逐个替换：

1. 挑一个调用点，把它对旧方法的调用改为调用新方法
2. 立即跑**受影响的测试模块**（非全量，节省时间）
3. 绿了 → 进入下一个调用点
4. 红了 → 回退这个调用点的修改，分析原因后再试

**回退策略**：
- 回退前用 `git diff -- <file>` 确认文件只有重构相关修改
- 如有无关修改，引用 `branch-manager` 的"暂存与恢复"章节暂存无关内容
- 仅回退当前调用点：`git restore <file>`
- 分析原因后从 stash 恢复无关修改重试

**关键约束**：
- 一次只改一个调用点，不改多个
- 每个调用点切换后必须跑测试（受影响模块范围内）
- 红了不猜测、不调试多个修改，立刻回退

**最后一个调用点切换后**：跑全量门禁 `bash scripts/gate/verify.sh`。

**输出**：每切换一个调用点后，输出 `调用点 N/M: 文件:行号 → 测试通过`。

## Phase 5: 删除旧方法

确认零引用后删除：

1. 用 `rg "old_function_name"` 再次全仓搜索（覆盖 `.py`、`.ts`、`.tsx`、`.js`、`.json`、`.md`），确认所有调用已切换
2. 删除旧方法定义
3. **特征测试去留**（区分情况）：
   - 情况 A：新方法完全保持旧行为 → 将特征测试中的调用改为新方法名，**保留**作为回归测试
   - 情况 B：新方法有意改变了部分行为 → 删除旧特征测试，记录原因到 Phase 0 输出清单
4. 跑全量测试确认全绿

**关键约束**：引用搜索必须覆盖整个仓库，包括注释和字符串中的引用。发现残留调用必须回到 Phase 4 处理。

**测试范围**：全量门禁 `bash scripts/gate/verify.sh`。

## Phase 5.5: 代码审查

重构涉及大量代码变更，在最终确认前进行审查：

1. 使用 `merge-review` skill 检查变更与预期的一致性
2. 如有 code-review agent，并行启动审查

发现的问题修复后回到 Phase 4 重新切换受影响的调用点。

## Phase 6: 清理验证

1. 如果 Phase 2 使用了 `_new` 后缀，将所有使用处重命名为最终名称（IDE 批量重命名 + 验证测试全绿）
2. 全量门禁：`bash scripts/gate/verify.sh`
3. 调用 `qeda-test-guard` skill 检查测试覆盖完整性（尤其 L4 e2e 测试是否受影响）
4. 输出重构总结：旧方法 → 新方法，调用点数量，测试数量，已知缺陷处理情况

完成后建议使用 `qeda-commit` skill 分段提交：
- Phase 1 测试作为独立 commit
- Phase 2 新方法 + Phase 3 测试作为一个 commit
- Phase 4 替换调用点合为一个 commit
- Phase 5 删除旧方法为最后一个 commit

这样出问题时可精细回滚。

## 铁律速查

| 规则 | 内容 | 违反后果 |
|------|------|:------:|
| R0 | 测试先于实现 — 没有特征测试锁定旧行为的重构不是重构，是重新写 bug | 行为退化无法被检测，只能上线后暴露 |
| R1 | 一次只改一个调用点 — 批量替换是重构事故的头号原因 | 大面积测试失败后无法定位问题来源 |
| R2 | 红了立刻回退 — 测试失败时不修改测试适配代码，不调试多个改动 | 绿色安全网被破坏，后续修复基于错误假设 |
| R3 | 旧方法删前必须零引用 — 全仓搜索确认，不靠记忆 | 残留调用在非测试路径中被遗忘，运行时才暴露 |
| R4 | 不猜测行为 — Phase 0 说不清楚行为规约则不得进入 Phase 1 | 特征测试基于错误理解，锁定了错误基线 |
| R5 | 发现旧代码 bug 先记录不立即修复 — 重构和修复分离 | 行为变化与结构变化混合，无法判断测试失败来源 |
| R6 | 公共 API 慎删 — 优先考虑 deprecation warning 过渡 | 外部调用方无感知行为变更，向下兼容被破坏 |

## 实战反例

| Agent 可能产生的想法 | 实际现实 | 违反规则 | 实际后果 |
|---------------------|---------|:------:|---------|
| "50 个调用点都一样的模式，批量替换没问题" | 即使模式相同，上下文差异可能引发边界 bug | R1 | 大面积测试失败无法定位是哪个调用点的问题 |
| "测试红了是因为新方法签名变了，改断言就行" | 特征测试的作用是锁定旧行为，修改断言等于丢弃安全网 | R2 | 行为退化被"修正"的测试掩盖 |
| "这个旧方法很简单，不用全仓搜索，应该没引用了吧" | 注释、配置、字符串模板中可能有隐藏引用 | R3 | 运行时才报错，且堆栈跟踪不直接指向被删方法 |
| "Phase 0 的大致行为清楚了，不用逐行读懂旧代码" | 遗漏的边界条件可能导致新方法行为不兼容 | R4 | 特征测试覆盖不足，Hidden bug 在新方法中被"修正" |
| "这个 bug 顺手修一下，反正都在改这个文件" | 重构和修复混合后，无法区分是重构还是修复导致的测试变化 | R5 | 出问题时无法二分定位，回退也分不开 |

## 错误处理

| 环节 | 失败条件 | 处理方式 |
|------|---------|---------|
| Phase 0.5 | git 工作区有未提交变更 | 引用 `branch-manager` skill 处理（stash 或提交） |
| Phase 4 | 调用点切换后测试变红 | 立刻 `git restore` 回退该调用点，分析原因后再试 |
| Phase 4 | 并行替换导致文件冲突 | 暂停，手动合并后转为逐一串行替换 |
| Phase 5 | 全仓搜索发现残留引用 | 回到 Phase 4 处理残留调用点 |
| Phase 6 | 全量门禁不通过 | 逐 checkpoint 回退（见 `branch-manager` 的"Checkpoint 回退点"章节） |
