# 跨仓库功能复刻方法论

## 前置条件

- 源仓库可访问，并已记录**版本锚点**（commit SHA 或 tag）
- 目标仓库可编译、可运行（至少一类构建与测试命令可用）
- 已确定要复刻的功能名称与源码入口
- 已确认源码许可与第三方归属允许搬运

## 项目绑定（调用方提供）

本 skill 只规定方法与判据，不内置任何项目路径、名称或命令。开工前由调用方提供绑定信息，
写在调用方项目的 AGENTS.md，或把 `references/project-binding.md` 模板复制一份到调用方项目后填写：

| 绑定项 | 说明 |
|--------|------|
| 源仓库路径 + 版本锚点 | 本次复刻的基线 |
| 目标仓库路径 + 构建/测试命令 | 验证入口 |
| 运行实例启动方式与隔离参数 | 并行实例的端口、调试参数、状态目录 |
| 调试与取证通道 | 日志、进程级调试端口、状态库、UI 自动化 |
| UI 断言通道 | 程序化输入与截图方式 |
| 项目专属规则文件 | 该项目已踩过的坑与既有约定 |

绑定项缺失时先向调用方索取，不要用猜测的路径或命令开工。

## 场景路由

| 用户意图 | 对应章节 |
|---------|---------|
| 复刻一个新功能（从零开始） | 支柱 1 装配链先通 |
| 功能写了但不生效 / 调用方看不到 | 支柱 2 声明面多层一致 |
| UI 元素不出现 / 界面与源不一致 | 支柱 3 证据驱动验证 |
| 两仓跑同一用例结果不一致 / 判定回归还是预期变更 | 支柱 3 黄金基线 + 一致性台账 |
| 移植前准备 | 移植前冻结 |
| 移植完成收尾 | 收尾审计 + 一致性台账 |
| 测试用例移植 | 支柱 3 黄金基线 + 一致性台账 |

## 支柱 1：装配链先通

> 复刻不是翻译代码，是接通链路。先画装配链路图，确认每条链在目标仓库走通，再写代码。

### 操作步骤

1. **画装配链路图**：回答四问
   - 功能入口被激活时，上下文属于哪棵树/哪个容器？
   - 能力（工具、服务、组件）注册进哪个实例？
   - 可见面（调用方可见清单、页面渲染）从哪聚合？
   - 同一功能有几个实例并存？
2. **找同款先例**：在源仓库找已跑通的同构路径，不自行设计
3. **识别多树/多实例陷阱**：多容器共存是常态，按实例逐一确认归属
4. **最小纵向切片**：选一条行为，打通「注册 → 可见 → 执行 → 呈现」全链再铺量

### 完成标准

- [ ] 装配链路图已画（各树/容器 + 可见面聚合点）
- [ ] 行为清单已列（每条可观测行为 + 验收方式）
- [ ] 同款先例已定位（路径 + 行号）
- [ ] 实例数量与隔离方式已确认
- [ ] 首个纵向切片端到端通过

## 支柱 2：声明面多层一致

同一能力通常需要在多个声明点同时登记，缺任何一层都会出现不同症状，且多数不报错。

### 通用四层（按目标仓库实际层名映射）

| 层 | 典型位置 | 作用 | 缺失症状 |
|---|---------|------|---------|
| 1 | 组合/装配声明 | 产物是否包含该能力 | 产物中不存在 |
| 2 | 可见清单（调用方可见的 schema/规格） | 调用方能否看见 | 清单不含，无报错 |
| 3 | 执行注册 | 能否真正调用 | 可见但调用时报未接线 |
| 4 | 会话/请求规格 | 本次会话是否携带 | 主流程里不可用 |

### 操作步骤

1. 逐层检查四层声明是否都有 → 补缺
2. 校验闭包语义：声明面随打包裁剪整体退场，无悬挂引用
3. 载荷按契约映射，不原样过边界

### 接口变更：expand → migrate → contract

- **expand**：新增兼容形态（加可选字段、加新入口），旧形态保留
- **migrate**：逐个消费方切换到新形态
- **contract**：确认旧形态无人使用后再删除

判据：加可选字段是安全变更；删除消费方依赖的字段、修改字段类型是破坏性变更。

### 契约断言（轻量，不引入框架）

- **只断言消费方实际用到的字段**：按 schema/类型匹配断言，不追提供方全量 schema——过度规格化会让无关变更误报
- **断言三态**：新增可选字段放行；删除消费方依赖字段、字段类型变更必须失败
- **事故回流**：任何在集成环境暴露的接口问题，都要补成一条契约断言，否则同类问题不会被门禁拦截
- **契约覆盖 = 消费方用例覆盖**：没被用例走过的交互，等于没有契约保护

### 错误处理（症状 → 检查点）

| 症状 | 优先检查 |
|------|---------|
| 可见但调用报未接线 | 层 3 执行注册 |
| 清单不含但无报错 | 层 2 可见清单 |
| 执行成功但下游拿不到上下文 | 层 4 会话/请求规格绑定 |
| 只读能力未接线 | 读取端口的装配 |

## 支柱 3：证据驱动验证

### 四档（由低到高，重要结论用高档）

| 档 | 手段 | 判据 |
|----|------|------|
| 0 | **黄金基线**：移植前从源仓跑出实际输出，归一化后冻结 | 移植后零差异，或有差异逐条判定 |
| ① | 静态对账：类型检查 + 产物清单对账 + 测试全绿 | 全部通过 |
| ② | 活体检查：运行时读取实际状态（计算样式、schema、事件序列） | 实测 = 预期 |
| ③ | 实景操作：真实输入后截图/状态存档 | 元素在场且形态正确 |

### 黄金基线纪律

- 非确定性值（时间戳、随机 ID、迭代顺序、浮点格式）在边界归一化，否则每次都是噪音
- 有差异必须逐条判定：预期变更（更新基线）还是回归（修代码）
- **禁止无脑更新基线**——橡皮图章式的快照更新等于零保护
- 冻结时已知的缺陷要标注（注释或工单），后续作为独立变更修复
- 只冻结本次改动涉及的分支，覆盖跟随变更，不求全量

### 双仓对照评估（同一输入跑两边）

同一输入（snippet、脚本或请求）在源仓与目标仓各自的装配链上直跑（用同构临时文件树），四维度采证：

| 维度 | 采什么 |
|------|--------|
| 结算/输出形态 | 最终产物与返回结构 |
| 日志捕获 | 两侧日志级别与关键字段 |
| 事件类型序列 | 事件种类与顺序 |
| 时长画像 | 各阶段耗时（单次采样不作性能结论） |

逐维度给双侧证据，无法判定的维度明确写原因；判断「两边都没有」时按 R15 做双侧逐行 diff。

### 证据通道交叉

单一通道会漏，重要结论至少两路交叉：

| 通道 | 能看到 | 盲区 |
|------|--------|------|
| 应用诊断日志 | 装配/失败事件 | 错误字段可能是脱敏投影 |
| 进程级调试通道 | 完整错误对象、真实 DOM | 需直连运行进程 |
| 状态库 | 运行状态、事件序列 | 需一致性快照（WAL 等） |
| DOM/结构查询 | 可见实例的节点 | 多实例时可能命中隐藏实例 |
| 框架内部探针 | 组件内部状态 | 并发渲染可能丢弃调用 |

## 移植前冻结（第 0 步）

1. **版本锚点与许可**：记录源仓 commit/tag；确认许可与归属允许搬运
2. **回归陷阱清单**：列出目标仓**已改进、可能被源版本冲掉**的行为，移植后逐条复验
3. **行为清单**：每条可观测行为 + 验收方式，与链路图一起作为规格
4. **黄金基线**：按支柱 3 的纪律从源仓采集并冻结

## 铁律速查

| 规则 | 内容 | 违反后果 |
|------|------|---------|
| R1 | 组合产物中的保留路径只允许类型导入，禁止值导入 | 产物在隔离环境解析外部依赖时报类型错误 |
| R2 | 声明面多层一致（组合声明 / 可见清单 / 执行注册 / 会话规格） | 调用方不可见，或可见但执行报未接线 |
| R3 | 可见面可能经中间合并层聚合，不直连注册表——外部能力必须显式声明到该层 | 注册了但调用方永远看不见 |
| R4 | 开发服务器/打包器的预打包缓存——源码改动后必须重启或清缓存 | 在旧缓存上调代码，以为修了但没生效 |
| R5 | 多实例共存是常态——取证必须过滤不可见实例 | 撞隐藏实例，误判为状态衰减 |
| R6 | 宿主诊断字段可能是脱敏投影 | 只看日志永远拿不到完整错误对象 |
| R7 | 组件身份必须稳定（禁内联包装导致重挂） | 框架判别为新组件 → 卸载重挂 → 局部状态丢失 |
| R8 | SSR/静态渲染下外部 store 订阅走服务端快照（恒缺席） | 高频重渲染场景不可用，改用快照读取 |
| R9 | 冲突残留（stash pop 等）必须即时清理 | 配置/JSON 损坏，启动失败 |
| R10 | 载荷不原样过边界（按 wire 契约映射） | 客户端按存储形态消费 → 类型错误 → 整块降级 |
| R11 | **落盘即接线**：组件/模块落盘前先建消费者（stub 也行）；宿主端口声明属于声明面，新增需同步「端口声明 + 注册 + 消费」三处 | 组件完整、样式齐备、零消费点，功能永远不出现 |
| R12 | 流水线执行器的 cwd 是主会话工作区，不是任务工作树——测试与写入路径必须绝对化并在人设写明防越界 | 测试跑了别的仓库；执行者越界改主仓库 |
| R13 | 程序化输入（合成事件）可能被忽略——注入后必须轮询「用户可见效果出现」确认成功，失败重注入设上限；真实输入设备是可靠替代 | 输入静默丢失且无报错 |
| R14 | 并行实例隔离三件套（端口 + 调试参数 + 状态目录）——起实例前查端口占用；操作前核对实例归属；开发服务器自动换端口会导致实例加载错前端 | 数据写进别人的实例目录 |
| R15 | 「两边都没有」的结论必须双侧逐行 diff 背书——grep 未命中 ≠ 不存在（实现可能换名） | 误判「需立项」实为「已对齐」 |
| R16 | 迁移完成必跑两个收尾审计：导出面 × 消费点交叉核对；样式/资源孤儿比对 | 「已定义未消费」静默搁浅 |

## 一致性台账

每个能力一行，状态只有四种：未开始 / 已移植待验 / 已验证 / 故意偏离。**故意偏离必须写理由**，
否则后续审计会把「有意不搬」误判为缺口。模板见 `references/parity-ledger.md`。

## 收尾审计（迁移完成后的强制动作）

1. **导出面 × 消费点交叉核对**：列出每个组件/模块的导出，逐个全仓查找消费点（排除定义自身与测试）——零消费即缺口候选，再判定：内部子件（非缺口）/ 真缺口（给出应消费位置）/ 死代码（删除）
2. **样式/资源孤儿比对**：样式前缀 × 引用位置；孤儿意味着「写好了但没接全」
3. **规范源对照**：每个真缺口查源仓库同名实现在哪被消费——消费位置就是移植落点
4. **台账对账**：逐条收口一致性台账——「已移植待验」不得计入完成，「故意偏离」须有理由
5. **可回滚确认**：新路径必须能通过开关/配置单独关闭，或可在版本控制上独立回退；旧路径在验证通过前保留（对应 expand/contract 纪律）
6. **回执落盘**：审计结论、证据位置、残余风险、回滚方式与开关名写成可追溯记录，不只留在会话里

## 实战反例

| 可能的想法 | 实际现实 | 违反规则 | 实际后果 |
|-----------|---------|---------|---------|
| 「注册了就行」 | 可见面经中间层聚合，不走注册表 | R2/R3 | 能力清单为空但无报错 |
| 「可见清单留空，由功能开关决定」 | 上层展开体要求直接调用，留空即不可见 | R2/R3 | 设计完成但无法启动 |
| 「服务实例传了就行」 | 会话上下文也必须绑定 | R2 | 执行时服务不可用 |
| 「局部状态用 useState 就够」 | 内联包装组件被判别为新类型 → 重挂 | R7 | 弹层状态永远丢失 |
| 「测试 stub 渲染属性就行」 | stub 与真实组件 props 不同步 | R10 | 测试绿但实机崩 |
| 「改完源码刷新页面就行」 | 预打包缓存不随源码更新 | R4 | 反复修改无效 |
| 「组件写完样式写完就行」 | 宿主端口声明面没有它，消费永远缺席 | R11 | 组件落盘但界面不出现 |
| 「测试直接跑默认目录就行」 | 执行器 cwd 是主会话工作区 | R12 | 测试跑了别的仓库 |
