# PR 验证记录与评审线程

按 [PR 修改前状态确认](../SKILL.md#pr-修改前状态确认)取得当前远端 head、base、CI、评审、冲突与审批状态。
只刷新说明或读取状态时，沿用当前远端候选。需同步分支时按已有授权执行。
项目的测试入口、验证状态和报告由项目规则定义。

## 刷新 PR 验证清单

1. 读取最新 PR 正文、当前提交的 CI、评审报告、相关历史作业及现有后续工单。核对归档与测试设计中的人工验收范围。只追查本次口径涉及的旧轮次。
2. 在原验证区同步下表三类记录。沿用现有正文结构和来源，修改受影响的条目。
3. 写入前重读正文和 head/base。任一变化时重新核对受影响条目。写入后从托管平台回读全部适用区域，确认描述、提交和证据链接一致。

| 区域 | 应记录的内容 |
| --- | --- |
| 当前验证 | 远端 head/base、该提交的必需 CI、对应评审报告、冲突和平台正式审批。还在本地的修复注明推送与复验状态。 |
| 历史验证 | 原提交、当轮结果和原始证据，追加修复、复验、归档和后续工单。把后继结果和时间顺序写在同一条事项里。 |
| 人工用例 | 实际场景、待验收或受阻的条件、执行责任与证据。针对真实外部服务和生产写入，沿用用户裁定和相应授权。 |

### 历史失败结案

先确定用户看到的失败来自当前检查、历史作业、评审场景或人工用例。确认旧检查名、提交和原始作业，再找修复提交及覆盖同一行为的复验证据。

- 有修复与对应通过证据时，结果栏写「已关闭（历史失败）」。同一行保留旧失败，附修复或归档链接及后续通过证据。原作业保留失败状态。
- 找到的后继检查缺少同一用例、覆盖已移除或证据不足时，按事实标注待复验或证据待确认。必测失败继续沿用项目的修复与回归流程。
- 当轮待回执有后续结果时补上回执。用户裁定另开工单的既有缺口保留原观测状态，并附工单。
- 例如旧提交因打包检查失败，修复后同一门禁通过。清单显示「已关闭（历史失败）」，同时链接旧失败作业、修复提交和当前通过作业。当前验证区只展示当前提交的检查。

### 人工用例

逐项标记待人工验收、受阻、已通过或待写入授权，并写明可观察的验收条件。隔离测试的通过写明测试环境及覆盖点。历史实机观察注明轮次和覆盖点，真实服务仍待验收时保留该状态。

### 评审发布与合入状态

通过 QEDAReview 读取或发布评审时，先按[使用前同步](../../../orchestration/auto-code-generator/references/qedareview-local-verification.md#使用前同步)更新工具仓。

评审报告 PASS、当前 CI、合并冲突、平台审批和合入授权分别核对。发布评审后先回读提交、场景结果和证据，再更新 PR 摘要。平台审批数或门槛不可读时标明未核实。当前评审与 CI 通过时，可以明确报告已通过的检查及仍待满足的合入门禁。

## 评论与评审线程

本节用于发布、编辑、回复评论以及解决或重开评审线程，操作按当前已有授权执行。

1. 读取 PR 最新状态、head/base、对应 CI 和评审，再读目标评论、线程全文及后续回复。比较正文、更新时间和线程状态。评论数与 ID 可以保持不变。
2. 有新提交、评审或回复时，核对问题是否已解决、代码位置是否已变、原证据是否仍覆盖当前 head。需要本地验证或修改时，按 [PR 修改前状态确认](../SKILL.md#pr-修改前状态确认)同步相关代码和证据。仅回帖时，按问题是否受基线变化影响决定是否需要同步。
3. 已有等价回复时复用其记录。编辑时保留仍有效的正文。只有修复已推送到目标 PR 且验证支持当前提交时，才标记已生效或结案。还在本地的修复注明进度。
4. 实际写入前重新核对 PR、对应 CI 和评审、目标线程内容与状态。变化时重算更新。无法核实最新信息时先保留原记录。


## PR 值守与收敛

### pr-watch 用法

Gitea 的只读快照工具位于 branch-manager 的 `tools/pr-watch.mjs`。从任意工作区运行，设置 `GITEA_SERVER`、`GITEA_REPO`，或在脚本旁的 `pr-watch.config.json` 配置 `server`、`repo`、`login`。扫描自己名下的开 PR 时需要 `GITEA_LOGIN` 或配置文件的 `login`。命令行仓库参数优先于环境变量，环境变量优先于配置文件。

```bash
node <branch-manager>/tools/pr-watch.mjs 94 owner/repo
```

认证使用用户级 `~/.gitea-token`，其次是 `GITEA_TOKEN`，最后才应急使用 GCM。公开仓可降级匿名读取。TLS 默认严格校验证书，经确认的自签证书环境可以显式设置 `GITEA_INSECURE=1`。仓库内的配置和状态文件保持 Git 忽略。

首次运行建立快照，后续只报告变化。信号覆盖 PR 状态、草稿、head/base、mergeable、评论新增/编辑/删除、正式评审及当前提交的 CI 状态和回执。失败作业链接使用 API 实际返回的 `target_url`。状态以服务器、仓库和 PR 号为键，评论和评审正文只存摘要哈希。读取期间候选变化或返回不完整时，当轮保留旧快照。读取权限不足的正式评审显示「不可读」。当前提交的正式批准记录只提供变化信号，实际审批和合入条件以平台分支保护为准。

退出码 `0` 表示成功读取，`1` 表示配置或读取失败，`2` 表示监控的 PR 均已合并或关闭。成功读取后按下面的检查确认交付结论。

### 每轮核对和处置

| 检查 | 处置 |
| --- | --- |
| head 漂移 | 对照平台与本地。远端可快进时在新 head 继续，出现回退或分叉时核对并行写者，保留远端。 |
| base 或 mergeable 变化 | 对照 [PR 修改前状态确认](../SKILL.md#pr-修改前状态确认)。已有同步授权时处理冲突，复验双方受影响功能和装配，再以当前候选重新核对 CI 与评审。 |
| CI 状态或回执变化 | 按当前 head 核对平台必需作业、队列状态和日志，缺失回执继续待确认。失败按下节处置。 |
| 评审或评论变化 | 读取评审全文、线程及正式评审，核对提交、正文与历史记录。按 [评论与评审线程](#评论与评审线程)逐项处理，推送后的结案需有复验证据。 |

QEDAReview 每次独立使用前按[使用前同步](../../../orchestration/auto-code-generator/references/qedareview-local-verification.md#使用前同步)更新。修复后按[本地验证与增量复用](../../../orchestration/auto-code-generator/references/pre-pr-local-verification.md)复验。OpenSpec 等生命周期门禁依项目规则核对当前规格、归档、复核和验证结论。

### CI 失败与重跑

先读取当前提交的原作业与日志。已知环境偶发问题有证据且原生入口支持时，在授权范围内重跑同一提交的受影响作业。保留原失败与重跑回执，只有该提交对应的正式回执通过才更新当前检查。单跑通过只能作为诊断证据。连次失败、原日志缺失或找不到原生重跑入口时如实记录，继续定位原因。为重跑创建空提交会更换候选并使既有 CI 与评审失效，应保留失败状态或在有实际修复后推送新候选。

### 收敛与定时任务

当前 head 的最新评审、所有适用必需 CI、已核对的 head/base、平台无冲突状态均满足时，结束当轮工程收敛。正式审批、分支保护等门禁全部满足后才报告可合入。审批不足时明确当前数和门槛，合入继续按 branch-manager R8。已合并或关闭时结束跟踪，工作树和分支按各自生命周期收尾。

会话内可以轮询或复用已有值守。用户明确要求长期周期监控时，值守提示词写明仓库、PR、工作区、head/base、评审基线和基线债，引用 branch-manager 与项目本地验证入口，带上上述检查、授权范围、变化报告和停用条件。无变化的轮次保持静默。
