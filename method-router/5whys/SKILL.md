# 5 Whys 根因追问

## 前置条件

- 问题已有明确的现象描述（"XXX 出问题了""XXX 不对"）
- 用户能回答追问（交互式），或有代码/日志可查（自动化）
- 问题不是纯技术选型或汇报需求（那是其他 Skill 的职责）

## 铁律速查

| 规则 | 内容 | 违反后果 |
|------|------|:------:|
| **R0** | 每一层 Why 必须基于上一层的答案，不能跳跃或并行 | 因果链断裂，根因错误 |
| **R1** | 追问停在第 5 层或遇到"不可控因素"为止。不强制凑满 5 层 | 无意义追问降低可信度 |
| **R2** | 每层 Why 必须可验证——要么有代码位置，要么有待验证假设 | 无法复现的推理只是猜测 |
| **R3** | 不重复 5W2H 的工作。如果用户有量化数据，应路由到 5W2H | 浪费 Token，输出冗余 |

## 实战反例

| Agent 可能产生的想法 | 实际现实 | 违反规则 |
|---------------------|---------|:------:|
| "只问了 3 层就找到原因了，但说好 5 层，再凑 2 层吧" | 凑出来的 Why 偏离主线，引入错误归因 | R1 |
| "这层 Why 的答案没有代码佐证，但逻辑上说得通" | 说得通 ≠ 事实。没有验证的推理链是空中楼阁 | R2 |
| "用户给了数据，但 5 Whys 也能做，就直接开始追问了" | 有数据用 5W2H 效率更高（一次性定位），5 Whys 是次选 | R3 |

---

## 工作流

```
Phase 0: 确认问题 ──▶ 明确"XXX 出问题了"的现象定义
    │
    ▼
Phase 1-5: 逐层追问 ──▶ 每一层：Why? → 答案 → 验证/标注
    │
    ▼
Phase 6: 汇总根因链 ──▶ A ← B ← C ← D ← E 可视化
    │
    ▼
Phase 7: 输出修复建议 ──▶ 针对每一层给出阻断方案
```

---

## Phase 0: 确认问题

**目的**：确保第一层 Why 基于准确的问题描述。

### 步骤

1. 让用户用一句话描述"出了什么问题"
2. 确认现象是可观察的，不是解释或判断
3. 如果用户描述模糊，追问澄清

### 现象 vs 解释

| 现象（正确） | 解释（错误） |
|-------------|-------------|
| 匹配率只有 21.2% | 因为 AI 输出质量差 |
| API 返回 500 错误 | 因为数据库挂了 |
| 用户无法登录 | 因为认证模块有问题 |

> 第一层 Why 基于现象，第二层开始基于解释。混淆会导致追问方向从一开始就偏。

---

## Phase 1-5: 逐层追问

每层执行相同的三步循环。

### 单层追问模板

```markdown
### 第 {N} 层: Why?

**问题**: {上一层答案或初始现象}

**为什么？**

> {用户回答或 Agent 从代码/日志中推断的答案}

**验证**: {代码位置 / 日志证据 / 标注"⚠️ 待验证"}
**深度**: {已到第 N 层，距根因还有 {5-N} 层}
```

### 追问停止条件

| 条件 | 说明 | 示例 |
|------|------|------|
| **代码根因出现** | 找到了具体的代码决策点 | "因为 `if x > 0` 不处理负数" |
| **不可控因素** | 第三方/外部系统的限制 | "因为上游 API 不返回状态码" |
| **配置/数据问题** | 非代码逻辑问题 | "因为 yaml 里没有配置别名" |
| **已达 5 层** | 标准停止点 | 汇总根因链 |

### 追问策略

| 情况 | 策略 |
|------|------|
| 用户能交互回答 | 逐层提问，每次一问，等回答 |
| 有代码可查 | Agent 自行从代码推理，给出答案后标注来源 |
| 用户回答模糊（"可能""大概"） | 要求证据或代码位置，否则标注"⚠️ 推测" |

---

## Phase 6: 汇总根因链

**目的**：将 5 层追问可视化为因果链。

### 输出格式

```markdown
## 根因链

初始现象 → 第1层 → 第2层 → 第3层 → 第4层 → **根因(第5层)**
    │        │        │        │        │           │
  观察    直接原因   间接原因   深层原因  终极原因     可阻断点
```

### 根因分类

每条追问的答案归类：

| 层 | 类别 | 可阻断性 |
|:--:|------|:--------:|
| 1-2 | **直接原因** | 🟢 容易阻断，修复成本低 |
| 3-4 | **深层原因** | 🟡 可阻断，需要设计变更 |
| 5 | **根本原因** | 🔴 需系统性修复，阻断后问题永久消失 |

---

## Phase 7: 输出修复建议

**目的**：针对每一层给出阻断方案，优先推荐阻断深层和根本层。

### 输出格式

```markdown
## 修复建议

| 层 | 阻断策略 | 位置 | 效果 |
|:--:|---------|------|:----:|
| 1 | {临时缓解方案} | — | 🩹 短期 |
| 3 | {流程改进} | {file:line} | 🟡 中期 |
| 5 | **{根因修复}** | {file:line} | ✅ 长期 |

### 推荐行动
1. **立即**: {第 1 层阻断} — 止血
2. **本周**: {第 3-4 层阻断} — 消除重复发生
3. **本月**: **{第 5 层阻断}** — 根除问题
```

## 错误处理

| 环节 | 失败条件 | 处理方式 |
|------|---------|---------|
| Phase 0 | 用户描述的现象是解释而非现象 | 追问：能描述一下你具体看到了什么吗？（报错信息/日志/数字） |
| Phase 1-5 | 某一层用户不知道答案 | 标注"⚠️ 第 N 层答案缺失"，从代码/日志中自行推断，无法推断则停止 |
| Phase 1-5 | 某一层引出多个并行的 Why | 选择一个最可能的主线深入，其他分支记录为 `📎 分支链` |
| Phase 1-5 | 追到"人的失误"（写错了/忘了） | 这是无效根因。继续追问：为什么流程允许这个失误发生？ |
| Phase 6 | 链长 < 3 层 | 信息不足但不必强凑。标注"⚠️ 根因链较短，可能未触及根本原因" |

> **核心原则**：5 Whys 的价值不在于层数，而在于有没有追到"可阻断的代码级或配置级根因"。追到了 3 层就停比瞎凑 5 层强 10 倍。

## 输出格式建议

- 追问过程用折叠块展示（完整但可跳过）
- 根因链用 ASCII 箭头图
- 修复建议用表格 + checkbox action items
- 输出尾部加衔接提示：`💡 建议用 SCQA 格式化此报告`
