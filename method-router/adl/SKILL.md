# ADL 矩阵（技术生命周期评估）

## 前置条件

- 评估对象是**一项技术/框架/平台**（而非多个同类方案对比——那是 Pugh）
- 需要判断的是**采用时机**（现在用/观望/放弃）

## 铁律速查

| 规则 | 内容 | 违反后果 |
|------|------|:------:|
| **R0** | 生命周期判断必须基于证据（发布时间/社区活跃度/采用率/维护状态），禁止凭热度感觉 | 热度 ≠ 阶段，跟风必踩坑 |
| **R1** | 四个阶段必须给出判断依据，模糊时标注"介于 X/Y"而非硬选 | 硬选阶段 = 伪精确 |
| **R2** | 必须结合自身定位（团队能力/风险偏好/业务需求），脱离定位的结论无意义 | 同技术在不同团队结论不同 |
| **R3** | 结论是"建议"而非"命令"，必须列出采用/观望/放弃各自的前提条件 | 剥夺决策者的选择权 |
| **R4** | 评估后 3 个月内应复查一次（生命周期变化快） | 半年后结论已过期 |

## 四阶段特征速查

| 阶段 | 特征 | 采用策略 |
|------|------|---------|
| **引入（Emerging）** | 发布 <1 年、API 不稳定、社区小、创新强 | 观望为主；团队技术强+业务高风险偏好可 PoC |
| **增长（Growth）** | 快速迭代、社区增长快、主流开始采用 | 适合跟进：PoC → 试点 → 推广 |
| **成熟（Mature）** | 稳定、API 冻结、社区平稳、生态完善 | 主流选择：无特别风险 |
| **衰退（Decline）** | 维护停滞、社区流失、替代品出现 | 不新增采用；存量评估迁移 |

## 工作流

```
Phase 0: 明确对象 ──▶ 技术 + 使用场景（用户确认）
    │
    ▼
Phase 1: 收集证据 ──▶ 发布时间/版本节奏/社区/采用率/维护状态（用数据说话）
    │
    ▼
Phase 2: 定阶段 ──▶ 四阶段定位 + 判断依据（模糊处标注区间）
    │
    ▼
Phase 3: 结合定位 ──▶ 团队能力/风险偏好/业务需求 → 建议（采用/观望/弃用）
    │
    ▼
Phase 4: 列前提 ──▶ 每项建议的前提条件（什么情况下改变结论）
    │
    ▼
Phase 5: 输出 ──▶ 结论 + 复查提醒（3 个月后复查）
```

## 实战反例

| Agent 可能产生的想法 | 实际现实 | 违反规则 |
|---------------------|---------|:------:|
| "这技术最近很火，值得跟进" | 热度是营销不是阶段证据 | R0 |
| "肯定是增长期，不用查" | 不查数据 = 拍脑袋 | R0 |
| "结论：建议采用" | 没结合团队定位的建议是空话 | R2 |
| "这技术成熟稳定，放心用" | 成熟期也可能被替代品快速淘汰（如旧框架） | R3/R4 |

## 与 Pugh 的分工

| 场景 | 用 ADL | 用 Pugh |
|------|--------|---------|
| 一项新技术要不要用 | ✅ 定生命周期阶段 | — |
| 多个同类方案选一个 | — | ✅ 同阶段内量化对比 |
| 组合用法 | ADL 筛掉衰退期方案 → Pugh 对剩余方案打分 | |
