# ADR 架构决策记录

## 前置条件

- 有一个**已做出或正在做的决策**（技术选型/方案定案/规则变更/边界划分）
- 需要的是**结构化归档**（而非探索过程——那是 Pugh/Design Thinking）

## 铁律速查

| 规则 | 内容 | 违反后果 |
|------|------|:------:|
| **R0** | 决策后 24 小时内记录，禁止拖延归档 | 背景细节丢失，记录变摆设 |
| **R1** | 理由必写且具体（含数据/权衡），禁止"因为好/大家都这么用" | 无理由的 ADR 无法被挑战与演进 |
| **R2** | 备选方案必列（至少 2 个，含被否理由） | 看不到被否的选项 = 看不到思考过程 |
| **R3** | 状态字段必填且可演进（proposed/accepted/superseded/deprecated） | 无法区分"有效"与"已废弃"决策 |
| **R4** | 后果（正面+负面）必写，负面后果是未来回访的入口 | 只写好处 = 埋雷 |

## 模板（一页）

```markdown
# ADR-{编号}: {决策标题}

- 状态: proposed | accepted | superseded | deprecated
- 日期: YYYY-MM-DD
- 决策者: {角色}

## 背景
{为什么需要这个决策：问题、约束、触发事件}

## 决策
{最终选择，一句话说清}

## 理由
{选择它的具体原因：数据/权衡/与目标的关系}

## 备选方案
- {方案 B}：{简介} — 被否理由：{…}
- {方案 C}：{简介} — 被否理由：{…}

## 后果
- 正面: {…}
- 负面: {…}（可接受原因：{…}）

## 演进记录
- {日期}: 初始 proposed
- {日期}: accepted（{触发原因}）
```

## 工作流

```
Phase 0: 确认决策已定或基本成形（未定先走 Pugh/Design Thinking）
    │
    ▼
Phase 1: 收集素材 ──▶ 背景 / 决策 / 理由 / 备选 / 后果 五要素
    │
    ▼
Phase 2: 编号归档 ──▶ 放入 docs/adr/ 或知识库 analysis/（编号递增）
    │
    ▼
Phase 3: 状态标记 ──▶ 初始状态（proposed 或 accepted）
    │
    ▼
Phase 4: 关联引用 ──▶ 在相关文档/代码注释中引用 ADR 编号
```

## 实战反例

| Agent 可能产生的想法 | 实际现实 | 违反规则 |
|---------------------|---------|:------:|
| "决策做完了，等有空再补记录" | 三天后背景细节已丢，记录变成编造 | R0 |
| "理由写'性能更好'就够了" | 无法量化就无法被挑战，也无法指导后续演进 | R1 |
| "备选方案没必要写，反正没选" | 被否选项的理由是防回归的最强文档 | R2 |
| "状态默认 accepted，反正定了" | 未评审就 accepted = 跳过挑战环节 | R3 |

## 归档位置约定

- 项目决策 → `docs/adr/ADR-{编号}.md`
- 个人/方法论决策 → 知识库 `knowledge/analysis/`（关联 knowledge/index.md）
- 每季度回访一次 superseded 的 ADR，确认是否需 deprecated
