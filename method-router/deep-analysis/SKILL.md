# 5W2H 深度根因分析

## 目标与边界

把“哪里失败”与“为什么失败”分开回答。证据不足时，交付最后成功点、首个未完成阶段、候选原因及最小验证动作；不强行给出唯一根因。

适用于用户要求深度分析、根因定位、解释反复失败、性能或数据异常。简单事实查询无需展开全部维度。

默认先只读诊断。分析请求不自动授权重启、清空数据、关闭保护、业务写入或修改产品。用户已授权的实施可继续，但仍须遵守项目流程和范围。复用项目现有规格、测试和记录，不另建第二套持久证据体系。

## 基本规则

1. **事实可追溯**：为关键结论关联日志、命令结果、源码位置、请求或截图。缺少数据标“未知”，允许有依据的假设和不确定性。
2. **症状不等于原因**：超时只证明期限内未满足条件；端口监听不等于服务就绪；界面可见不等于模型或业务链路可用。
3. **先核对同一对象**：区分运行批次、进程、版本、配置、用户数据目录、连接和业务目标。不同批次的证据不能拼成同一次成功。
4. **源码必须匹配实物**：本地源码、安装包、生成产物和实际加载版本分别核对。无法匹配时，源码仅作解释候选，不作为实机根因证明。
5. **不制造精度**：没有测量依据，不填写归因百分比、置信概率、精确 ROI；多个原因可能交互，不要求占比合计 100%。
6. **区分诊断与验收**：修复一个测试辅助脚本不代表修复产品；单测通过不替代真实环境验收；模拟通过需明确标注。

## Phase 0：建立上下文与停止条件

先读取适用项目规则、相关规格、现有测试与经验。记录当前任务目标、授权操作、需保留的数据及已有失败次数。

选择能回答本轮问题的最小范围，写明：

- 要验证的行为及其独立通过条件。
- 当前已知事实、缺失证据、前次实验改变了什么。
- 本轮时间或尝试预算、何时收集证据、何时停止或恢复。

相同条件下已有失败，只有出现新假设、新观测能力或明确改变的变量才重试。不要以“再等等”“再重启一次”替代实验设计。到达预算应报告未决项，不强行补齐结论。

## Phase 1：WHAT——定义现象和影响

用实际期望与观察描述问题，避免一开始就带入原因。例如“180 秒内未进入应用首页”，而非“插件死锁”。

优先列出：

| 项目 | 需要记录的内容 |
|---|---|
| 期望与实际 | 用户行为、成功条件、实际返回或画面 |
| 范围 | 环境、版本、受影响对象、已成功与未执行部分 |
| 基线 | 同条件成功记录；若条件不同，逐项标出 |
| 量化 | 有依据的次数、耗时、样本和分母；未测量不估填 |
| 证据身份 | 批次、时间与时区、进程、构建版本、配置和目标 |

优先使用现有日志、测试输出及受支持的诊断接口。只读取必要内容，脱敏凭据和业务隐私。截图用于证明画面，协议或日志用于证明调用；两者不能互相替代。

## Phase 2：WHERE / WHEN——定位第一个断点

先建立真实时间线，再追调用依赖。按适用架构拆阶段，例如：

进程创建 → 传输连接 → 服务就绪 → 客户端资源加载 → 模块激活 → 界面挂载 → 模型调用 → 业务读写 → 持久化回读。

这只是检查入口，不是假定每个系统都有这条串行链；应以实际 await、回调、事件、并行分支和门槛为准。

对每个相关阶段记录“进入、完成、失败、未观测或未执行”，定位最后成功点和首个未完成阶段。没有日志不自动等于没有执行，需核对日志覆盖范围和落盘时机。

关键注意：

- 区分实际等待时间、外层测试总时长、超时后的截图和清理时间。
- 进程退出、崩溃文件或断连若发生在清理之后，不能倒推为最初原因。
- 一个“加载中”画面可能覆盖多个阶段，不能根据文案直接锁定具体模块。
- UI 之外尚未发出模型请求时，不把问题归因于模型额度或回答质量。
- 异步任务被启动不等于上层等待它完成；查清实际等待关系再判断阻塞或死锁。
- 版本、缓存、动态安装、启动参数、代理、证书、用户目录等差异都是待控制变量，不能只比较代码。

记录精确源码位置；闭源环境可使用实际安装版本、公开状态、日志和产物定位，不能编造文件行号。不要因链路超过五层而截断重要因果关系。

## Phase 3：WHY——形成可反驳的假设

每条解释明确标记：

- **已观测事实**：直接证据证明发生了什么。
- **推断**：由哪些事实推出，成立依赖什么前提。
- **候选原因**：尚需实验区分的解释。
- **已排除或已削弱**：排除范围及仍未覆盖的条件。

为主要候选维护一个紧凑表，不穷举无关原因：

| 候选原因 | 支持证据 | 反证或缺口 | 可区分的预测 | 最小验证动作 |
|---|---|---|---|---|
| 示例：某模块初始化未完成 | 最后完成日志在其前 | 无逐模块状态，其他依赖也未观测 | 同条件移除该模块后阶段能前进 | 保持其余条件不变的隔离对照 |

“恢复普通启动后正常”只能证明那组条件可工作。如果普通启动同时改变参数、探针和加载顺序，不能证明任何单一差异是原因。

遇到数据冲突，先核对来源权威性、版本、时间口径、样本和分母。日期较新不自动更可信；保留冲突直至解释。关联不当作因果，最近提交者不自动是责任人。

## Phase 4：HOW——设计与执行最小实验

优先选择能最大程度区分候选、风险低且可恢复的实验。每次实验说明：

1. 假设及与替代解释不同的预测。
2. 固定条件、唯一主动改变的变量；无法固定的混杂因素。
3. 观测指标、独立成功条件、采样位置与时间。
4. 有界期限、失败后的取证动作及恢复方式。
5. 实际结果、对假设的影响、下一步或停止结论。

尽量使用匹配基线的 A/B 对照。注意探针、调试参数、日志和测试夹具本身可能改变时序或依赖；必要时先验证观测工具是否影响被测对象。

对于启动或 UI 卡住，在自动清理前有界采集关键状态、网络失败、运行时错误、模块进度和截图。CDP 适用于可连接的浏览器/Electron 页面；需先确认目标实例和页面身份。不要为取证擅自重启带未保存内容的浏览器，不把 CDP 检查称为所有原生窗口验收。

超时后先判断是否仍有有效进展、预算是否合理。只有已有进度证据和明确的新预算时才延长等待；不能以调大超时掩盖未定位的阻塞，也不能删除验收门槛换取通过。

根因可确认的依据包括可重复的干预对照，或足够直接的错误与调用链证据。对不能实验的问题，说明证据强度和限制，不宣称已经排除所有其他解释。

## Phase 5：WHO / HOW MUCH——落地修复与成本

按模块拥有者、依赖边界和实际接口分配处理责任，不按最近修改者归责。说明谁有能力确认缺失证据或执行后续动作；未知负责人就标未知。

将措施分为：已确认问题的修复、临时缓解、待验证假设的实验。不要把缓解写成根因修复。

成本按已有依据给出范围，区分等待、实施、回归和真实验收；未知时注明需先测量。优先级结合影响、复现概率、证据强度、风险和工作量，不要求无依据的精确 ROI 才能行动。

若进入代码实施，加载适用编码规范并沿用项目流程。需要完整修复闭环时转入 evidence-driven-dev；此 Skill 不重复建立其实施和评审机制。

## Phase 6：CHECK——验证与收口

先检查诊断结论是否超出证据，再检查修复：

- 原失败是否在同条件重现；若无法重现，诚实记录。
- 修复后是否通过独立预期，关键反例和受影响路径是否覆盖。
- 实际加载产物是否包含修复，真实运行目标是否正确。
- 已修复的辅助脚本、尚未定位的启动问题、未执行的业务验收分别列出。
- 结果是否写回项目已有权威记录；临时探针与环境是否按约定恢复。

并非每个问题都需要大规模测试；验证强度匹配影响。无法完成真实验收时保留未完成或受阻状态，不把局部通过升级为整体完成。

## 输出约定

先给出最重要的已知结论，再按问题复杂度组织内容。无需机械生成七个长章节，至少说明：

1. **卡在哪里**：最后成功点、首个未完成阶段、已确认与未决边界。
2. **依据是什么**：关键时序和证据位置，版本及环境差异。
3. **为什么还不能确定**：最有解释力的候选及反证缺口。
4. **下一步怎么做**：最小区分实验、停止条件、恢复方式；或已确认修复及验证。

不要用完整的报告格式掩盖缺少证据。若只有症状定位，结论就应停在症状定位。
