# 鱼骨图（Fishbone / Ishikawa）

## 定位

多因素混杂场景的根因分析框架：先按维度穷举所有可能原因（广度），
再逐条验证收敛到少数主因（深度）。解决"原因太多、不知道从哪下手"
的问题，防止分析漏掉某一类原因。

## 适用场景

- 问题症状模糊，无法直接看出根因（任务积压、订单下降、bug 频发、性能劣化）
- 可能原因分布在多个方向，单条线索追下去容易只见树木不见森林
- 需要团队或多个 Agent 协作全面找原因，再统一收敛
- 用户提到：鱼骨图、因果图、Ishikawa、原因太多、从哪下手、全面找原因

## 核心步骤

1. **明确问题现象并量化** — 把问题写成一句可度量的话（现象 + 影响指标 + 当前值）
2. **确定分类维度** — 默认 6M（人 Man / 方法 Method / 设备 Machine / 材料 Material /
   环境 Environment / 测量 Measurement）；可按场景替换为流程阶段、模块、系统层次
3. **各维度逐类枚举可能原因** — 头脑风暴式列出该维度下的所有候选，先不管
   重要性和证据，避免过早收敛
4. **深挖每条候选** — 对每条候选追问"为什么是这个原因"，确认其因果路径
   成立，剔除明显不成立的
5. **收敛 Top 3 主因** — 依据证据、出现频率、数据关联度给候选排序，
   收敛出 3 个以内主因
6. **对接后续动作** — 对每个主因继续用 5Whys 单链深挖，或直接制定对策

## 示例

**问题**：接口响应时间从 200ms 劣化到 2s（性能劣化类）。

| 维度 | 候选原因 |
|------|---------|
| 人 | 新成员不了解性能约束、值班人员未关注告警 |
| 方法 | 压测流程缺失、缓存策略未评审 |
| 设备 | 服务器 CPU 老化、磁盘 IO 下降 |
| 材料 | 数据库连接池配置过小、第三方 SDK 版本过旧 |
| 环境 | 并发流量翻倍、CDN 节点故障 |
| 测量 | 监控指标缺失、告警阈值不合理 |

收敛结果：数据库连接池过小（证据：连接等待数上升）、流量翻倍未扩容
（数据：QPS 曲线）、监控缺失导致劣化 2 周未被发现（频率：同类事故第 3 次）。
Top 3 主因确定后分别对接 5Whys 或直接制定对策。

## 边界与互补

| 框架 | 关系 |
|------|------|
| 5Whys | 单链深挖（层次），鱼骨图先广度后深度（维度 + 层次）；鱼骨图收敛出的主因用 5Whys 继续下钻 |
| MECE | 用 MECE 校验鱼骨图的维度划分是否穷尽、候选是否重叠 |
| SCQA | 鱼骨图的分析输出可衔接 SCQA 统一格式化报告 |

## 输出格式

```markdown
## 鱼骨图分析：{问题现象}

| 维度 | 候选原因 |
|------|---------|
| 人 | {候选 1}、{候选 2} |
| 方法 | ... |
| 设备 | ... |
| 材料 | ... |
| 环境 | ... |
| 测量 | ... |

### Top 主因（按证据排序）

| 优先级 | 主因 | 证据/频率 | 下一步（5Whys / 对策） |
|:------:|------|----------|------------------------|
| 1 | {主因} | {证据} | {动作} |
```

> **核心价值**：鱼骨图的价值在于"不漏"——先用维度把搜索空间铺满，
> 再谈收敛。维度定错比候选列少更致命，必要时先过 MECE。
