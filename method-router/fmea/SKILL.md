# FMEA 失效模式与影响分析

## 前置条件

- 有明确的系统边界或流程步骤清单（组件/步骤 ≥ 3 个）
- 需要的是**逐环节的结构化风险盘点**（而非一次方向性头脑风暴——那是 pre-mortem）

## 铁律速查

| 规则 | 内容 | 违反后果 |
|------|------|:------:|
| **R0** | 必须按「失效模式 → 失效影响 → 失效原因 → 现有控制」逐环节走，禁止跳步 | 漏掉中间环节，影响链断裂 |
| **R1** | S/O/D 三项评分必须独立给出，RPN=S×O×D 只做排序参考，不单独作为决策依据 | 单一 RPN 掩盖高风险低概率问题 |
| **R2** | 只对 RPN Top 5-8 或 S≥8 的项输出缓解行动，禁止全量输出 | 50 条行动 = 0 条被执行 |
| **R3** | 不改变用户的变更计划，只标注风险与建议行动。阻止是用户的事 | 越权 go/no-go |

## 评分标准

| 维度 | 含义 | 1 分 | 10 分 |
|------|------|------|-------|
| **S 严重度** | 失效对系统/用户的影响 | 几乎无感知 | 灾难性（安全/数据丢失） |
| **O 发生度** | 失效发生的频率 | 几乎不可能 | 几乎必然发生 |
| **D 检测度** | 现有控制能否发现失效 | 必然能发现 | 完全无法检测 |

**RPN = S × O × D**（1-1000）。另将 **S ≥ 8** 的项单独标红——即使 RPN 不高也必须处理。

## 工作流

```
Phase 0: 明确边界 ──▶ 列出组件/步骤清单（让用户确认，禁止跳过）
    │
    ▼
Phase 1: 找失效模式 ──▶ 每个环节 3-5 个，覆盖正常退化 + 极端情况
    │
    ▼
Phase 2: 逐项分析 ──▶ 每个失效模式填：影响 / 原因 / 现有控制
    │
    ▼
Phase 3: 打分排序 ──▶ 独立打 S/O/D → 算 RPN → 排序 + S≥8 标红
    │
    ▼
Phase 4: 输出行动 ──▶ 仅 Top 5-8 项：缓解行动 + 建议负责人
    │
    ▼
Phase 5: 汇总报告 ──▶ 按 SCQA 格式输出（method-router Phase 4 统一收口）
```

### Phase 1 失效模式找法（防遗漏）

- 正常路径退化：输入异常、并发、超时、资源耗尽
- 依赖失效：上游接口、第三方服务、数据库、缓存
- 状态问题：脏数据、幂等性、部分成功
- 人为因素：误操作、权限边界、配置错误

## 与 pre-mortem 的分工（防重复执行）

| 维度 | pre-mortem | fmea |
|------|-----------|------|
| 视角 | 假想已失败，发散头脑风暴 | 逐环节打分，收敛排序 |
| 输出 | 风险 Top 5 + 缓解方向 | RPN 排序 + 行动清单 |
| 适用 | 代码变更、上线前 | 系统性评估、架构审查 |

**method-router 路由**：risk + 代码变更 → pre-mortem；risk + 系统性评估 → FMEA。两者不重复运行（R3）。

## 实战反例

| Agent 可能产生的想法 | 实际现实 | 违反规则 |
|---------------------|---------|:------:|
| "把每个失效模式都列出来，最全面" | 30 个失效模式的表让决策者麻木，Top 5 才有效 | R2 |
| "RPN 高的就是最危险的" | S=10,O=1,D=1 → RPN=10，但一旦发生就是灾难 | R1 |
| "这个环节太简单，不用分析" | 简单环节往往无控制，正是 D 分高的重灾区 | R0 |
| "风险太多，建议取消这个方案" | 风险分析 ≠ 决策，Agent 只标注不阻止 | R3 |
