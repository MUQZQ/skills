# 管理与协作方法论

## 目标与边界

把“谁负责什么、何时交接、如何并行、遇到不清晰怎么办”变成可执行的协作协议。方法论只负责组织
工作和反馈，不创建第二套任务状态、审批流程或完成结论；项目生命周期、用户授权和仓库规则始终优先。

## 铁律速查

| 规则 | 内容 | 违反后果 |
|------|------|---------|
| R0 | 每项工作只能有一个 `A`（Accountable，最终负责者）；`R` 可以多个，但不能用“大家负责”替代责任归属 | 冲突时无人决策、任务互相等待 |
| R1 | 委派前写清目标、允许范围、禁止范围、约束、预期输出和验证证据 | 子 Agent 只能凭猜测执行，难以验收 |
| R2 | 只有依赖、写入、资源、契约和验证均可隔离的工作才进入并行 WIP；不为填满卡槽拆分内聚场景 | 并行覆盖、失败爆炸半径扩大 |
| R3 | 执行者发现上下文、范围、验收或冲突不清时，立即向 `A` 提问并暂停，不得自行补全授权 | 未经确认的越界修改和错误方向 |
| R4 | 每次交接都返回状态、改动、验证证据、风险和下一步；失败必须升级，不得静默吞掉 | 协调者无法判断真实进度 |
| R5 | 每个工作项明确时间盒、检查点和超时动作；时间压力不能替代测试、审查或验收证据 | 超时后隐瞒风险或制造虚假完成 |

## 方法工具箱

### 1. RACI：先定责任，再定任务

- `R`（Responsible）：实际执行工作的人或 Agent。
- `A`（Accountable）：对范围、决策、整合和最终验收负责的人；每项工作恰好一个。
- `C`（Consulted）：在执行前提供必要意见的人或系统。
- `I`（Informed）：需要接收状态但不参与日常执行的人或系统。

先为每个可验收工作项建立 RACI，再决定是否委派或并行。架构、范围、依赖波次和最终验收不能只由
`R` 自行决定。

### 2. 委派任务卡：让责任可交接

使用六字段任务卡：

```text
目标：单一可观察结果
允许范围：可修改的准确边界
禁止范围：相邻任务、越权动作和不可触碰资源
约束：依赖、技术、时间、权限和上下文限制
预期输出：实现、报告或状态的具体形式
验证证据：命令、断言、日志或人工检查方式
```

任务卡是协作接口，不是第二份持久任务状态。任务状态仍由项目权威 tracker 持有。

### 3. Kanban/WIP：按能力安排并行

使用 `Ready → Doing → Blocked/Review → Done` 的最小看板。`Doing` 的上限由实际可用子 Agent 卡槽、
共享资源和安全隔离条件共同决定：

1. 先完成公共基础和外部依赖，再把可独立验收的场景组放入 `Ready`。
2. 有空闲卡槽时，优先调度已通过隔离门禁的独立场景组。
3. 没有安全独立工作时保持卡槽空闲，不为制造并行而拆分 TDD、公共契约或共享资源。
4. 出现冲突或重叠时冻结相关 WIP，保留改动，由 `A` 重新划分边界。

### 4. Timeboxing/Critical Path：管理时间而不是催促时间

- **Timeboxing（时间盒）**：Sol 为每个场景组设置准备、执行、验证和协调缓冲的时间预算；Luna 在时间盒内
  执行，并在检查点报告剩余工作、风险和是否需要 Sol 决策。
- **Critical Path（关键路径）**：优先识别阻塞后续工作的公共契约、外部依赖、迁移、集成和最终验证；关键
  路径上的工作先排依赖，非关键路径的独立场景才进入并行卡槽。
- **Slack（缓冲）**：保留用于失败恢复、冲突协调和最终验收的缓冲，不把全部时间预算分配给 Luna 的编码。
- 时间盒到期时只允许三种动作：完成并验收、带证据暂停并重新规划、或明确升级阻塞；不得静默延长或跳过
  必要验证。

### 5. OODA/PDCA：按问题状态选择闭环

- 线上故障、快速变化或信息不完整：使用 OODA（观察、判断、决策、行动），先恢复可控状态，再补齐复盘。
- 稳定的流程或效率问题：使用 PDCA（计划、执行、检查、改进），用指标和反馈验证改进是否有效。
- 不要在同一问题上重复运行同类型方法；方法路由已选 OODA 或 PDCA 时，管理层只补责任和协作信息。

## Sol-Luna 协作参考

在 Sol-Luna 场景中，用以下 RACI 作为默认起点，再依据项目生命周期调整：

| 工作项 | Sol | Luna | 协作要求 |
|--------|-----|------|---------|
| 需求澄清、架构和范围 | `A` | `C` | Luna 不清晰时立即提问，Sol 决策后再执行 |
| 场景组、依赖波次和卡槽调度 | `A/R` | `C` | Sol 优先安排安全并行，不能为填槽拆分内聚场景 |
| 时间预算、关键路径和检查点 | `A/R` | `C` | Sol 设置时间盒和缓冲；Luna 在检查点提前报告偏差，不静默超时 |
| 有界实现、测试和证据采集 | `A` | `R` | Luna 按六字段任务卡执行并返回真实证据 |
| 冲突、阻塞和越界处理 | `A` | `R`（发现并报告） | Luna 立即升级，不自行扩大范围或跨边界重试 |
| 最终整合、任务验收、生命周期和 Git | `A/R` | `I/C` | Luna 不更新权威状态、不归档、不 commit/push/部署 |

这里的 `A` 表示协作中的最终责任，不替代用户或项目生命周期的正式授权。Luna 返回的摘要只能作为待
核验执行证据，Sol 必须检查 diff、测试、状态和范围后再完成验收。

## 执行流程

1. **识别协作问题**：判断是角色分工、并行调度、阻塞升级还是持续改进。
2. **建立 RACI**：为每个独立验收项指定唯一 `A`，明确 `R/C/I`。
3. **检查 WIP 与时间**：读取依赖、写入、资源、契约和验证隔离条件，识别关键路径，计算安全卡槽、时间盒、检查点和缓冲。
4. **生成任务卡**：把每个委派项写成六字段任务卡；同一内聚场景保持在同一个执行上下文。
5. **执行与升级**：Luna 按卡执行；遇到不清晰、冲突、阻塞或越界风险立即向 Sol 提问并返回状态。
6. **协调与验收**：Sol 回收 diff、测试和风险，逐项更新项目权威 tracker，处理冲突并决定下一波。
7. **复盘改进**：重复性问题走 PDCA；突发问题走 OODA 后补充复盘，不把一次成功摘要当作流程改进证据。

## 输出格式

```yaml
management_route:
  problem_type: role_split | delegation | parallel_scheduling | time_management | escalation | improvement
  method_chain: [按已选路由填写]
  raci: []
  wip_decision: "并行 / 串行 / 等待依赖"
  time_management:
    timebox: "本轮时间预算"
    critical_path: []
    checkpoints: []
    timeout_action: "完成验收 / 带证据重排 / 升级阻塞"
  assignments: []
  escalation: "需要 A 决策的问题；无则为空"
  acceptance: "逐项验收所需的 diff、测试和状态证据"
```

缺少必要上下文时，不输出虚构的 RACI 或排期；先列出缺口和需要 `A` 决策的问题。

## 常见路由

| 用户意图 | 方法链 | 核心产物 |
|---------|--------|---------|
| “Sol 和 Luna 怎么分工” | RACI → 委派任务卡 | 角色责任矩阵、升级边界 |
| “如何充分利用子 Agent 卡槽” | RACI → Kanban/WIP → 依赖波次 | 并行波次与串行边界 |
| “如何安排时间、避免 Luna 超时” | RACI → Timeboxing → Critical Path → WIP | 时间预算、检查点、缓冲和超时动作 |
| “Luna 卡住或任务不清晰” | RACI → OODA → 升级 | 当前状态、待决策问题、恢复动作 |
| “协作流程反复低效” | RACI → PDCA → 复盘 | 指标、改进项、下一轮验证 |
