# DAG 依赖调度方法

## 目的与边界

用有向无环图表达工作项的硬依赖，在安全边界内缩短关键路径和总执行时长。目标不是最大化并发数或
填满卡槽；DAG 只产生本轮临时调度决定，不拥有任务状态、审批、验收或 Git 权限。

## 输入

- `nodes`：工作项标识、当前状态、可选权威时长或时间盒、资源需求；
- `edges`：有向边，统一定义 `u → v` 为 `u` 必须先于 `v` 完成；
- `grouping`：可选的已批准内聚分组及组内顺序；
- `capacity`：当前可用执行卡槽和独占资源；
- `eligible(node, running, reservations)`：调用方提供的动态安全准入判断；必须相对正在运行的节点和已预留的
  写入、独占资源、公共契约与验证资源判断是否隔离。

## 算法

1. 拒绝未知节点、自依赖和重复冲突边；对标准化后的图运行环检测。发现环时返回完整环路径和
   `NEEDS_COORDINATION`，不得猜测断边或启动执行者。
2. 存在已批准分组时执行图收缩：组内边进入 `internal_order`，跨组边形成组图；收缩后重新检查未知节点、
   自依赖和环。收缩引入环时撤销该分组并重划边界，无法恢复则返回 `NEEDS_COORDINATION`。
3. 计算拓扑层只用于解释依赖结构和估算并行机会，不把层级变成运行时屏障。有权威时长时计算加权最长
   路径；否则只报告最长依赖链，不声称精确耗时。
4. 初始化 `ready_queue`：所有未完成且剩余入度为零的节点进入候选队列，再用
   `eligible(node, running, reservations)` 过滤安全准入。候选多于卡槽时，依次按关键路径剩余长度、可解锁
   后继数量、等待时长排序；没有可靠权重时明确
   使用依赖链和解锁数量作为启发式，不伪造时间精度。
5. 采用完成事件驱动调度：有空闲卡槽时，每选择一个最高优先级的安全节点，都先原子登记其写入、独占资源、
   公共契约与验证资源预留，再基于更新后的 `running` 和 `reservations` 选择下一个，避免两个单独合格但彼此
   冲突的节点同时启动。节点经唯一负责人验收后立即更新后继入度，并把新就绪节点加入候选队列；每次派发
   前仍重新计算安全准入，不等待同一拓扑层的其他节点全部结束。预留只由唯一负责人在验收完成或协调冻结、
   重划后更新或释放。
6. 节点失败或阻塞时，只阻塞失败节点的后继；无依赖的其他分支继续运行。若失败暴露共享写入、资源或
   契约冲突，冻结受影响集合并由唯一负责人重划边界，不覆盖或清理既有改动。
7. 节点、边、分组、能力或安全准入条件变化时，从权威状态重算图与 `ready_queue`；不持久化旧层级或队列，
   不让临时调度结果反向改写正式依赖。

## 输出

```yaml
dag_schedule:
  validation: VALID | NEEDS_COORDINATION
  cycle_path: []
  graph_contraction: []
  topological_layers: []
  critical_path: []
  ready_queue: []
  running: []
  blocked_descendants: []
  scheduling_events: []
  rationale: "为什么当前节点被并行、串行、等待或重新排序"
```

输出必须区分“依赖就绪”和“安全可并行”。卡槽空闲但没有通过
`eligible(node, running, reservations)` 的节点时保持空闲，不能为了提高表面利用率拆分内聚工作或绕过验收。
