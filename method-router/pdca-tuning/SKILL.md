# PDCA 戴明环调优

## 核心概念

PDCA 是驱动持续改进的四阶段循环：

- **Plan（计划）**：定义问题边界 → 采集现状数据 → 根因分析 → 制定方案 → 设定可量化指标
- **Do（执行）**：将方案分解为最小可行步骤，先在小范围试点，记录执行中的一切关键数据
- **Check（检查）**：对比改进前后的量化指标，分析偏差来源，评判"成功/部分成功/需要转向"
- **Act（处理）**：将有效的改进固化为可重复的操作标准，沉淀教训，规划下一轮方向（或结束）

这个过程不是一次性的——每一轮的 Act 输出自然成为下一轮 Plan 的输入。正是这种循环让改进从"碰运气"变成可累积的能力。

## 触发后自动启动

触发本 skill 后，自动进入 PDCA 循环，无需等待人工逐阶段确认：

| 检查项 | 通过条件 | 不通过时 |
|--------|---------|---------|
| 问题是一次性的代码缺陷或配置错误？ | **否** — 问题应具有系统性，根因待定位 | 直接修复，告知用户"这是单次修复，不需要 PDCA" |
| 改进效果能否量化？ | **是** — 至少有一个可被测量和对比的数值 | 定性定义：用可观察的行为描述替代数值指标，按此口径追踪 |
| 是否已有明确方案只需执行？ | **否** — 根因尚不明确，需要探索 | 直接执行方案，但提醒用户在固定方案前应验证根因 |

检查通过后立即读取 `references/phases.md`，自动进入 Plan 阶段开始执行。

## 铁律速查

| 规则 | 内容 | 违反后果 |
|------|------|:------:|
| R0 | 量化一切 — 每个改进目标必须有可测量基线和目标值，无数值不下结论 | Check 阶段无法客观判断成败，全凭主观感觉 |
| R1 | 单一变量 — 每轮只改一个独立改进点，多项改动拆为多轮分别验证 | 因果归因混乱，不知道哪项改动真正有效 |
| R2 | 小步快跑 — 第 1 轮从最小可行改动开始，验证方向而非追求完美 | 大手术式改动失败后无法定位问题，浪费整轮时间 |
| R3 | 归类复用 — 进入 Plan 前先检查问题分类体系，同类问题复用已有方案 | 在相似问题上重复投入分析成本，经验无法累积 |
| R4 | 善用现成 Skill — 能用已有 skill 覆盖的步骤不重新实现 | 重复造轮子，PDCA 循环内耗增加 |
| R5 | 定期跳出审视 — 每 2 轮强制重新评估方向是否正确 | 在错误方向上持续投入，边际收益递减 |
| R6 | 诚实面对数据 — 不达标时禁止合理化失败，回到 Plan 阶段重审根因 | 错误因果假设被保留，后续轮次继续走偏 |
| R7 | 证据分层 — 每个结论标明证据覆盖类型与环境身份，替代证据不得冒充目标范围验收 | 在错误实例或替代链路通过后误报真实成功 |

## 证据覆盖类型与环境身份

每轮开始时先声明验收目标所需的证据覆盖组合，Check 时不得用其他类型替代目标范围：

| 等级 | 证据类型 | 能证明什么 |
|------|---------|-----------|
| L1（静态） | 静态代码、配置与文档 | 设计或实现形状存在 |
| L2（替代环境） | 单元测试、Mock、Fixture、适配器 | 隔离契约在替代环境成立 |
| L3（真实服务） | 真实服务或集成运行 | 后端组件链路可运行 |
| L4（目标流程） | 目标客户端或目标运行环境的完整用户流程 | 用户声明的真实链路成立 |

这些类型表示覆盖范围，不是单一质量排名：L4 不能替代后端不变量所需的 L1-L3，L1-L3 也不能替代用户流程所需的 L4。每个运行基线同时记录：代码版本、配置与数据根目录标识（敏感值脱敏）、输入对象指纹、运行时/服务配置摘要、运行编号和起止时间。无法确认环境身份时，结论只能标记为“待验证”。

## 自治执行原则

PDCA 循环应当自动推进，无需在每阶段结束时等待人工确认：

- **自主驱动** — 从 Plan → Do → Check → Act 自动串联执行。每进入新阶段时向用户发送简短通知，不阻塞等待确认。
- **异常才打断** — 仅在以下情况暂停请求人工介入：指标无法采集导致 Check 无法完成、根因分析出现两种互斥假设、跳出审视判定需切换方向但新方向超出上下文能力。
- **人工可随时介入** — 用户在任何阶段都可插入指令调整方向。接收到人工指令时，将当前阶段状态持久化，按用户指定方向继续。

核心原则：**能自动的全自动，该打断的不含糊**。

## 实战反例

| Agent 可能产生的想法 | 实际现实 | 违反规则 | 实际后果 |
|---------------------|---------|:------:|---------|
| "同时改数据库查询和缓存策略，效果肯定更好" | 两项改动互相干扰，不知道谁起效 | R1 | 如果有效则不知道复制哪个，如果无效则不知道回退哪个 |
| "第一轮就做好完整方案，一步到位" | 一步到位很少成功，失败后全部推倒重来 | R2 | 浪费大量实施成本，增加试错恐惧 |
| "改完之后感觉快多了，不用再测数据" | 主观感受不可复现，无法追踪趋势 | R0 | 看似"优化"了，下次出问题无法复现当时状态 |
| "这个问题跟上次处理的差不多，但上次没记录方案" | 同类问题反复出现但每次都从零分析 | R3 | 团队完全依赖个人记忆，能力无法沉淀 |
| "Check 数据没达标，但改进了 20% 已经不错了" | 用相对改善掩盖绝对目标未达成 | R6 | 根因分析错误被保留，下一轮继续在错路上微调 |

## 错误处理

| 环节 | 失败条件 | 处理方式 |
|------|---------|---------|
| 自动启动检查 | 问题为一次性缺陷，不适合 PDCA | 直接修复，告知用户"单次修复不需 PDCA" |
| Plan | 根因分析出现互斥假设 | 暂停请求人工介入，两个假设无法同时验证 |
| Do | 执行步骤受阻于环境或权限 | 重试 2 次，仍失败则降级为方案建议输出 |
| Check | 指标数据无法采集 | 暂停请求人工介入，改用可观察的行为描述 |
| Check | 连续 2 轮无改善 | 强制触发跳出审视，评估是否切换方向 |
| Act | 标准化方案与实际流程冲突 | 记录冲突点，将"待解决冲突"作为结论输出 |

## 输出质量指标

| 指标 | 目标值 | 检查方法 |
|------|--------|---------|
| 基线数据完整度 | 改前所有核心指标均已采集 | Plan 阶段完成时检查 |
| 改进效果达标率 | Check 阶段对比达到预设目标值 | 每轮 Check 阶段验证 |
| 跳出审视触发率 | 每 2 轮必须执行一次 | 轮次计数器检查 |
| 经验沉淀率 | 每轮 Act 阶段必须输出标准化方案或教训记录 | Act 阶段完成时检查 |
| 证据可追溯率 | 关键结论 100% 关联运行编号和证据 | Check 阶段检查证据账本 |
| 真实链路覆盖率 | 声明为真实验证的阶段 100% 由目标环境执行 | 对照操作边界与执行记录 |

## 轮次管理

用下表追踪每轮 PDCA 的进度。每轮结束时更新，下一轮开始前先回顾此表确认当前轮次和待改进方向：

| 轮次 | Plan 核心假设 | Do 操作摘要 | Check 结果（改前→改后，达标率） | Act 决策 |
|------|--------------|------------|-------------------------------|---------|
| 1 | ... | ... | ... | 进入下一轮 / 标准化 / 方向调整 |

**轮次上限**：最多 5 轮。经验上，超过 5 轮的 PDCA 循环边际收益急剧下降——如果 5 轮仍未达成目标，通常说明 Plan 阶段的根因分析存在根本性偏差，应该重新审视问题定义而非继续微调。从第 4 轮起就主动评估"是否该结束"。

## 四阶段执行

四个阶段的操作指南分布在 `references/phases.md` 中。进入每个阶段前读取对应章节：

- **Phase 1: Plan** → `references/phases.md` 第 1 节
- **Phase 2: Do** → `references/phases.md` 第 2 节
- **Phase 3: Check**（含跳出审视）→ `references/phases.md` 第 3 节
- **Phase 4: Act** → `references/phases.md` 第 4 节

四阶段自动串联执行。每进入新阶段时向用户发送一条简短通知，不阻塞等待。仅在遇到异常条件（无法采集数据、互斥假设、方向切换超限）时才暂停请求人工介入。人工也可随时主动插入指令调整方向。

## 停止决策

何时结束 PDCA 循环？在每轮 Act 阶段结束后对照 `references/decision-matrix.md` 中的决策矩阵：

- 指标达成（达标率 ≥ 100%）→ 标准化并输出总结报告
- 连续 2 轮 Check 无改善 → 总结教训，输出报告
- 跳出审视发现更优替代方案 → 转入 Act，将方向调整作为结论
- 第 5 轮结束 → 强制输出最终报告

## 报告输出

最终产出按 `references/report-template.md` 格式输出 PDCA 总结报告，包含问题概述、轮次汇总表、量化对比、标准化产出的工序/配置、以及遗留问题和下一轮方向建议（如有）。

## 快捷场景指引

| 用户场景 | 建议起点 |
|---------|---------|
| 已有明确改进目标，不确知根因 | 从 Plan 阶段完整开始 |
| 已做过改动，想知道效果 | 跳过 Plan/Do，从 Check 阶段切入 |
| 改进已见效，想固化流程 | 从 Act 阶段开始，聚焦标准化 |
| 问题模糊，感觉"哪里不对" | 从 Plan 的问题定义步骤开始，先定性再定量 |
