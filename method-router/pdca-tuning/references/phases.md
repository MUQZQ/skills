# PDCA 四阶段详细步骤

各阶段的详细操作指南、检查清单和参考示例。

---

## Phase 1: Plan（计划）

### 目标
定义问题边界、采集现状数据、定位根因、设计候选方案、设定可量化的成功指标。

### 步骤

#### 1.1 问题定义
用 5W2H 框架界定问题：

| 维度 | 说明 |
|------|------|
| **What** | 具体什么问题？ |
| **Where** | 出现在哪个模块/环节？ |
| **When** | 什么时间/条件下发生？ |
| **Who** | 影响范围是谁？ |
| **Impact** | 造成什么后果/损失？ |

**示例**：
> **What**：CI 构建时间从 5 分钟增加到 12 分钟
> **Where**：GitHub Actions 的 `build` job
> **When**：从上周三发布 v2.3 后开始
> **Impact**：每次 PR 额外等待 7 分钟，团队每天损失约 30 分钟

#### 1.2 现状数据采集
收集改进前基线数据。不同类型问题的建议采集项：

| 问题类型 | 建议基线数据 |
|---------|------------|
| 性能问题 | 执行时间、吞吐量、资源占用、P50/P95/P99 |
| 代码质量 | 静态分析分数、测试覆盖率、代码重复率、复杂度指标 |
| 流程效率 | 周期时间、等待时间、重做率、阻塞率 |
| 稳定性 | 错误率、重启次数、MTBF、MTTR |

关键原则：**数据口径在改进前后必须一致**，否则对比无意义。

同时建立证据账本。每个关键结论至少关联以下字段：

| 字段 | 内容 |
|------|------|
| 运行身份 | 运行编号、代码版本、起止时间 |
| 环境身份 | 目标实例、配置与数据根目录标识、运行时摘要；敏感值只保留脱敏摘要 |
| 输入身份 | 输入对象标识或内容指纹 |
| 阶段状态 | 阶段名以及已通过、失败、被阻断或未执行 |
| 证据引用 | 日志、截图、追踪、只读快照或输出文件 |
| 证据覆盖类型 | L1（静态）、L2（替代环境）、L3（真实服务）或 L4（目标流程） |

没有证据引用的结论只能标记为“待验证”。页面可见、接口返回和后台进程存活分别是不同证据，不得相互冒充完整业务成功。

#### 1.3 根因分析
使用至少一种结构化分析方法，核心原则是**追溯到可操作的代码/配置/流程层级**。推荐的几种方法：

- **5 Whys**：从表面现象连续问 5 次"为什么"，每次将问题向系统深层推进一层，直到触及可以动手修改的具体层面
- **对比实验**：对比"出问题的"和"正常的"之间的差异——时间段对比、环境对比、配置对比，差异点就是根因候选
- **排除法**：列出所有可能原因，设计最小实验逐个排除，保留最后一个站得住脚的

输出格式：
```
根因假设：[一句话描述]
证据支撑：[哪些数据和差异观察支持这个假设]
可操作点：[根据这个根因，具体可以修改什么]
```

> 如果根因分析停在了"人太多""流程不好"这种无法直接操作的层面，说明还没有追到根。继续问"为什么"直到落到可以改的代码、配置、文档或规则。

#### 1.4 方案设计
基于根因假设，设计候选方案。每轮只验证一个假设，因此方案要精确定位到单点改动。

好方案的三个特征：
- **因果清晰**："因为根因是 A，所以做 B 应该能改善 C"
- **可逆**：失败了可以回退，不会造成不可逆的破坏
- **可测量**：改完之后能用同一口径的数据验证效果

#### 1.5 SMART 指标定义
为改进目标定义 SMART 指标：

| 维度 | 要求 | 示例 |
|------|------|------|
| Specific | 具体数值 | CI 构建时间 |
| Measurable | 可测量 | GitHub Actions 的 job duration 字段 |
| Achievable | 现实可达 | 从 12 分钟降到 6 分钟（可行），而非降到 30 秒（不现实） |
| Relevant | 与问题直接相关 | 构建时间降低 = 团队等待时间减少 |
| Time-bound | 有时间约束 | 本轮改进后，持续观察 3 个工作日 |

## Phase 2: Do（执行）

### 目标
将 Plan 中的方案在最小范围内执行，记录过程数据。

### 步骤

#### 2.1 分解为最小可行步骤
将方案拆分为原子操作序列，每步都应该是可独立执行和验证的：

```
1. [操作描述] → 预期中间结果：[...] → 验证方式：[...]
2. [操作描述] → 预期中间结果：[...] → 验证方式：[...]
```

#### 2.2 小范围试点
第 1 轮不应对全局生效。选择一个隔离的试点环境：
- 如果是代码改动：先在 feature branch 测试，不合入 main
- 如果是配置改动：先对单个服务/实例生效，观察一段时间
- 如果是流程改动：先在 1 个团队试行 1 周

试点环境必须可追溯；在目标环境允许时，使用独立的运行目录、用户数据目录、日志目录或临时输出目录隔离状态。无法隔离时，记录共享边界、潜在污染和恢复方式。已经验证稳定且仍满足输入与配置 lineage 的缓存或中间结果默认保留复用，不应为了“干净”而无条件清除。Mock 只能位于明确边界内，测试结束后不得混入正式产物或真实成功证据。

当验收约束为“只通过用户界面操作”时，产品操作必须由目标客户端的可见控件完成；API、RPC、脚本注入和数据库只允许承担启动控制、只读诊断或证据采集，不得替代业务操作或写入结果。窗口与页面应按稳定的业务状态和可见元素选择，不假设第一个窗口、固定标题或接口成功就是目标流程。

#### 2.3 执行记录
执行真实测试前先核对测试工具是否仍调用当前目标链路，选择器、状态结构、超时策略和断言权威是否与产品一致；发现漂移时先修复或明确标记测试工具限制。

执行过程中持续记录：

| 时间 | 操作 | 预期中间结果 | 实际中间结果 | 异常记录 |
|------|------|-------------|-------------|---------|
| ... | ... | ... | ... | ... |

关键：**记录异常比记录正常更重要**——任何偏离预期的中间结果都是 Check 阶段偏差分析的线索。

对异步或长流程记录适用于该流程的完整生命周期：

```text
started → phase transitions → result_submitted → succeeded / failed / timed_out → cleanup_complete
```

`result_submitted` 和 `cleanup_complete` 仅在流程实际存在相应阶段时记录，不得虚构节点。失败、超时和清理是不同状态，不能合并。重试只用于幂等步骤并记录次数；每次运行必须能判断是同一运行内的子任务/修复重试，还是用户重复发起了新的命令。

### Do 阶段小结模板
```markdown
## Do 阶段小结

### 执行摘要
[一句话描述做了什么事]

### 操作序列
1. [操作] → 预期：[...] → 实际：[...]  ✓/✗
2. ...

### 异常记录
[如有异常，记录细节和初步判断]
```

## Phase 3: Check（检查）

### 目标
对比改进前后的量化指标，分析偏差来源，做一次跳出审视，输出效果判断。

### 步骤

#### 3.1 指标对比
用同一口径测量改进后的数据，与基线对比：

| 指标 | 改前 | 改后 | 变化量 | 变化率 | 达标率 |
|------|------|------|--------|--------|--------|
| CI 构建时间 | 12 分钟 | 6.5 分钟 | -5.5 分钟 | -45.8% | 107% (目标 6 分钟) |

除汇总指标外，还必须给出阶段状态矩阵：

| 阶段 | 状态 | 证据覆盖类型 | 证据引用 |
|------|------|---------|---------|
| ... | 已执行且通过 / 已执行但失败 / 被前置阻断 / 尚未执行 | L1-L4 | ... |

“被阻断”和“尚未执行”不得计为失败或成功；仅有 Mock/静态证据的阶段必须显式标注，避免把局部通过包装成全流程通过。

#### 3.2 偏差分析
如果结果与预期存在偏差（无论正负），分析原因：
- **正向偏差**（超预期改善）：是否有未考虑到的连带效应？
- **负向偏差**（未达目标）：根因判断是否准确？是否有未被控制的变量？

Check 时复核测试工具是否漂移：执行脚本是否实际调用了目标链路，选择器与状态结构是否已经过时，静态门禁是否覆盖实际分支，断言读取的是权威结果还是旧投影/缓存。测试工具自身的固定超时、错误环境或替代操作应单独归因，不能算作产品失败。

#### 3.3 跳出审视（每 2-3 轮触发一次）
暂停当前方向的评估，退后一步问三个问题：

**替代路径**：是否存在完全不同的解法？例如——与其持续优化 CI 构建脚本，不如换一个更快的 CI 平台。如果答案是"有"，记录该替代方案的描述和潜在收益。

**局部最优**：当前方案是否因为 Plan 阶段的根因判断限制了视野？如果根因分析有误，后续所有轮次都在错误方向上优化。重新审视根因假设，看看是否有证据表明它本身就需要修正。

**边际收益**：本轮改进幅度与前几轮相比是否在递减？如果趋势是"第 1 轮 +40%、第 2 轮 +20%、第 3 轮 +5%"，继续在当前方向投入的性价比值得商榷。

如果三个问题中任一指向"换方向更优"，转入 Act 阶段，以"方向调整"作为本轮结论。

#### 3.4 效果判断

| 结果分类 | 判断标准 | 下一步 |
|---------|---------|--------|
| **成功** | 达标率 ≥ 100% | 进入 Act，标准化 |
| **部分成功** | 50% ≤ 达标率 < 100%，且趋势为正 | 进入 Act，规划下一轮优化方向 |
| **无效果** | 达标率 < 50%，趋势为负或持平 | 重新进入 Plan，修正根因分析 |
| **方向调整** | 跳出审视发现更优替代方案 | 进入 Act，输出方向调整结论 |

### Check 阶段小结模板
```markdown
## Check 阶段小结

### 指标对比
| 指标 | 改前 | 改后 | 变化率 | 达标率 |
|------|------|------|--------|--------|
| ... | ... | ... | ... | ... |

### 偏差分析
[正向/负向偏差的原因分析]

### 跳出审视（如触发）
1. 替代路径：[有/无，具体描述]
2. 局部最优：[是/否，证据]
3. 边际收益：[递增/递减，趋势数据]

### 效果判断
**成功 / 部分成功 / 无效果 / 方向调整**
```

## Phase 4: Act（处理）

### 目标
根据 Check 的结果，决定是将改进标准化、沉淀教训、还是规划下一轮方向。

### 步骤

#### 4.1 决策分支

```
Check 结果
├── 成功 → 标准化工序 → 更新文档/模板/自动化 → 输出最终报告
├── 部分成功 → 标准化已生效部分 → 规划下一轮优化的方向 → 开启下一轮
├── 无效果 → 分析根因修正 → 记录本次排除的假设 → 重新进入 Plan
└── 方向调整 → 记录发现 → 输出更优替代方案 → 作为最终结论输出
```

#### 4.2 标准化（仅适用于"成功"和"部分成功"场景）
将已验证有效的改动固化为可被他人重复执行的操作：

- **代码/配置标准化**：提交代码到仓库、更新配置模板、添加自动化校验
- **流程标准化**：更新团队文档、在 checklist 中增加步骤、设置自动化提醒
- **知识沉淀**：在团队文档/知识库中记录"这个变化为什么有效"，便于未来参考

标准化的关键标准：**一个不熟悉上下文的新人，能否仅凭标准化文档完成相同的操作？**

#### 4.3 教训沉淀（适用于所有场景）
无论成功与否，每轮 PDCA 都应至少沉淀一条可复用的经验：

| 轮次 | 经验类型 | 具体内容 |
|------|---------|---------|
| 1 | 有效的根因 | [什么模式/方法帮助定位了根因] |
| 1 | 避免的方案 | [尝试了什么但无效，为什么] |

每轮收口时保存本轮证据包和结论。涉及版本控制时，只有在用户已授权且工作树安全的前提下才形成小范围 checkpoint、同步最新代码；否则只记录当前版本状态和建议动作。只把跨项目的方法、判定规则和防护措施沉淀回通用 Skill，项目路径、接口名、数据样例和临时替代物留在项目记录中。

#### 4.4 下一轮方向（如继续）
为下一轮 PDCA 设定起点：
- 本轮的目标是否已达成？如果没有，剩余缺口是多少？
- 本轮的根因分析是否被验证或证伪？是否需要修正？
- 下一轮的假设是什么？优先验证哪个方向？

### Act 阶段小结模板
```markdown
## Act 阶段小结

### 本轮结论
**成功 / 部分成功 / 无效果 / 方向调整**

### 标准化产出（如适用）
- [修改的文件/配置/流程]
- [更新的文档/模板]

### 经验沉淀
| 类型 | 内容 |
|------|------|
| 有效经验 | ... |
| 排除的假设 | ... |

### 下一步
[关闭循环输出报告 / 进入下一轮 PDCA / 重入 Plan 修正根因]
```

## 参考示例：完整一轮 PDCA

**场景**：用户希望提升代码仓库的 pylint 分数。

> **用户**：我们的 pylint 评分从 8.5 降到 6.2，帮我系统性地提升到 8.0 以上。

### Plan
- **问题**：pylint 评分 6.2，自上周 refactor 分支合入后下降
- **基线数据**：`pylint main/` 输出 6.2/10，共有 47 个 warning
- **根因分析**：对比合入前后 diff，发现新增了 3 个文件未通过 pylint 检查，其中 2 个是团队成员新增的模块，1 个是第三方依赖的包装层。直接原因是 CI 中的 pylint 门槛从 `--fail-under=8.0` 被错误修改为 `--fail-under=5.0`
- **方案**：恢复 pylint 门槛到 8.0，同时创建 pre-commit hook 防止门禁配置被未审查修改
- **成功指标**：pylint 评分从 6.2 → 8.0

### Do
1. 修改 `.pylintrc` 门槛回 8.0
2. 添加 pre-commit hook 校验 pylint 配置文件的变更
3. 修复 47 个 warning 中的关键项

### Check
- pylint 评分：6.2 → 7.8，达标率 97.5%（目标 8.0）
- 剩余 12 个 warning 均为历史遗留的复杂度问题，本质上是设计问题，不属本轮的修改范围
- 偏向正面的部分成功

### Act
- 标准化：pre-commit hook 已生效，门槛变更需要 PR 审查
- 经验：防护机制比代码修复更优先——先堵住退化的入口，再清理存量
- 下一轮方向：处理剩余 12 个复杂度相关的 warning，需要调整函数拆分逻辑
