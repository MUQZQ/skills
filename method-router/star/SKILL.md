# STAR 结构化叙事

## 前置条件

- 有一个已完成的事件/项目/周期需要总结
- 用户能提供基本的事实信息（或 Agent 可从上下文/日志中提取）

## 铁律速查

| 规则 | 内容 | 违反后果 |
|------|------|:------:|
| **R0** | Result 必须量化。不能说"效果好"，要说"响应时间从 2s 降到 200ms" | STAR 失去说服力，退化为流水账 |
| **R1** | Action 必须是"我/我们 做了什么"，不是"应该做什么"或"环境发生了什么" | 情境和任务已经描述了环境，Action 重复环境信息是冗余 |
| **R2** | S+T 不超过全文 30%。核心是 Action 和 Result | 头重脚轻，读者在前 30% 就失去耐心 |

---

## 四要素

```
Situation ──▶ Task ──▶ Action ──▶ Result
  情境         任务       行动       结果
   │            │          │          │
 背景是什么   目标是什么  我做了什么  达到了什么效果
 (20%)        (10%)      (40%)      (30%)
```

---

## 工作流

```
Phase 0: 收集素材 ──▶ 用户口述 / 日志提取 / git log
    │
    ▼
Phase 1: 撰写 S+T ──▶ 情境（背景）+ 任务（目标）
    │
    ▼
Phase 2: 撰写 Action ──▶ 行动步骤（核心）
    │
    ▼
Phase 3: 撰写 Result ──▶ 量化成果 + 反思
    │
    ▼
Phase 4: 组装输出
```

---

## Phase 0: 收集素材

**目的**：从用户或上下文中提取 STAR 所需的原始信息。

### 素材问题

| 要素 | 引导问题 |
|------|---------|
| S | 这件事发生在什么背景下？项目处于什么阶段？团队什么情况？ |
| T | 你的目标是什么？要解决什么问题？有什么约束？ |
| A | 你具体做了什么？步骤是什么？中间遇到什么困难？怎么克服的？ |
| R | 最终结果如何？有什么数据可以证明？学到了什么？ |

---

## Phase 1: S + T（情境 + 任务）

**目的**：用最短篇幅建立上下文，让读者理解"为什么这件事重要"。

### 撰写规则

- S: 2-3 句，只写与 Action 直接相关的背景
- T: 1 句，明确目标或挑战
- 禁止在此阶段写行动或结果

### 示例

```markdown
## 情境

Datasheet 参数提取管道上线后，匹配率持续在 21% 左右，
远低于团队设定的 70% 目标。11 个器件类型中 5 个匹配率低于 11%，
直接影响下游 BOM 生成的准确性。

## 任务

在一周内定位根因，将匹配率提升到 50% 以上。
```

---

## Phase 2: Action（行动）

**目的**：详细描述做了什么，这是 STAR 的核心——展示能力。

### 撰写规则

- 按时间顺序或逻辑顺序排列
- 每步包含：做了什么 + 为什么这么做 + 遇到的困难
- 使用主动语态："我/我们做了 X"
- 3-5 个关键步骤

### 示例

```markdown
## 行动

1. **数据收集与分类** — 导出 11 个器件类型的匹配报告，
   按匹配率分组（高/中/低），发现低匹配率器件集中在 4 种类型识别错误的器件上。

2. **根因定位** — 使用 5W2H 深度分析，追踪数据流从 AI 提取到参数对比的 4 个环节，
   定位到 3 个代码级根因：类型推断关键词过宽(`device_finder.py:399`)、
   "跳过"值未过滤(`yaml_reader.py:209`)、别名映射缺失(`device_config.yaml`)。

3. **修复实施** — 逐一修复 3 个根因，每个修复后跑回归测试验证。

4. **效果验证** — 全量重跑 11 个器件类型的提取和对比，确认匹配率改善。
```

---

## Phase 3: Result（结果）

**目的**：用数据证明行动的成效，量化个人/团队的贡献。

### 撰写规则

- 必须量化：数字、百分比、时间
- 对比前后：before → after
- 包含反思：学到了什么、下次会怎么做
- 1-2 句反思

### 示例

```markdown
## 结果

| 指标 | 改进前 | 改进后 | 提升 |
|------|:-----:|:-----:|:---:|
| 整体匹配率 | 21.2% | 72.5% | +51.3% |
| 低匹配器件数 (< 50%) | 5 个 | 0 个 | -5 |
| 完全匹配器件数 (≥ 90%) | 2 个 | 8 个 | +6 |

**反思**: 本次改进暴露了类型推断阶段的健壮性不足——
依赖关键词匹配而非结构化 Schema 映射。后续在类似管道设计中，
应在类型推断后增加交叉验证环节，而非依赖单一推断源。
```

---

## Phase 4: 组装输出

```markdown
# {标题}

> {一句话核心成果}

## 情境
{2-3 句背景}

## 任务
{1 句目标}

## 行动
{3-5 步关键行动}

## 结果
{量化对比 + 反思}
```

## 场景适配

| 场景 | S+T 侧重 | A 侧重 | R 侧重 |
|------|---------|--------|--------|
| **技术复盘** | 架构背景、技术栈 | 技术决策、关键代码 | 性能指标、稳定性 |
| **项目汇报** | 项目目标、时间线 | 关键里程碑、风险应对 | 交付物、商业影响 |
| **面试回答** | 角色、团队、项目背景 | 个人贡献（"我"做了什么） | 量化成果 + 学习 |
| **事故报告** | 事故影响、时间线 | 排查过程、修复步骤 | 恢复时间 + 预防措施 |
| **周报** | 本周目标 | 完成的任务（列表） | 成果 + 下周计划 |

---

## 与 SCQA 的区别

| 维度 | STAR | SCQA |
|------|------|------|
| 目的 | 展示个人/团队做了什么 | 说服决策者采取行动 |
| 视角 | 第一人称叙事 | 第三人称分析 |
| 节奏 | 背景→目标→行动→成果 | 现状→问题→提问→答案 |
| 适合 | 复盘/汇报/面试 | 分析报告/提案/风险报告 |

---

## 错误处理

| 环节 | 失败条件 | 处理方式 |
|------|---------|---------|
| Phase 0 | 用户无法提供具体数据 | 标注"⚠️ 数据待补充"，用定性描述替代 |
| Phase 2 | Action 少于 3 步（过于简单） | 细化步骤，拆解"做了什么"的每个决策点 |
| Phase 3 | Result 无法量化 | 用定性+对比描述，标注"⚠️ 建议后续补充数据" |

> **核心价值**：STAR 不是写作技巧——它是让不可见的工作变得可见的工具。所有工程师都应该能用 STAR 回答"你做了什么、为什么重要"。
