# PR 前本地验证与增量复用

## 层级边界

本参考只决定“推送或开 PR 前还要验证什么、哪些旧证据可以复用”，不重复其他规则的职责：

- 代码级缺陷、证据状态和严重程度由 `code-review` 负责；
- 提交是否具备资格、审查模式和修复循环由 `code-review-before-commit` 负责；
- 项目原生命令、报告字段和结论值由项目规则负责。

引用方向保持单向；不把 PR 交付逻辑写回审查或提交闸门。PR 检视仍是后续防线，本参考负责的是
把本地可判定的问题在交付前处理掉。

## 目标

把能在本地判定的问题在推送或开 PR 前发现并修完，同时避免每次小改都重跑已通过的全部场景。
本地门禁决定“交付前还要验证什么”，不替代 Stage 4 的最终验证，也不要求重新执行整套收尾。

## 证据粒度

证据挂在场景上，不挂在测试命令上。一条场景的通过证据至少包含：

- 场景与可观察结果；
- 实际命令或可重复方法、退出状态；
- 证据位置（截图、日志、断言、运行产物）；
- 该证据依赖的输入：相关源码、测试、配置、生成结果、数据版本和构建/启动来源。

依赖输入不变，证据继续有效；任一变化，只让受影响的场景失效。不要把“任何改动”都当成全部失效，
也不要因为测试文件没变就沿用实际行为已改变的旧结果。

## 从 spec 推导场景

测试不是“想到什么测什么”，而是从 spec 推导。这里的 spec 指项目自己的规格制品；
项目没有同名文件时使用其对应物，名称与结构以项目规则为准。

- spec 的 Requirement / Scenario / 验收例子是唯一权威；
- 测试设计（如 test-design.md）从 spec 推导输入分类、边界与组合；
- 测试映射（如 test.md）把每个场景映射到测试代码和可观察通过条件；
- 任务清单（如 tasks.md）从 spec 推导实施项；
- 每个 diff 改动块都能反查到 spec 场景，或给出“无行为变化”的依据。

两条反查缺一不可：测试 ↔ spec 场景，diff ↔ spec 场景。反查不上的属于 spec 缺口或越界实现，
先回到 spec 修正或报告，不临时新增没有依据的测试。

## 覆盖体检

从 spec 推导后，按角度检查推导是否完整；只判断适用性，不重复项目规则：

- 边界与输入分类：空、极值、非法、组合；
- 失败与恢复：失败、超时、重试、部分成功、回滚；
- 非功能：性能与规模、并发/取消/幂等、权限/安全/隐私、迁移与持久化；
- 装配与消费者：真实入口、插件职责、依赖方向、共享组件消费者；
- 跨仓与微服务：共享 store、跨服务契约、各仓独立 change；
- 环境与数据：平台、版本、主题、视口、数据版本、配置；
- 交付面：文档/帮助/迁移说明，新测试是否进入项目 CI 入口；
- 测试有效性：旧错误应使断言失败，修复后通过。

缺角处理：spec 漏了，回到 spec 补场景再补测试；本轮不扩展，登记为残余风险并说明影响，
不能静默省略。

## 三层门禁

按成本从低到高执行；前一层失败先修，不带着确定性错误跑昂贵的场景。

### L0 确定性检查

目标是把可机械判定的问题清零，通常秒级：

- 类型检查和静态检查，包括未使用变量；
- 新增 import 或依赖在包清单中声明；
- 源码到生成物、发布目录或打包输入的同步；
- 项目已有的架构、格式和结构门禁。

优先运行项目原生命令；没有对应命令时用最小等价检查，不为此新建一套工具链。

### L1 影响面选择

只运行本次改动实际影响的范围；按影响面选择包、测试文件和场景：

- 用项目已有的依赖图、工作区过滤或测试工具的受影响模式选择包、测试文件和场景；
- 对 UI 场景，按“入口组件 + 关键状态 + 共享模块”判断影响，不按文件路径猜测；
- 把选择结果和排除依据写进本轮验证说明，便于复核。

项目已有工作区过滤、受影响测试或 lane 命令时直接使用；没有时按改动文件到场景的映射手工选择。
不要为了省事退回全量，也不要为了快而跳过受影响项。

### L2 场景级复用

复用旧结果必须逐项满足：

1. 场景的预期和验收条件没有变化；
2. 相关源码、测试、配置、生成结果、数据版本、构建和启动来源没有变化；
3. 上一次结果确实是当前最终实现产生的，而不是更早版本或跳过的结果。

只满足部分条件时重跑该场景，或如实标记为未完成。复用记录写进项目已有的验证报告或状态区块，
不新建第二份账本、指纹脚本或场景数据库；项目已有 capture/check 机制时沿用其字段和命令，
只额外写清依赖输入。

## 缺陷修复的影响面

修复被点名的一处行为时，同时检查同一原因在同组件内的其他入口、状态和文案：

- 同一操作在成功、失败、空态、加载、分页和边界条件下的表现；
- 用户可见的动作名称是否与实际触发的行为一致；
- 合并上游或同步目标分支后，新功能与本改动的交互是否保留双方意图。

这一步是枚举，不是扩大范围；只处理本次改动引入或加重的部分。

## 交付前的状态分账

把两类结论分开记录，不能互相替代：

- 代码问题：Critical / Important / Minor 的未决数量；
- 验收场景：每项的通过、未执行、受阻及责任方。

代码问题清零不等于验收通过。环境或外部服务不可用导致的受阻，记 `BLOCKED` 并写明责任方，
不要在代码上反复制造修复提交来“解决”它。

## 速度与循环控制

- 本地把可修的问题一次修完，再推送或开 PR，避免每修一处就产生一个新 head。
- 已通过且依赖未变的场景不重跑，只重算并重跑受影响场景。
- 一轮评审提出的问题，先在本地按 L0/L1 复现并修复，再统一推送。
- 不为“多跑一轮”而重跑无关场景，也不为“看起来绿了”而跳过受影响场景。

## 与项目流程的关系

项目已有验证状态、报告或 capture/check 协议时，本参考只提供选择与复用判断，不替换其字段、
命令或结论值。项目要求完整重新复核时按项目规则执行；本参考的受影响复用不能覆盖项目的强制
完整复核要求。

## 实战反例

| Agent 可能产生的想法 | 实际现实 |
|---|---|
| “改了样式，页面截图没问题就够了” | 发布目录或打包输入未同步，PR 上仍是旧样式 |
| “测试通过就算场景通过” | 断言常量或映射不等于真实挂载后的可观察结果 |
| “上次跑过，这次改动很小，直接复用” | 相关模块、数据版本或构建来源已变，旧证据失效 |
| “为了保险，把所有场景再跑一遍” | 浪费时间，且不覆盖本地无法复现的环境问题 |
| “代码问题清零了，PR 可以合入” | 仍有未执行或受阻的验收场景，结论不是 VERIFIED |
