# QEDAReview 本地验证

使用 QEDAReview 的 QEDA 项目，每轮本地验证都用 QEDAReview 核对场景、通过条件和证据。范围包括首次验证、修复后的增量验证，以及同步目标分支后的回归。测试执行仍以候选项目原生命令和环境为准。

## 使用前同步

在使用 QEDAReview 前，定位工具仓的检出、确认其配置的官方 remote 与分支，再运行工具仓自己的同步脚本。每次开始新一轮验证或独立使用 QEDAReview 都先同步。已开始的一轮绑定刚核对过的工具提交，续接新一轮时重新同步。

在 QEDAReview 仓库根目录执行。配置使用其他 remote 或分支时替换参数。

    node scripts/sync-repo.mjs --remote origin --branch main --json

检查同步退出码、工具仓最终提交和实际获取的远端提交。记录 QEDAReview 工具提交，同时保留产品 head/base 两个独立标识。脚本报告本地领先时，继续核对远端版本，因为退出码零也可能表示本地领先。

工具仓有本地改动时保留现场。同步失败、分叉、本地领先或相关工具文件已被修改时，优先使用已有且合规的干净检出同步。找不到可用检出时，记录 QEDAReview 验证项受阻，继续可以独立执行的项目原生验证。工具版本和执行来源明确后再补做该项。

## 核对本地候选

1. 同步后读取工具仓当前的 AGENTS 和检视说明。用其提供的入口核对候选规格、范围、历史问题及验收清单。已开 PR 时可用当前版 `context-pack.mjs` 获取与远端候选绑定的上下文。
2. 明确场景来源和实际受测的产品候选。尚未推送的本地改动以本地候选的差异、构建产物及隔离环境为证据。远端上下文仍按远端提交标注，报告指出额外的本地输入。
3. 按[本地验证与增量复用](pre-pr-local-verification.md)运行受影响的项目原生验证。已有证据逐项判断可复用性，历史失败核对对应复验与后续工单。外部服务及生产写入沿用人工验收范围。
4. 用 QEDAReview 的当前检查口径核对实际结果和证据，再更新项目原有验证记录。通过、失败、前置受阻及人工用例按实测记录。需要发布评审时，按[评审发布与合入状态](../../../independent-tools/branch-manager/references/pr-records.md#评审发布与合入状态)处理，沿用现有发布授权。

未开 PR 或工具仅支持读取远端候选时，使用当前 QEDAReview 规则核对本地清单和项目原生证据，按实际能力标记工具检查结果。只读核对与本地验证可以先做，推送、发布正式评审和正式审批分别沿用已有授权。
