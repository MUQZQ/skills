# Project Reviewer：设计验收 review 工程生成器

把一个项目的"基准真相"（设计图、规格、契约、冻结行为）拆解成逐项可执行、可判定、留证据的验收检查，生成本地 review 工程；用户（或评审会话）逐项执行，循环修复直到问题清零。方法论源自 QEDAgent design-qa 实例（视觉真相对照 + P0-P3 分级 + 多轮对照历史）。

**必读顺序**：执行任何判定前先读 `references/verdicts.md`（判定词表有严格约束，写错状态会破坏整套门禁）；编册检查项前读 `references/extraction.md`（七类基准各自的断言提取法）；完整流程与证据规范见 `references/methodology.md`。四个产出模板在 `templates/`。

## 一、核心原则（12 要素速览）

1. **基准真相**：每个检查项必须锚定一个基准物（hash 钉住），禁止凭感觉检查。
2. **基准分类**：七类——UI 稿 / 架构图 / 契约图 / 流程图 / 规格场景 / API 文档契约 / 回归基线，方法随类别不同（见 extraction.md）。
3. **检查项原子化**：一条只判一件事；判据必须可判定（命令/数值/存在性/行为描述），做不到的标 subjective 单独管理。
4. **分级**：P0 数据损坏/安全突破/核心路径不可用；P1 结构性偏差；P2 可见偏差；P3 打磨不阻断。具体语义由阶段 0 的项目映射表定义。
5. **判定词表**：PASS / FAIL / NOT_ACCEPTED / BLOCKED / NA / WAIVED——每个词有触发主体和约束，详见 verdicts.md。
6. **五项视觉检查**（仅 UI 类）：字体/间距/颜色/图标/文案。
7. **交互与运行时检查**（UI/流程类必须有）：真实交互证据，不是静态截图。
8. **状态与尺寸记录**：每份证据记录采集环境（视口/DPR/数据状态/命令+退出码），保证可复现。
9. **对照过程历史**：轮次只追加不覆盖；每轮结论含"复测范围+新增 P0/P1/P2 计数"。
10. **真实数据原则**："预期差异"认定须三要素齐备，且只豁免内容差异，永不豁免容器行为（布局/溢出/截断/状态处理）。
11. **观察不等于接受**：记录性观察与验收结论分离；主观接受只能由用户书面给出。
12. **收尾门禁**：断言级测试证据（文件+行号+分类计数）+ P0-P2 未豁免项清零 + 未覆盖范围声明。

## 二、六阶段流程

### 阶段 0：立项与映射表（强制产出）
- 确定范围：整个产品 / 某特性 / 某变更。
- 产出**项目类型→严重度/T1 语义映射表**并经用户确认。这是就绪谓词的前置——P0"安全/资金"是交易域语义，纯库项目应是 unsound/semver 违约/API panic，移动应用是支付/权限/崩溃，遗留系统是数据丢失/回滚路径。映射表未确认，后续一切不可判定。
- 若项目同时存在外部任务体系（如 OpenSpec tasks.md），声明仲裁关系：reviewer track 是唯一验收状态源，外部勾选须引用 track 判定 ID；reviewer 定位为该任务体系的执行细化，不建第二份任务状态。

### 阶段 1：基准盘点
- 找全基准物（设计图/规格/ADR/API 文档/待冻结行为），逐个分类登记：名称、类别、hash、日期、原始出处、**入档路径**（外部临时文件必须先复制入档再算 hash，否则 hash 无处比对）。
- 基准来源独立性：基准必须来自实现产物之外；禁止以实现截图为基准。规格/特征测试类基准须冻结于实现开始前（commit 时序可证）或由独立会话产出。
- 同级冲突或新鲜度冲突（陈旧设计图 vs 新鲜 ADR）：判 BLOCKED 升级用户，不自行取舍。
- 盘点外部前置阻塞（如未完成的硬前置任务）：直接登记 BLOCKED（引用前置编号），排除出修复循环。

### 阶段 2：实现盘点（只读）
- 盘点路由/页面/状态、公共 API 面、测试清单（unit/e2e/已有门禁）、启动方式、取证手段。只读，不修改任何实现。
- 产出取证准备清单：哪些检查项可以引用现有测试（记下命令），哪些必须人工采集。

### 阶段 3：检查项编册
- 每个基准物拆原子断言 → track 文档检查项表（ID | 断言 | 层级 T1/T2/T3 | 方法 | 判据 | 证据要求 | 状态 PENDING）。
- 编册只以基准物为依据，禁止用实现现状反向裁剪或缩水检查项；编册不由实现方会话起草（判据窄化会在源头发生）。
- UI/流程类 track 必须附状态×路由枚举表（至少：首次进入/空态/运行中/完成/错误），未枚举的状态不得出现在结论范围之外。
- 优先映射现有测试：生成"检查项→现成命令"映射，映射不到的才进人工池。纯视觉像素对照默认 T3 并注明抽样率。
- **就绪谓词（四项 AND，缺项拒绝开跑并输出诊断）**：映射表已确认 ∧ ≥1 条 T1 轨 ∧ 每轨基准已钉住（hash+入档）∧ 每项判据可判定（subjective 单列）。附加约束：P0 检查项全部必须 T1，T1 占比建议 ≥40%。

### 阶段 4：基线执行
- 逐项跑、存证据、记问题。证据规则见 methodology.md（三档分级、断言级引用、晚于代码 rev）。
- 零 FAIL 且零 BLOCKED 时直达阶段 6。

### 阶段 5：修复循环
- 轮次进入准则（三种触发）：上轮所有 FAIL 已修复或已 WAIVED ｜ 用户提交新反馈/新参考物 ｜ 基准经再基线变更。
- 每轮只复测受影响项+邻近项（邻近项=同 track 内共享该实现组件/状态机/测试文件的检查项）。
- 止损：按**问题**计数（非检查项）——同一问题两轮同样失败升级用户；派生检查项（derived-from）继承父项失败计数，防拆项绕止损；拆分/新增检查项须用户确认。每 track 硬上限 3 轮，超限按 NOT_ACCEPTED 强制结项。
- 轮次记录一行制：`rounds/N.md`（ID | 状态 | 证据路径 | 判定），AI 出草稿用户只批注。

### 阶段 5.5：正式环境终验（进入结项的强制关口）
- 在正式集成环境（非临时/隔离取证环境）重跑 T1 全部 + T2 受影响项，并做一次基准并排复核。未终验不得结项。

### 阶段 6：结项
- 门禁：P0-P2 未豁免项清零 ∧ T1 全跑 ∧ T3 至少执行一轮并记录样本 ∧ skip 清单计入未覆盖 ∧ NOT_ACCEPTED 存在时降"有条件通过"并单列待接受清单。
- 结项报告标注基准层级，声明认证强度（回归基线下的 PASS=行为未变，≠ 正确性）；写"抽样复验 X% 未发现失败"，禁写"全部已验证"。

## 三、硬规则（防伪与角色）

- **角色分离**：写代码的会话不能给自己的产出判 PASS；evidence/ 与 tracks/ 对实现方会话只读禁写；实现方材料白名单=仅启动/环境信息，禁止包含操作步骤、预期值、截图。
- **判定单向转换**：BLOCKED→FAIL 允许（证明非环境所致）；FAIL→BLOCKED/NA 禁止。有 FAIL 历史的项终态为 NA/WAIVED 时须单独清点、用户逐项签字。
- **BLOCKED 双语义**：取证条件不可行，或被未关闭的更高优先级问题阻塞（引用阻塞 issue ID）；须用户确认+最小复现尝试证据；结项时强制转 FAIL 或入未覆盖声明。
- **NOT_ACCEPTED 仅用户触发**，必须挂差距描述；subjective 判据项独立清单不阻塞结项，唯一出口=用户书面接受（记录人/时间/原文）。
- **威胁模型声明**（写入工程 README）：本套机制防偷懒与自我证实，不防蓄意导演式造假；单人+同机+同源模型环境下，P0 项建议异构模型评审或显式记录同源折扣。

## 四、人工节点（仅 4 个，各配最小决策模板）

1. BLOCKED 确认：一句话环境事实 + 复现尝试记录。
2. NA/再基线确认：hash 对比或范围条款原文 + 变更理由。
3. 主观接受：差距描述 + 接受原文 + 日期。
4. 止损升级：问题两轮失败史 + 当前修复方案。

## 五、生成物结构

在目标项目根创建 `review_<project>/`（或用户指定目录；遵循项目规则"审查记录不提交"，不进 git）：

```
review_<project>/
├── README.md        # 章程：范围/基准表(含hash)/映射表/13轨式总表/判定规则摘要/执行协议/进度看板
├── tracks/          # 每基准物一份 Txx-*.md（对照材料/检查项表/证据源/对照过程/结论）
├── issues.md        # 跨轨问题清单（ID/级别/状态/所属轮次/复测记录）
├── evidence/        # 证据：按 <轨>/<轮次>/<编号> 命名，附采集元数据
├── rounds/          # 轮次一行制记录 N.md
└── templates/       # 从本技能 templates/ 复制
```

## 六、技能进化

落地后每个新项目（尤其异质形态）作为校准集：结项时把新形态经验回写 `references/extraction.md`，使用统计记入 `USAGE.md`。
