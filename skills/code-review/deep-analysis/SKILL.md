# 5W2H 深度根因分析

## 何时激活

- 用户报告指标异常："匹配率这么低"、"转化率下降了"、"为什么 XX 不行"
- 用户要求深度分析："深度分析"、"根因分析"、"5W2H 分析"、"5W1H 分析"
- 数据管道问题："数据不对"、"匹配不上"、"提取有问题"
- 需要代码级定位的问题："为什么 XX 功能不正常"

## 分析流程

```
用户提出问题
    │
    ▼
Phase 0: 上下文收集 ──▶ 读取 README/AGENTS.md 了解项目架构
    │
    ▼
Phase 1: WHAT 量化分析 ──▶ 现象描述 + 数据收集 + 影响范围
    │
    ▼
Phase 2: WHY 根因推导 ──▶ 因果链分析 + 代码级根因定位
    │
    ▼
Phase 3: WHERE/WHEN 定位 ──▶ 文件:行号 + 错误时序链
    │
    ▼
Phase 4: WHO 责任矩阵 ──▶ 问题 → 责任模块 → 解决者
    │
    ▼
Phase 5: HOW 修复方案 ──▶ 代码级修改 + 效果预估 + 优先级
    │
    ▼
Phase 6: HOW MUCH 成本量化 ──▶ 工时估算 + 资源需求 + ROI + 风险评估
    │
    ▼
输出 5W2H 深度分析报告
```

---

## 铁律速查 (Iron Rules)

以下规则不可妥协，任何 Phase 违反将导致分析结论失效：

| 规则 | 内容 | 违反后果 |
|------|------|:------:|
| **R0** | 每个结论必须有量化数据支撑，禁止使用"可能""大概""应该"等模糊词 | 结论不可信，无法验证 |
| **R1** | 根因必须精确到 `文件:行号` + 具体代码片段 | 无法复现，修复无从下手 |
| **R2** | 因果链必须完整推导（A→B→C），不得跳步或单向归因 | 治标不治本，问题复发 |
| **R3** | 修复方案必须含具体代码示例，概念性描述视为未完成 | 开发者无法落地执行 |
| **R4** | WHY 先于 HOW：根因未确定前，不急于给出修复方案 | 方向性错误，浪费工时 |
| **R5** | 修复成本未量化前，不得给出优先级结论 | P0/P1 排序无依据 |

## 实战反例 (Anti-Patterns)

以下是 Agent 执行深度分析时容易产生的偏差，提前设防：

| Agent 可能产生的想法 | 实际现实 | 违反规则 | 实际后果 |
|---------------------|---------|:------:|---------|
| "问题很明显，不用逐 Phase 走，直接给修复就行" | 跳过 Phase 1-3 的诊断相当于跳过医生的检查直接开药——患者可能死于误诊。表面症状和根因往往不在同一层面 | R2, R4 | 治标不治本，用户验收时发现修复无效，浪费双方时间 |
| "大概在 XXX 文件那一带，不用精确到行号" | 一个文件可能有 500+ 行，模糊定位等同于让开发者大海捞针。更糟的是，Agent 指的"那一带"可能完全错误 | R1 | 开发者花 30 分钟定位到正确行号，信任崩塌 |
| "P3 修复不用写代码示例，提个方向就行" | 所有优先级都应具体，因为 P3 可能被降级为 P0。没有代码示例的建议只是概念，不是修复方案 | R3 | 后续接手者无法判断修复是否对应原始分析 |
| "这个数据和问题关系不大，粗略估计一下就行" | 数据驱动是分析可信度的基石。一个错误估计会导致整个因果链坍塌 | R0 | 归因比例错误 → 优先级错位 → 资源浪费 |
| "我搜到了几个文件可能相关，不逐个验证了" | 相近文件名/关键词匹配不等于逻辑关联。`device_config.py` 和 `device_config.yaml` 可能分属不同模块 | R1, R2 | 错误归因到无关模块，导致跨团队误伤 |
| "工时不好估，就先不写 HOW MUCH 了" | HOW MUCH 是决策者最关心的维度之一。不给工时等于不给预算 | R5 | 管理层无法排期，修复搁置 |

### Phase 0: 上下文收集

**目标**：了解项目架构和待分析问题的背景。

1. 读取 `README.md` 或 `AGENTS.md`，理解项目整体架构
2. 确认用户提出的问题/指标的具体含义
3. 确定需要分析的数据源（报告文件、对比结果等）
4. 识别涉及的核心代码模块

**输出**：
```
== 分析任务确认 ==
问题: {用户描述}
项目: {项目名称}
架构: {简要架构描述}
数据源: {报告/日志/配置文件}
涉及模块: {模块列表}
```

### Phase 1: WHAT — 发生了什么（现象量化）

**目标**：用数据和表格描述问题的具体表现，不做原因推断。

#### 分析维度

| 维度 | 内容 |
|------|------|
| **核心指标** | 当前值 vs 预期值，差距量化 |
| **影响范围** | 哪些器件/模块/用户受影响 |
| **分布特征** | 按类型/模块/时间的分布 |
| **不匹配分类** | AI 独有 / 人工独有 / 值不匹配 的比例 |

#### 输出格式

```markdown
## WHAT: 现象量化

### 核心指标
| 指标 | 当前值 | 预期值 | 差距 |
|------|--------|--------|------|
| 匹配率 | 21.2% | >70% | -48.8% |
| 受影响器件 | 5/11 (45.5%) | 0 | +5 个 |

### 影响分布
| 类型 | 器件数 | 平均匹配率 | 问题 |
|------|--------|-----------|------|
| 类型正确 | 6 | 18.8%-36.8% | 参数名映射不完整 |
| 类型错误 | 4 | 0%-10.7% | Schema 完全错配 |
```

### Phase 2: WHY — 为什么发生（根因推导）

**目标**：通过代码级分析找出根本原因，建立因果链。

#### 分析方法

1. **追踪数据流**：从输入到输出，逐步检查每个环节
2. **定位代码决策点**：找到做出错误判断的代码位置
3. **建立因果链**：A → B → C 的逻辑推导
4. **量化根因影响**：每个根因导致多少比例的问题

#### 因果链模板

```
根因 A → 中间结果 B → 最终表现 C
   │            │            │
  代码位置     影响范围      量化占比
```

#### 根因分类

| 类别 | 说明 | 示例 |
|------|------|------|
| **类型识别错误** | 器件/模块被错误分类 | LDO 被识别为 Active_Crystal |
| **数据质量问题** | 上游输出无效数据 | AI 输出"跳过"值 |
| **映射/配置缺失** | Schema/别名/字典不完整 | 缺少 "Active Crystal" 别名 |
| **算法逻辑缺陷** | 对比/匹配策略不足 | 值对比策略未覆盖边界情况 |
| **流程/架构问题** | 管道设计缺陷 | 缺少类型交叉验证环节 |

---

### Phase 3: WHERE/WHEN — 在哪里/何时发生（精确定位）

**目标**：将每个根因精确到文件和代码行，并分析错误时序。

#### WHERE — 问题定位

| 问题 | 文件 | 行号 | 根因代码 |
|------|------|------|---------|
| 关键词匹配过宽 | `device_finder.py` | 399 | `raw_lower` 匹配 `['active crystal', ...]` |
| "跳过"未过滤 | `yaml_reader.py` | 209 | 过滤列表不含 `"跳过"` |
| 别名映射缺失 | `device_config.yaml` | - | `type_aliases` 无 `"Active Crystal"` |

#### WHEN — 错误时序链

```
T0: AI 提取阶段
    └─→ LLM 输出错误 type + "跳过"值 ──→ *_ai_params.yaml
         ↓
T1: 器件发现阶段
    └─→ resolve_alias 失败 ──→ _infer_from_raw_type 误判 ──→ device_type="Active_Crystal"
         ↓
T2: Excel 解析阶段
    └─→ 非标列名无法映射 ──→ manual_params key 未标准化
         ↓
T3: 参数对比阶段
    └─→ 加载错误 schema ──→ 7 步查找全失败 ──→ 匹配率 0%
```

**时序依赖分析**：
- T1 类型错误是**根因**，导致 T3 的 18 种匹配策略全部不触发
- T0 "跳过"值是**次因**，导致部分参数即使类型正确也无法匹配
- T2 参数名不标准是**第三因**，影响类型正确器件的匹配率

### Phase 4: WHO — 谁的责任（责任矩阵）

**目标**：明确每个问题归哪个模块/角色负责。

| 问题 | 责任模块 | 具体组件 | 解决者 |
|------|---------|---------|--------|
| 器件类型识别错误 | **datasheet-parse** (AI Prompt) | LLM Prompt / type inference | AI Prompt 工程师 |
| "跳过"值未过滤 | **datasheet-parse** (上游) | extract_yaml.py 输出层 | AI Prompt 工程师 |
| 类型推断关键词过宽 | **datasheet-param-compare** | device_finder.py | 代码开发者 |
| 别名映射不完整 | **配置** | type_registry.py | 配置管理员 |
| Excel 参数名未标准化 | **datasheet-param-compare** | excel_parser.py | 代码开发者 |

### Phase 5: HOW — 如何解决（修复方案）

**目标**：给出可执行的修复建议，按优先级排序，附带预估效果。

#### 修复方案模板

```markdown
### P{level} — {修复名称}（预计效果：{提升幅度}）

| # | 文件 | 行号 | 修复内容 | 预计影响 |
|---|------|------|---------|---------|
| 1 | `{file}` | {line} | `{修改描述}` | `{影响说明}` |

**修复代码示例**：
```python
# {file}:{line}
{代码修改示例}
```
```

#### 优先级矩阵

| 优先级 | 修复类别 | 实施难度 | 预计效果 | 影响范围 |
|--------|---------|---------|---------|---------|
| **P0** | 类型识别修复 | 中 | +25% | 全局 |
| **P1** | 数据质量修复 | 低 | +10% | 部分器件 |
| **P2** | 配置补全 | 中 | +5% | Schema 映射 |
| **P3** | 流程优化 | 高 | +5% | 长期 |

#### 效果预估

| 修复阶段 | 预计匹配率 | 依据 |
|----------|-----------|------|
| 当前 | **21.2%** | 实际数据 |
| P0 修复后 | **~45%** | 4 个误识别器件恢复正常 |
| P0+P1 后 | **~55%** | 过滤"跳过" + 补全 Schema |
| 全部修复后 | **~70-75%** | 类型 100% 正确 + Schema 完整 |

### Phase 6: HOW MUCH — 成本与资源量化

**目标**：对每个修复方案进行成本、工时、资源和风险的系统性量化评估，支持决策者判断投入产出比（ROI）。

#### 分析维度

| 维度 | 内容 |
|------|------|
| **工时估算** | 每个修复所需人天（MD），含开发 + 测试 + 回归 |
| **资源需求** | 所需人员角色、技能、工具/环境 |
| **成本估算** | 人天成本 + 工具/基础设施成本 |
| **投入产出比** | 收益（匹配率提升/错误率下降）÷ 成本（工时） |
| **风险评估** | 变更范围、回滚难度、影响面、技术债 |

#### 输出格式

##### 工时与资源表

| 优先级 | 修复名称 | 工时 | 角色 | 风险等级 | 依赖 |
|--------|---------|------|------|---------|------|
| P0 | 类型识别修复 | 3 MD | AI 工程师 (1) + 开发者 (1) | 🟡 中 | 需重新运行全量测试 |
| P1 | 数据质量修复 | 1 MD | AI 工程师 (1) | 🟢 低 | P0 完成后 |
| P2 | 配置补全 | 1.5 MD | 配置管理员 (1) | 🟢 低 | 无 |
| P3 | 流程优化 | 5 MD | 架构师 (1) + 开发者 (2) | 🔴 高 | 需架构评审通过 |

|----------|-----------|------------------|-------------|------|
| P0 | 3 MD | +25% | **8.3%/MD** | ⭐ 立即实施 |

| P2 | 1.5 MD | +5% | **3.3%/MD** | 可并行实施 |

## 错误处理

各 Phase 遇到障碍时的降级与重试策略：

| 环节 | 失败条件 | 处理方式 |
|------|---------|---------|
| Phase 0 | 无 README/AGENTS.md，用户无法描述架构 | 降级：直接询问用户项目入口文件和核心模块，标注"上下文不完整" |
| Phase 1 | 无报告/日志/量化数据可采集 | 标注 `⚠️ 数据缺失`，用用户描述估算范围，继续后续分析 |
| Phase 1 | 数据来源矛盾（两份报告数字不一致） | 标注矛盾点，优先采信最新日期数据，附带说明 |
| Phase 2 | 代码无法定位到具体决策点（第三方库/闭源） | 标注 `🔒 代码不可达`，基于日志反推，区分"确定"与"推测" |
| Phase 3 | 行号因版本不同偏移 | 引用 git blame 或 commit hash 辅助定位，标注审阅时的版本 |
| Phase 3 | 时序链过长（>5 步），推导链路断裂 | 聚焦前 3 步核心链路，超出部分归入 `📎 次要链` |
| Phase 4 | 跨团队责任归属模糊 | 按"最近修改者"原则分配，标注 `⚡ 待跨团队确认` |
| Phase 5 | 修复涉及架构级变更，无法给出代码示例 | 标注 `🏗️ 需架构评审`，给出设计方向而非代码 |
| Phase 6 | 无法准确估算工时（新型问题/无历史参考） | 给出范围估算（如 2-5 MD），标注 `⏱️ 估算置信度: 低` |
| Phase 6 | 多修复存在依赖，无法独立排期 | 在路线图中标注依赖箭头（A→B），合并估算总工时 |

> **兜底原则**：任何 Phase 失败不中断全局流程。标注状态后继续，确保输出完整报告。缺失环节在报告中显式标注，让决策者判断是否追加分析。

## 分析原则

1. **数据驱动** — 每个结论必须有量化数据支撑，不使用"可能"、"大概"等模糊表述
2. **代码级定位** — 根因必须精确到文件:行号，给出具体代码片段
3. **因果链完整** — 不能只说"类型识别错了"，要说明为什么错（resolve_alias → None → _infer_from_raw_type 命中关键词）
4. **量化影响** — 每个根因的影响范围用百分比或数量表示
5. **可执行修复** — 修复建议必须包含具体代码修改，不只是概念性描述
6. **时序分析** — 区分根因、次因、第三因，明确错误的传递链
7. **成本量化** — 每个修复必须估算人天、资源和风险等级，不给出无成本预估的方案
8. **ROI 优先** — 按投入产出比排序修复建议，优先推荐低投入高回报的方案

## 适用场景

- **指标异常分析**：匹配率低、转化率低、错误率高
- **数据管道问题**：OCR → AI 提取 → 对比 → 报告的链条分析
- **类型/分类错误**：器件误分类、文档误识别
- **配置/映射问题**：Schema 不完整、别名缺失、单位转换遗漏
- **AI 输出质量问题**：LLM 输出无效值、幻觉、遗漏

---

## 最佳实践

1. **先读 README** — 理解项目架构后再分析具体问题
2. **先看报告** — 从对比报告/日志中提取量化数据
3. **再读代码** — 定位具体的代码决策点
4. **建立因果链** — 用 `→` 符号连接每一步推导
5. **量化归因** — 给每个原因分配影响比例，总和 100%
6. **给出修复代码** — 不只是"建议修复"，而是具体代码修改
