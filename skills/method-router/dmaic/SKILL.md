# DMAIC 六西格玛改进

## 前置条件

- 改进对象有可量化的指标（响应时间 / 错误率 / 匹配率 / 吞吐量等）
- 有历史数据或能采集数据建立基线
- 问题不是一次性故障（那是 OODA 的职责），而是系统性偏差

## 铁律速查

| 规则 | 内容 | 违反后果 |
|------|------|:------:|
| **R0** | Define 阶段必须量化目标。不能说"提高匹配率"，要说"从 21% 提升到 70%" | 没有量化目标，后续 Measure/Analyze/Control 全部无法落地 |
| **R1** | Measure 必须建立基线。不知道当前值就无法衡量改进效果 | 改进后无法证明有效，DMAIC 退化为 PDCA |
| **R2** | Control 必须有监控和告警。无 Control 的 DMAIC 只是 DM AI — 会退化的 | 改进成果 3 个月后悄悄滑回原点 |

---

## 五阶段总览

```
Define ──▶ Measure ──▶ Analyze ──▶ Improve ──▶ Control
 定义        测量        分析        改进        控制
  │           │           │           │           │
 目标+范围    基线+数据    根因+验证    方案+执行    监控+标准化
```

## Phase 1: Define（定义）

**目的**：明确改进什么、目标是什么、范围多大。

### 输出模板

```markdown
## Define: 项目定义

| 要素 | 内容 |
|------|------|
| **问题陈述** | {当前什么问题} |
| **目标 (SMART)** | 将 {指标} 从 {当前值} 提升到 {目标值}，在 {时间} 内完成 |
| **范围** | 涉及 {模块/流程}，不涉及 {排除项} |
| **关键指标 (CTQ)** | {1-3 个对客户/下游最关键的质量指标} |

**利益相关方**: {谁关心这个改进？}
**约束**: {预算/时间/技术限制}
```

## Phase 3: Analyze（分析）

**目的**：识别根因，用数据验证因果假设，区分相关性和因果性。

### 分析工具

| 工具 | 适用场景 | 对接 Skill |
|------|---------|-----------|
| **5W2H 深度分析** | 复杂根因，需要代码级定位 | 调用 5W2H Skill |
| **5 Whys** | 简单根因链 | 调用 5 Whys Skill |
| **MECE 穷举** | 多因素交织，先拆分维度 | 调用 MECE Skill |
| **Pareto 分析** | 识别少数关键原因 | 内置，80/20 排序 |

### 输出模板

```markdown

### 关键因子识别
```

## 错误处理

| 环节 | 失败条件 | 处理方式 |
|------|---------|---------|
| Define | 目标无法量化 | 标注"⚠️ 目标需量化"，给出可量化建议 |
| Measure | 无历史数据可采集 | 从当前开始采集 1 周数据作为基线，标注"基线基于短周期数据" |
| Analyze | 所有因子置信度低 | 标注"⚠️ 因果未验证"，建议 A/B 测试 |
| Improve | 方案实施后效果未达预期 | 回退方案，回到 Analyze 重新找根因 |
| Control | 告警系统未就绪 | 降级为人工周检，标注"⚠️ 自动化监控待建设" |

> **核心原则**：DMAIC 是数据驱动的——没有 Measure 就没有 DMAIC。如果无法测量，用 PDCA 替代。
