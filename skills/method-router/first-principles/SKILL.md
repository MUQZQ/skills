# First Principles 第一性原理

## 前置条件

- 问题涉及架构/设计/技术选型，而非故障排查
- 当前方案有"惯例"或"类比"的成分（"别人都这么用""我们一直这么干"）
- 需要突破性方案而非渐进式改进

## 铁律速查

| 规则 | 内容 | 违反后果 |
|------|------|:------:|
| **R0** | 每个基本原理必须是可证伪的事实，不是观点或偏好 | 建在观点上的方案，推翻时全部崩塌 |
| **R1** | 区分"物理约束"（不可改变）和"惯例约束"（可以打破）。只接受物理约束 | 把惯例当物理约束，创新空间被锁死 |
| **R2** | 从基本原理重建的方案必须优于现状才有意义。不能为了"第一性"而追求复杂度 | 产出更差的方案，方法论被质疑 |
| **R3** | 一次只拆解一个问题。不要试图从宇宙大爆炸开始推演 | 范围失控，分析永不结束 |

## 实战反例

| Agent 可能产生的想法 | 实际现实 | 违反规则 |
|---------------------|---------|:------:|
| "微服务是业界标准，直接用这个架构就行" | "业界标准"是类比思维。第一性原理应该问：这个系统真的需要独立部署/独立数据库/网络通信开销吗？ | R1 |
| "从硅原子的电子行为开始分析芯片选型" | 过度拆解。第一性原理拆到"当前问题范围的基本约束"即可，不是拆到宇宙起源 | R3 |
| "拆解完了，基本约束就是 CPU/内存/带宽，方案和原来一样" | 拆解到位后方案应该不同——至少选择理由变成了"因为满足约束"而非"因为别人都这么干" | R2 |

## 工作流

```
Phase 0: 定义问题 ──▶ 明确要解决什么，当前的惯例是什么
    │
    ▼
Phase 1: 拆解约束 ──▶ 区分物理约束（不可变）和惯例约束（可打破）
    │
    ▼
Phase 2: 列出基本原理 ──▶ 从物理约束推导出不可再分的真值
    │
    ▼
Phase 3: 重建方案 ──▶ 从基本原理出发，组合出解决方案
    │
    ▼
Phase 4: 对比验证 ──▶ 重建方案 vs 惯例方案 vs 物理极限
```

---

## Phase 0: 定义问题

**目的**：明确要解决的核心问题，并识别当前的"惯例假设"。

### 输出格式

```markdown
## 问题定义

**核心问题**: {一句话}
**当前方案**: {业界惯例 / 我们的惯例}
**惯例假设**: 
  - "因为 {X} 所以 {Y}" — {这是真的吗？}
  - "大家都用 {Z}" — {为什么？满足什么约束？}
```

### 惯例假设挖掘

问三个问题挖出隐藏的惯例：

| 问题 | 示例 |
|------|------|
| 如果没有任何技术限制，你会怎么做？ | 不用考虑语言/框架/团队的约束 |
| 当前方案里哪些是"必须这样"vs"一直这样"？ | 必须: 数据不能丢 / 一直: 用 Redis |
| 如果从头做一个最小可行版，最少需要什么？ | 剥离所有非核心功能 |

---

## Phase 1: 拆解约束

**目的**：将问题空间中的所有约束分为物理约束（不可变）和惯例约束（可打破）。

### 约束分类

| 类别 | 说明 | 示例 | 可变？ |
|------|------|------|:----:|
| **物理约束** | 自然规律、硬件极限、数学定理 | 光速 30 万 km/s、CAP 定理 | ❌ 不可变 |
| **业务约束** | 法规/合规/合同要求 | GDPR 数据必须在欧盟境内 | ❌ 不可变 |
| **系统约束** | 给定环境下的硬限制 | 单机内存 64GB、带宽 10Gbps | ⚠️ 可突破（加机器） |
| **惯例约束** | "大家都这么用"、"一直这么干" | 用 Redis 做缓存、微服务架构 | ✅ 可打破 |

### 约束清单模板

```markdown
## 约束拆解

| # | 约束 | 类别 | 可变？ | 如果打破会怎样？ |
|:-:|------|------|:-----:|-----------------|
| 1 | 查询延迟 < 1ms | 业务 | ❌ | 用户流失 |
| 2 | 数据不能丢 | 业务 | ❌ | 合规风险 |
| 3 | 用 Redis | 惯例 | ✅ | 可能用本地缓存更快 |
| 4 | 微服务架构 | 惯例 | ✅ | 单体可能更简单可靠 |
```

---

## Phase 2: 列出基本原理

**目的**：从不可变的约束出发，推导出不可再分的基本真值。

### 推导方法

```
约束: 查询延迟 < 1ms
  │
  └─▶ 什么能满足 < 1ms？
       ├── 内存访问: ~100ns ✅
       ├── SSD 随机读: ~100μs ❌ (>1ms 风险)
       ├── 网络 RPC: ~500μs-1ms ⚠️ (不稳定)
       └── 磁盘顺序读: ~10ms ❌

→ 基本原理 1: 热数据必须在内存中
→ 基本原理 2: 网络调用不能出现在查询热路径上
```

### 基本原理清单

```markdown
## 基本原理

从不可变约束推导出的不可再分的真值：

1. **{基本原理 1}** — 来源: {约束 X}
2. **{基本原理 2}** — 来源: {约束 Y}
3. **{基本原理 3}** — 来源: {约束 Z}
```

---

## Phase 3: 重建方案

**目的**：从基本原理出发，组合出解决方案。不考虑现有惯例。

### 重建方法

```
基本原理 1 + 基本原理 2 + 基本原理 3
    │
    ▼
什么架构/技术/方案同时满足这三个原理？
    │
    ├── 方案 A: {描述} — 满足原理 1,2,3
    ├── 方案 B: {描述} — 满足原理 1,3，原理 2 需要妥协
    └── 方案 C: {描述} — 满足原理 1,2，原理 3 不满足
    │
    ▼
选择：方案 A（最满足基本原理）
```

### 输出格式

```markdown
## 重建方案

### 方案 A: {名称} ⭐ 推荐

| 原理 | 如何满足 |
|------|---------|
| 原理 1 | {具体设计} |
| 原理 2 | {具体设计} |
| 原理 3 | {具体设计} |

**架构**: {简要架构描述}
**与惯例方案的差异**: {什么变了，为什么变}
```

---

## Phase 4: 对比验证

**目的**：验证重建方案确实优于惯例方案。

### 对比表

```markdown
## 对比验证

| 维度 | 惯例方案 | 第一性原理方案 | 物理极限 |
|------|:-------:|:-------------:|:-------:|
| 延迟 | 500μs | 100μs | 100ns (内存) |
| 复杂度 | 5 个服务 | 2 个服务 | 1 个单体 |
| 可靠性 | 99.9% | 99.99% | 100% |

**结论**: 第一性原理方案在延迟和可靠性上接近物理极限，
比惯例方案减少了 3 个服务和 80% 的网络调用。
```

### 最终输出

```markdown
## 第一性原理分析结论

**核心发现**: {一句话}

**打破的惯例**:
- {惯例 1} → 被 {原理 X} 推翻
- {惯例 2} → 被 {原理 Y} 推翻

**推荐方案**: {方案 A}
**相对于惯例方案的提升**: {量化对比}
**实施路径**: {下一步行动}
```

## 错误处理

| 环节 | 失败条件 | 处理方式 |
|------|---------|---------|
| Phase 0 | 用户的问题已经有明确的正确答案，不需要第一性原理 | 直接给答案。标注"此问题属于 Simple 域，不需要第一性原理拆解" |
| Phase 1 | 所有约束都是物理约束，找不到可打破的惯例 | 问题可能确实没有创新空间。标注结论，不强行找"惯例"来打破 |
| Phase 2 | 拆解过深，基本原理数量 > 10 | 收紧范围。只保留与核心问题直接相关的基本原理 |
| Phase 3 | 重建方案比惯例方案更差 | 诚实标注"惯例方案已经接近最优"。第一性原理的价值在于验证惯例的合理性 |

> **核心价值**：第一性原理的目标不一定是推翻惯例——有时它恰恰证明惯例是合理的。但无论结果如何，经过了"拆解→重建→对比"的决策，比未经审视的"跟风"决策好 100 倍。
