# OODA Loop 快速闭环

## 前置条件

- 问题需要快速响应（线上故障/用户投诉/编译阻断）
- 或问题处于 Complex 域，需要探测性行动
- 单轮执行时间 < 1 分钟（Chaotic 域）或 < 5 分钟（Complex 域）

## 铁律速查

| 规则 | 内容 | 违反后果 |
|------|------|:------:|
| **R0** | Chaotic 域禁止分析。第一轮 OODA 的 Observe 最多 10 秒 | 黄金救援时间被分析浪费 |
| **R1** | 每轮必须产生行动。不能连续两轮只有观察没有行动 | OODA 退化为纯观察，丧失闭环意义 |
| **R2** | Orient 是对 Observe 的解释，不是猜测。必须基于数据/日志/告警 | 错误判断导致错误行动，雪上加霜 |
| **R3** | 可用单向不可逆操作（切库/重启/降级），但必须标注 ⚠️ | 操作不可逆但未标注，他人无法接手 |

## 实战反例

| Agent 可能产生的想法 | 实际现实 | 违反规则 |
|---------------------|---------|:------:|
| "先全面收集信息再行动，确保判断准确" | 混沌场景信息永远不完整。等收集完，用户已经投诉 100 次了 | R0 |
| "观察到异常了，但不确定原因，再观察一轮" | 连续两轮只观察不行动 = 分析瘫痪。行动本身也是获取信息的手段 | R1 |
| "根据经验，这大概率是数据库连接池满了" | 经验 ≠ 当前事实。Orient 必须引用这一轮的 Observe 数据 | R2 |

## 工作流

```
   ┌─────────────────────────────────────────┐
   │                                         │
   ▼                                         │
Observe ──▶ Orient ──▶ Decide ──▶ Act        │
  观察        判断        决策      行动       │
   │                                         │
   └─────────────────── 反馈 ────────────────┘
   
   一轮 1-5 分钟，多轮循环直到问题解决或域切换
```

---

## 单轮模板

每轮输出以下四步：

```markdown
### OODA Round {N} — {耗时}

**Observe** (观察): {当前状态/数据/日志/告警}
**Orient** (判断): {对观察的解释——发生了什么？什么变了？}
**Decide** (决策): {做什么？选项 A/B/C → 选 X}
**Act** (行动): {具体操作 + 预期效果 + 回滚方式}

**结果**: {行动后的新状态}
**下一轮**: {继续 OODA / 问题解决 / 升级到 Complicated 域 → 切 5W2H}
```

## Phase 0: 初始 Observe（10 秒快照）

**目的**：在最短时间获取关键信号，不做深入分析。

### 快速检查清单

| 信号 | 检查方式 | 耗时 |
|------|---------|:--:|
| 用户影响 | 看投诉渠道/监控大屏 | 2s |
| 错误类型 | 看最近的错误日志/告警 | 3s |
| 变更关联 | 最近部署了什么？git log --oneline -5 | 3s |
| 关键指标 | CPU/内存/QPS/错误率 是否突变 | 2s |

## Phase 1-N: OODA 循环

每轮按以下顺序执行，不可跳步。

### Observe — 观察

**目的**：收集本轮决策所需的最小数据集。

- 只看与上一轮行动直接相关的数据
- 不收集"可能有用"的额外信息（那是 Complicated 域的事）
- 输出：1-3 条关键数据点

### Orient — 判断

**目的**：解释观察到的数据，形成对当前局势的理解。

- 必须引用 Observe 中的具体数据
- 明确区分"事实"和"推断"
- 如果无法判断，标注不确定性，选择一个最可能的假设

```markdown
**事实**: {Observe 中的硬数据}
**推断**: {基于事实的推理}
**置信度**: {高/中/低}
```

### Decide — 决策

**目的**：选择一个行动方案。

| 场景 | 决策策略 |
|------|---------|
| 有明确止损方案 | 立即执行，不比较 |
| 有多个方案 | 选最快能验证效果的，不是最完美的 |
| 无明确方案 | 选最小侵入性的探测行动 |
| 不可逆操作 | ⚠️ 标注，说明为什么必须现在做 |

### Act — 行动

**目的**：执行决策，观察结果。

```markdown
**操作**: {具体命令/操作}
**预期**: {执行后期望看到什么变化}
**回滚**: {如果出错如何恢复}
**实际结果**: {行动后的新状态 — 填入下一轮 Observe}
```

## 退出条件

| 条件 | 行动 |
|------|------|
| 问题解决 | 结束 OODA → 可选 Pre-mortem 复盘 |
| 问题稳定但根因不明 | 升级到 Complicated 域 → 切 5W2H 深入分析 |
| 3 轮无进展 | 升级到 Complex 域 → 切 PDCA 系统性改进 |
| 情况恶化 | 回滚上一轮行动，扩大止损范围 |

## Chaotic 域加速模式

当 Cynefin 判定为 Chaotic 时，OODA 进入加速模式：

| 步骤 | 正常模式 | 加速模式 |
|------|:-------:|:-------:|
| Observe | 1-2 分钟 | **10 秒**（只看最关键信号） |
| Orient | 基于分析 | **基于直觉+经验** |
| Decide | 比较方案 | **第一个可行方案** |
| Act | 谨慎执行 | **立即执行，先止血** |

加速模式的总原则：**行动速度 > 行动准确性**。错的行动比没行动好，因为行动产生信息。

## 错误处理

| 环节 | 失败条件 | 处理方式 |
|------|---------|---------|
| Observe | 监控/日志不可用 | 从用户描述中提取信号，标注"⚠️ 无系统数据，基于用户反馈" |
| Orient | 观察数据不足以判断 | 选最可能的假设，标注置信度低。下一轮优先收集验证数据 |
| Decide | 所有方案都有高风险 | 选风险最低的，标注 ⚠️。如果是不可逆操作，升级到用户确认 |
| Act | 行动失败（回滚） | 记录失败原因，下一轮 Orient 纳入新信息，调整判断 |
| Act | 行动无效果（3 轮无变化） | 假设可能错误，回到 Orient 重新判断。考虑升级域 |

> **核心原则**：OODA 的价值在于速度和闭环。比 5W2H 快 10 倍，比 PDCA 轻 10 倍。用对场景（Chaotic/Complex），它是救命工具；用错场景（Simple），它是过度设计。

## 输出格式建议

- 每轮输出用折叠块，完整保留但允许跳过
- 初始 Observe 用表格（4 行 × 检查项/方式/耗时）
- 每轮结尾标注"问题状态：{解决中/已解决/升级/恶化}"
- 链式输出后接 SCQA：`💡 问题解决后建议用 SCQA 格式化复盘报告`
