# Pre-mortem 事前验尸

## 前置条件

- 有一个具体的变更/决策待执行（上线、重构、迁移、新功能发布）
- 变更的范围和内容已知（或用户能描述）
- 不需要已发生的故障数据（这是预防性分析，不是事后复盘）

## 铁律速查

| 规则 | 内容 | 违反后果 |
|------|------|:------:|
| **R0** | 必须假想"已经失败"的视角，而非"会不会失败"的视角 | 后者触发心理防御，低估风险 |
| **R1** | 每个风险必须关联具体代码/配置/流程位置 | 抽象风险（"性能下降"）无法落地修复 |
| **R2** | 必须区分"可能发生"和"会发生"，只输出后者 | 列出 50 个风险 = 决策者全忽略，聚焦 Top 5-7 |
| **R3** | 不改变用户的变更计划，只做风险标注。阻止是用户的事 | 越权决策，Agent 不应替 PM/Tech Lead 做 go/no-go |

## 实战反例

| Agent 可能产生的想法 | 实际现实 | 违反规则 |
|---------------------|---------|:------:|
| "列出所有可能的风险，越全越好" | 30 个风险的清单让决策者麻木。5 个高概率高影响的风险比 30 个全量清单有用 10 倍 | R2 |
| "没有代码可查，就按经验列常见风险吧" | 通用风险（SQL注入/内存泄漏）是噪音。真正的风险藏在这次变更的具体改动里 | R1 |
| "综合来看风险太高，建议取消上线" | 风险分析 ≠ 决策。Agent 的职责是让风险可见，不是替人做 go/no-go | R3 |
| "假想失败了，但我更想说'应该不会失败'来安抚用户" | Pre-mortem 的核心价值恰恰是打破"应该不会"的乐观偏差 | R0 |

## 工作流

```
Phase 0: 定义变更范围 ──▶ 明确"什么要变、变多大、影响谁"
    │
    ▼
Phase 1: 假想失败场景 ──▶ "上线后出事了，怎么回事？" — 列出所有可能原因
    │
    ▼
Phase 2: 风险量化 ──▶ 概率 × 影响 × 可检测性 = RPN
    │
    ▼
Phase 3: 缓解措施 ──▶ 每个风险对应的预防/检测/回滚方案
    │
    ▼
Phase 4: 输出风险报告 ──▶ Top 5-7 风险 + Go/No-Go 条件
```

## Phase 0: 定义变更范围

**目的**：用 5 句话描述变更，确保分析聚焦在正确的范围。

### 输出模板

```markdown
## 变更概要

| 维度 | 内容 |
|------|------|
| **变更内容** | {一句话描述} |
| **影响模块** | {文件/服务/数据库列表} |
| **变更规模** | {+N 行 / -M 行 / 表结构变更 / 配置变更} |
| **回滚难度** | 🟢 简单 / 🟡 中等 / 🔴 困难 |
| **关键假设** | {这个变更建立在什么假设上？} |
```

---

## Phase 1: 假想失败场景

**目的**：用"已经失败"的视角，穷举可能的失败原因。

### 场景设定

> ⚡ 现在是 {上线后 48 小时 / 发布后 1 周}。变更已经执行，**并且失败了**。
> 用户正在投诉、监控在报警、你在排查问题。
> **最可能的失败原因是什么？**

### 视角切换提示

| 传统视角（风险检查） | Pre-mortem 视角（已失败） |
|---------------------|-------------------------|
| "这个改动会不会导致性能下降？" | "性能已经降了 80%，是什么改动导致的？" |
| "有没有并发安全问题？" | "数据已经出错了，哪个并发条件没覆盖？" |
| "兼容性会不会有问题？" | "老版本客户端已经大面积报错了，哪个接口不兼容？" |

### 失败原因穷举

按以下分类逐一审查：

| 分类 | 检查点 |
|------|--------|
| **代码逻辑** | 边界条件、空值处理、异常路径、类型转换 |
| **数据/状态** | 迁移脚本、数据库锁、数据一致性、回滚数据 |
| **依赖/环境** | 第三方 API、配置变更、环境差异、DNS/网络 |
| **并发/时序** | 竞态条件、分布式事务、定时任务冲突 |
| **兼容性** | API 版本、客户端版本、Schema 变更 |
| **人因** | 操作顺序错误、文档过时、沟通遗漏 |
| **容量/性能** | 内存泄漏、连接池耗尽、慢查询、雪崩 |

## Phase 2: 风险量化

**目的**：给每个风险打分，聚焦高 RPN 项。

### RPN 计算

```
RPN = 概率 × 影响 × 可检测性

概率 (1-5):    1=几乎不可能  3=可能      5=几乎确定
影响 (1-5):    1=忽略不计    3=中度影响  5=灾难性
可检测性 (1-5):  1=立即发现    3=几小时内  5=数天后才发现  ← 越高越危险
```

### 输出格式

```markdown
## 风险量化

| # | 失败场景 | 概率 | 影响 | 可检测 | RPN | 分类 |
|:-:|---------|:---:|:---:|:-----:|:---:|------|
| 1 | {场景 1} | 4 | 5 | 4 | **80** | 并发 |
| 2 | {场景 2} | 3 | 4 | 3 | **36** | 数据 |
| 3 | {场景 3} | 2 | 4 | 2 | **16** | 兼容性 |
```

### RPN 阈值

| RPN | 等级 | 行动 |
|:---:|:----:|------|
| ≥ 60 | 🔴 高危 | 必须在上线前有缓解措施，否则建议 No-Go |
| 30-59 | 🟡 中危 | 应有缓解措施，可接受残留风险 |
| < 30 | 🟢 低危 | 记录下来，不阻塞上线 |

---

## Phase 3: 缓解措施

**目的**：为高 RPN 风险设计预防、检测和回滚方案。

### 输出格式

```markdown
## 缓解措施

### 🔴 风险 1: {场景名称} — RPN {score}

**预防**: {上线前的代码修改/测试补充}
**检测**: {上线后的监控/告警/日志}
**回滚**: {如果发生，如何快速恢复}

**文件**: `{path}:{line}`
**负责**: {建议负责人}
```

### 缓解层级

```
            预防（上线前）        检测（上线后）         回滚（出事后）
               │                    │                    │
        ┌──────┴──────┐     ┌──────┴──────┐     ┌──────┴──────┐
        │ 代码审查      │     │ 监控告警     │     │ 一键回滚     │
        │ 单元测试      │     │ 日志分析     │     │ 灰度切换     │
        │ 集成测试      │     │ 用户反馈     │     │ 数据恢复     │
        └──────────────┘     └──────────────┘     └──────────────┘
```

## Phase 4: 输出风险报告

**目的**：汇总为决策者可用的 Go/No-Go 建议。

### 完整模板

```markdown
# Pre-mortem 风险分析报告：{变更名称}

> 报告类型：风险审查 | 日期：{YYYY-MM-DD} | 方法：Pre-mortem

## 变更概要
{Phase 0 表格}

## 假想失败
⚡ 假设变更已失败，以下是倒推出的最可能原因：

## 风险量化
{Phase 2 表格}

## 缓解措施
{Phase 3 详情}

## Go/No-Go 建议

| 条件 | 状态 |
|------|:----:|
| 无 🔴 高危 RPN ≥ 60 | {✅/❌} |
| 所有 🔴 风险有缓解措施 | {✅/❌} |
| 回滚方案已测试通过 | {✅/❌} |
| 监控告警已配置 | {✅/❌} |

**建议**: {Go / Conditional Go / No-Go} — {一句话理由}

## 残留风险
即使执行缓解措施，仍存在的无法消除的风险：

| 风险 | 接受理由 |
|------|---------|
| {残留风险} | {为什么接受} |
```

## 错误处理

| 环节 | 失败条件 | 处理方式 |
|------|---------|---------|
| Phase 0 | 用户无法描述变更范围 | 从 git diff / 最近提交中自行推断，标注"⚠️ 基于代码推断的范围" |
| Phase 1 | 变更太小（< 20 行），找不到 ≥ 3 个风险 | 标注"变更规模小，未发现高概率失败场景"，不强行编造 |
| Phase 2 | 无历史数据参考，概率/影响难以估计 | 用范围值标注（如概率 2-4），降低 RPN 置信度 |
| Phase 4 | 用户不回应 Go/No-Go 的确认 | 只输出分析，不代替决策。标注"⚠️ 待决策者确认" |

> **核心原则**：Pre-mortem 是"打破乐观偏差"的工具，不是"阻止上线"的工具。即使输出 3 个 🔴 风险，也不等于说 No-Go。让决策者看到完整的风险图景——这才是价值。

---

## 输出格式建议

- Phase 0 用表格，Phase 1 用场景化叙述（"假设已失败，为什么？"）
- RPN 用颜色区分（🔴🟡🟢）
- Go/No-Go 条件用 checkbox（✅/❌）
- 报告尾部衔接到 SCQA：`💡 建议用 SCQA 格式化此报告`
