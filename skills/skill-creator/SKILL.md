# Skill 创建器

一个用于创建新 skill 并迭代优化的 skill。

从宏观上看，创建 skill 的过程大致如下：

- 确定你希望这个 skill 做什么，以及大致怎么做
- 撰写 skill 初稿
- 创建几个测试 prompt，并用带有该 skill 访问权限的 Claude 运行它们
- 帮助用户定性和定量地评估结果
  - 在后台运行的同时，如果没有现成的定量 eval 就起草一些（如果有的话可以沿用或按需修改）。然后向用户解释这些 eval（如果已存在则解释现有的）
  - 使用 `eval-viewer/generate_review.py` 脚本向用户展示结果，同时也让他们看到量化指标
- 根据用户对结果的评估反馈（以及在量化基准中暴露出的明显缺陷）重写 skill
- 重复以上步骤直到满意
- 扩展测试集并更大规模地重试

使用此 skill 时，你的任务是判断用户处于流程的哪个阶段，然后介入并帮助他们推进这些阶段。例如，用户可能说"我想做一个做 X 的 skill"。你可以帮他们细化需求、写初稿、写测试用例、确定评估方式、运行所有 prompt，然后反复迭代。

另一方面，用户可能已经有一个 skill 初稿。这种情况下你可以直接进入 eval/迭代循环。

当然，你应该保持灵活——如果用户说"不需要跑一堆评估，陪我随便弄弄就行"，你也可以这样做。

然后，当 skill 完成后（顺序可以灵活），你还可以运行 skill 描述优化器——我们有独立的脚本专门做这个——来优化 skill 的触发效果。

OK 吗？OK。

## 与用户沟通

Skill 创建器可能会被编程背景差异很大的用户使用。你可能还没听说（这确实是很新的事），现在有个趋势是：Claude 的能力正在激励水管工打开终端，父母和祖父母去搜索"如何安装 npm"。另一方面，大多数用户可能比较熟悉电脑。

所以请关注上下文线索，理解如何措辞沟通！默认情况下，给你一些参考：

- "评估（evaluation）"和"基准（benchmark）"在边界线，可以用
- "JSON"和"断言（assertion）"需要看到用户确实了解这些概念的明显信号，否则应加以解释

如果你不确定，简单解释一下术语是 OK 的，不用担心。

## 创建 Skill

### 捕获意图

首先理解用户的意图。当前对话中可能已经包含了用户想要捕获的工作流（例如他们说"把这个转成 skill"）。如果是这样，先从对话历史中提取答案——使用的工具、步骤顺序、用户做的修正、观察到的输入/输出格式。用户可能需要补充一些空白，应在进入下一步前确认。

1. 这个 skill 应该让 Claude 能够做什么？
2. 什么时候应该触发这个 skill？（用户什么说法/上下文）
3. 期望的输出格式是什么？
4. 是否应该设置测试用例来验证 skill 是否有效？具有客观可验证输出的 skill（文件转换、数据提取、代码生成、固定工作流步骤）适合使用测试用例。主观输出的 skill（写作风格、艺术）通常不需要。根据 skill 类型给出适当的默认建议，但让用户决定。

### 访谈与研究

主动询问边缘情况、输入/输出格式、示例文件、成功标准和依赖项等问题。在这些方面搞清楚了再写测试 prompt。

检查可用的 MCP——如果对研究有用（搜索文档、查找类似 skill、查找最佳实践），可以通过子 Agent 并行研究（如果有），否则内联进行。做好功课以减少用户的负担。

### 撰写 SKILL.md

根据用户访谈，填写以下组件：

- **name**：Skill 标识符
- **description**：何时触发、做什么。这是主要的触发机制——同时包含 skill 做什么 AND 何时使用的具体上下文。所有"何时使用"的信息放在这里，不要放在正文中。注意：目前 Claude 倾向于"欠触发" skill——应该使用但不使用。为了对抗这个问题，请让 skill 描述稍微"激进"一点。例如，不要写"如何构建一个简单的快速仪表板来展示内部 Anthropic 数据。"，你可以写"如何构建一个简单的快速仪表板来展示内部 Anthropic 数据。当用户提到仪表板、数据可视化、内部指标，或想要展示任何类型的公司数据时，务必使用此 skill，即使他们没有明确说'仪表板'。"
- **compatibility**：所需工具、依赖项（可选，很少需要）
- **skill 的其余部分 :)**

### Skill 撰写指南

#### Skill 的解剖结构

```
skill-name/
├── SKILL.md（必需）
│   ├── YAML frontmatter（name、description 必需）
│   └── Markdown 指令
└── 打包资源（可选）
    ├── scripts/    - 用于确定性/重复性任务的可执行代码
    ├── references/ - 按需加载到上下文的文档
    └── assets/     - 输出中使用的文件（模板、图标、字体）
```

#### 渐进式披露

Skill 使用三级加载系统：
1. **元数据**（name + description）- 始终在上下文中（约100词）
2. **SKILL.md 正文** - skill 触发时在上下文中（理想情况 <500 行）
3. **打包资源** - 按需加载（无限制，脚本可以不加载就执行）

这些字数统计是近似值，你可以根据需要适度超出。

**关键模式：**
- 将 SKILL.md 保持在 500 行以内；如果接近此限制，增加一层层级结构，并给出清晰的指示让模型知道下一步该去读什么
- 从 SKILL.md 清楚地引用文件，并说明何时去读它们
- 对于大型引用文件（>300 行），包含目录

**领域组织**：当 skill 支持多个领域/框架时，按变体组织：
```
cloud-deploy/
├── SKILL.md（工作流 + 选择）
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```
Claude 只读取相关的引用文件。

#### 出乎意料原则

不言自明，skill 不得包含恶意软件、漏洞利用代码或任何可能危害系统安全的内容。skill 的内容不应在其描述的意图上让用户感到意外。不要配合创建误导性 skill 或旨在促进未授权访问、数据外泄或其他恶意活动的 skill。不过像"扮演 XYZ 角色"之类的事是 OK 的。

#### 撰写模式

在指令中使用祈使句式。

**定义输出格式** - 可以这样：
```markdown
## 报告结构
始终使用以下精确模板：
# [标题]
## 执行摘要
## 重要发现
## 建议
```

**示例模式** - 包含示例很有用。可以这样格式化（但如果示例中有"输入"和"输出"，可能要做些变化）：
```markdown
## 提交信息格式
**示例 1：**
输入：使用 JWT 令牌添加了用户认证
输出：feat(auth): 实现基于 JWT 的认证
```

#### 工程化工作流型 Skill 模版 (Engineered Workflow Skill Template)

> **适用判断**：本模版适用于满足 ≥3 项以下条件的 skill。若不满足，退回到通用结构（name + description + 操作步骤 + 错误处理）。
> - 包含 ≥5 个有严格顺序依赖的步骤
> - 使用子 Agent 并发或批次执行
> - 有 ≥5 条不可违反的核心规则
> - 输出可被自动化校验（覆盖率、完整率等）
> - 单次执行耗时较长或经常因错误中断

**文件结构（所有项均可选）：**

```
skill-name/
├── SKILL.md（核心工作流指令，必需）
└── references/（按需创建）
    ├── sample_output.yaml     # 期望输出示例
    ├── templates/             # 子 Agent prompt 模板
    ├── faq.md                 # 常见问题和解决方案
    └── version_history.md     # 版本变更记录
```

**SKILL.md 内部结构：**

| 层级 | 章节 | 使用条件 |
|------|------|---------|
| **核心** | YAML Frontmatter | name + description **必填**；license、keywords、sticky_session 等均可选 |
| **核心** | 前置条件 / 触发确认 | 明确输入要求、依赖项检查、缺少信息时的追问策略 |
| **核心** | 工作流总览 / 场景路由 | 步骤顺序或场景→分支映射表 |
| **核心** | 操作步骤 | 每步含操作指令 + 可选完成标准，长步骤用 checkbox，短步骤标序号即可 |
| **核心** | 错误处理 | 表格或列表，包含失败条件 + 重试/降级策略 |
| **核心** | 铁律速查 (Iron Rules) | 不可妥协的核心规则，格式：`\| 规则 \| 内容 \| 违反后果 \|`。即使只有 2-3 条也比没有好 |
| **核心** | 实战反例 (Anti-Patterns) | 多 Agent、多文件或长链路 skill 的核心防护——预判 Agent 容易产生的合理化借口 vs 实际后果。通用反例模式：路径漂移、并发覆盖、跳过校验、相近误匹配、字段省略 |
| **增强** | 工具 / MCP API 清单 | 有专用 MCP 工具集时添加，列出工具名及参数 |
| **增强** | 意图识别路由表 | 同一 skill 覆盖多种用户意图时使用（`用户输入 → 缺失信息 → 路由`） |
| **增强** | 执行确认 / 授权闸门 | 高风险操作前暂停并请求用户确认（如"即将写入 N 条规则，确认？"），约 50% 的 skill 中使用 |
| **增强** | 参考文档索引 | 有 references/ 目录时添加，列出每个文件及用途 |
| **增强** | 输出格式建议 / 展示模板 | 向用户展示结果时，定义推荐的格式化方式 |
| **增强** | 输出质量指标 | 输出可量化时使用，格式：`\| 指标 \| 目标值 \| 检查方法 \|` |

**关键模式详解：**

1. **意图识别路由** — 最常见的交互型 skill 模式，帮助模型在多种用户请求间正确分流：
   ```markdown
   | 用户输入 | 缺失信息 | 操作 |
   |---------|---------|------|
   | "导出 BOM" | 未指定格式 | 追问：需要 Excel 还是 CSV？ |
   | "检查 DRC" | 未指定规则集 | 使用默认规则集 |
   ```

2. **步骤化工作流** — 长步骤用四段式，短步骤简化即可：
   - 长步骤模板：`**目的**→**操作**→**完成标准(checkbox)**→**→ 下一步**`
   - 短步骤写法：`1. 读取文件 → 2. 解析内容 → 3. 输出结果`

3. **铁律机制**：用 R0, R1, R2... 编号核心规则，三列表格同时展示"违反后果"，让模型理解规则重要性。正文中通过 `**R7 铁律详解**` 交叉引用。

4. **铁律 + 反例，双面防护** — 铁律定义"必须做什么"，反例解释"为什么 Agent 可能会违反它"。反例表利用对 LLM Agent 行为模式的了解预先设防——以下模式对多 Agent/多文件/长链路 skill 通用：
   - 路径漂移（相对路径在子 Agent 中解析到意外位置）
   - 并发文件覆盖（多个 Agent 写同名文件互相覆盖）
   - 跳过校验（Agent 认为"差不多"就跳过 validate 步骤）
   - 相近章节/名称误匹配（含相同关键词的不同对象被混淆）
   - 格式字段省略（source、table_name 等元数据字段被遗漏）
   反例表格式：`\| Agent可能产生的想法 \| 实际现实 \| 违反规则 \| 实际后果 \|`

5. **前置条件 / 触发确认** — 审查型和执行型 skill 的通用模式，明确回答"调用前必须满足什么条件"：
   ```markdown
   ## 前置条件
   - 原理图已打开且处于焦点状态
   - 目标元件已选中（或通过 designator 指定）
   - MCP 连接正常（pre_check 通过）
   ```

6. **执行确认 / 授权闸门** — 高风险操作前暂停流程，请求用户确认：
   ```markdown
   > ⚠️ 即将执行以下操作：
   > - 写入 42 条间距规则到 PCB
   > - 覆盖现有的 `default` 规则集
   > 输入 yes 确认，或 no 取消。
   ```
   适用于写入 PCB、批量修改、删除操作等不可逆场景。

7. **输出格式建议** — 面向用户展示结果时的通用模式：
   ```markdown
   ## 输出建议
   - 以表格展示元件清单（designator | value | footprint | 状态）
   - 以列表展示每个检查项的通过/失败/警告
   - 附带快捷操作建议（如"点击下方按钮修复"）
   ```

8. **模板渲染机制** — 子 Agent 的 prompt 放在 `references/templates/` 下，SKILL.md 中明确要求调用前读取并渲染模板变量，避免硬编码。

9. **量化指标收尾** — 仅用于输出可自动化验证的 skill，定义可量化的成功标准（参数数量、覆盖率、失败率等）。

**完整骨架示例（核心骨架）：**

```markdown
---
```

### 撰写风格

尽量向模型解释为什么事情很重要，而非使用沉重的强制执行式 MUST。运用心智理论，尽量让 skill 具有通用性，不要过度局限于特定示例。先写初稿，然后用全新的眼光重新审视并改进。

### 测试用例

写完 skill 初稿后，提出 2-3 个真实的测试 prompt——真正用户会说出来的那种。与用户分享："这是我想尝试的几个测试用例。这些看起来对吗，还是想增加更多？"然后运行它们。

将测试用例保存到 `evals/evals.json`。此时不要写断言——只写 prompt。你将在下一步运行过程中起草断言。

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "用户的任务 prompt",
      "expected_output": "期望结果的描述",
      "files": []
    }
  ]
}
```

参阅 `references/schemas.md` 获取完整 schema（包括 `assertions` 字段，稍后添加）。

## 运行和评估测试用例

本节是一个连续序列——不要中途停下。不要使用 `/skill-test` 或其他任何测试 skill。

将结果放在 `<skill-name>-workspace/` 中，与 skill 目录同级。在工作区内，按迭代组织结果（`iteration-1/`、`iteration-2/` 等），在其中每个测试用例对应一个目录（`eval-0/`、`eval-1/` 等）。不要一次性创建所有这些——随用随建。

### 第 1 步：在同一轮中启动所有运行（带 skill 的 AND 基线）

对于每个测试用例，在同一轮中启动两个子 Agent——一个带有 skill，一个不带。这很重要：不要先启动带 skill 的运行，然后再回来做基线。一次性全部启动，这样所有运行大致同时完成。

**带 skill 的运行：**

```
执行此任务：
- Skill 路径：<path-to-skill>
- 任务：<eval prompt>
- 输入文件：<eval files，如果没有则为 "none">
- 保存输出到：<workspace>/iteration-<N>/eval-<ID>/with_skill/outputs/
- 需要保存的输出：<用户关注的内容——例如，"the .docx file"、"the final CSV">
```

**基线运行**（相同 prompt，但基线取决于上下文）：
- **创建新 skill**：不带任何 skill。相同 prompt，不指定 skill 路径，保存到 `without_skill/outputs/`。
- **改进现有 skill**：使用旧版本。编辑前，先快照 skill（`cp -r <skill-path> <workspace>/skill-snapshot/`），然后将基线子 Agent 指向快照。保存到 `old_skill/outputs/`。

为每个测试用例写一个 `eval_metadata.json`（断言可以先为空）。给每个 eval 一个描述性名称，表示它在测试什么——不要只叫"eval-0"。目录也使用这个名字。如果此迭代使用了新的或修改过的 eval prompt，为每个新 eval 目录创建这些文件——不要假设备份从前面的迭代带过来。

```json
{
  "eval_id": 0,
  "eval_name": "描述性名称-在这里",
  "prompt": "用户的任务 prompt",
  "assertions": []
}
```

### 第 2 步：运行进行中时起草断言

不要干等运行完成——可以利用这段时间高效地工作。为每个测试用例起草量化断言，并向用户解释。如果断言已经存在于 `evals/evals.json` 中，审查它们并解释它们检查的内容。

好的断言是客观可验证的，且具有描述性名称——它们应该在基准查看器中清晰地阅读，让人一瞥就立即理解每个断言检查什么。主观 skill（写作风格、设计质量）更适合定性评估——不要把断言强加在需要人工判断的事情上。

更新 `eval_metadata.json` 文件和 `evals/evals.json`，将起草好的断言加入。也向用户解释他们将在查看器中看到什么——定性输出和量化基准。

### 第 3 步：运行完成时捕获计时数据

当每个子 Agent 任务完成时，你会收到包含 `total_tokens` 和 `duration_ms` 的通知。立即将这些数据保存到运行目录的 `timing.json`：

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

这是捕获这些数据的唯一机会——它通过任务通知传来，不会在其他地方持久化。收到每个通知就处理，而不是尝试批量处理。

### 第 4 步：评分、聚合，启动查看器

所有运行完成后：

1. **对每次运行评分**——启动一个评分子 Agent（或内联评分），读取 `agents/grader.md` 并根据输出评估每个断言。将结果保存到每个运行目录的 `grading.json` 中。grading.json 的 expectations 数组必须使用 `text`、`passed` 和 `evidence` 字段（不要用 `name`/`met`/`details` 或其他变体）——查看器依赖这些确切的字段名。对于可以通过编程检查的断言，编写并运行脚本而不是肉眼判断——脚本更快、更可靠，且可以跨迭代复用。

2. **聚合为基准**——从 skill-creator 目录运行聚合脚本：
   ```bash
   python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
   ```
   这会生成 `benchmark.json` 和 `benchmark.md`，包含每种配置的通过率、时间和 token，附带均值 ± 标准差和增量。如果手动生成 benchmark.json，参阅 `references/schemas.md` 了解查看器期望的确切 schema。
将每个 with_skill 版本放在其基线对应版本之前。

3. **做一次分析师扫描**——读取基准数据，发现聚合统计可能隐藏的模式。参阅 `agents/analyzer.md`（"分析基准结果"部分）了解需要关注的内容——像无论 skill 如何都始终通过的断言（无区分力）、高方差 eval（可能不稳定）、时间和 token 的权衡等。

4. **启动查看器**，包含定性输出和量化数据：
   ```bash
   nohup python <skill-creator-path>/eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json \
     > /dev/null 2>&1 &
   VIEWER_PID=$!
   ```
   对于第 2 轮及以上，还需传入 `--previous-workspace <workspace>/iteration-<N-1>`。

   **Cowork / 无头环境：** 如果 `webbrowser.open()` 不可用或环境没有显示器，使用 `--static <output_path>` 写入独立 HTML 文件而非启动服务器。当用户点击"提交所有审查"时，反馈将以 `feedback.json` 文件形式下载。下载后，将 `feedback.json` 复制到工作区目录，供下一轮迭代使用。

注意：请使用 generate_review.py 来创建查看器；无需写自定义 HTML。

5. **告诉用户**类似："我已在浏览器中打开结果。有两个标签页——'Outputs' 让你逐个点击测试用例并留下反馈，'Benchmark' 显示量化对比。完成后回到这里告诉我。"

### 用户在查看器中看到的内容

"Outputs"标签页一次显示一个测试用例：
- **Prompt**：给出的任务
- **Output**：skill 产生的文件，尽量内联渲染
- **Previous Output**（第 2 轮及以上）：折叠显示上次迭代的输出
- **Formal Grades**（如果运行了评分）：折叠显示断言通过/失败
- **Feedback**：自动保存的文本框
- **Previous Feedback**（第 2 轮及以上）：他们上次的评论，显示在文本框下方

"Benchmark"标签页显示统计摘要：每种配置的通过率、时间和 token 用量，包含逐项 eval 分解和分析师观察。

导航通过上一个/下一个按钮或箭头键。完成后，他们点击"提交所有审查"，将所有反馈保存到 `feedback.json`。

### 第 5 步：读取反馈

当用户告诉你他们完成时，读取 `feedback.json`：

```json
{
  "reviews": [
    {"run_id": "eval-0-with_skill", "feedback": "图表缺少坐标轴标签", "timestamp": "..."},
    {"run_id": "eval-1-with_skill", "feedback": "", "timestamp": "..."},
    {"run_id": "eval-2-with_skill", "feedback": "完美，非常喜欢", "timestamp": "..."}
  ],
  "status": "complete"
}
```

空反馈表示用户认为没问题。将改进重点放在用户有具体投诉的测试用例上。

完成后终止查看器服务器：

```bash
kill $VIEWER_PID 2>/dev/null
```

## 改进 Skill

这是循环的核心。你已经运行了测试用例，用户已经审查了结果，现在你需要根据他们的反馈改进 skill。

### 如何思考改进

1. **从反馈中泛化。** 这里的关键大事是，我们正在努力创建能够在海量不同 prompt（可能真的数百万甚至更多）中被重复使用的 skill。在这里你和用户仅在少数几个例子上反复迭代，因为这有助于加快进度。用户对这些例子的输入输出了如指掌，能快速评估新输出。但如果你们共同开发的 skill 只对这些例子有效，那就毫无用处。不要做琐碎过拟合的改动，也不要做过分严格的 MUST 约束——如果有些顽固问题，试试换用不同的比喻，或推荐不同的工作模式。尝试的代价相对低廉，也许你会找到很棒的方法。

2. **保持 prompt 精简。** 删除那些没有实际价值的东西。一定要阅读转录（transcript），而不仅仅是最终输出——如果看起来 skill 让模型浪费时间做无效的事情，可以尝试删除 skill 中导致这种情况的部分，看看效果。

3. **解释为什么。** 努力解释你所要求的一切背后的**为什么**。今天的 LLM 是*聪明的*。它们有很好的心智理论，当有好的框架时，可以超越机械指令去真正实现目标。即使用户的反馈简洁或沮丧，也要尝试真正理解任务、理解用户为什么写下他们所写的以及他们到底写了什么，然后将这种理解传达给指令。如果你发现自己写 ALL CAPS 的 ALWAYS 或 NEVER，或者使用超级死板的结构，那是一个黄色警告——如果可能的话，重新表达并解释推理，让模型理解为什么要求的事情很重要。这是一种更人性化、更有力量、更有效的方法。

4. **寻找跨测试用例的重复工作。** 阅读测试运行的转录，注意是否所有子 Agent 都独立编写了类似的辅助脚本或采取了相同的多步骤方法。如果所有 3 个测试用例都导致子 Agent 写了一个 `create_docx.py` 或 `build_chart.py`，那是一个强烈的信号——skill 应该打包那个脚本。写一次，放在 `scripts/` 中，并告诉 skill 使用它。这节省了每次调用从头造轮子的时间。

这个任务相当重要（我们正在努力创造每年数十亿的经济价值！），你的思考时间不是瓶颈；慢慢来，仔细斟酌。我建议先写修订稿，然后用全新的眼光再看并改进。真的全力以赴地去理解用户的想法和他们想要什么、需要什么。

### 迭代循环

改进 skill 之后：

1. 将你的改进应用到 skill
2. 在新的 `iteration-<N+1>/` 目录中重新运行所有测试用例，包括基线运行。如果是创建新 skill，基线始终是 `without_skill`（无 skill）——这在各迭代间保持不变。如果是改进现有 skill，自行判断什么作为基线合适：用户带来的原始版本，或上一轮迭代版本。
3. 以指向上一轮迭代的 `--previous-workspace` 启动审查器
4. 等待用户审查并告诉你他们完成
5. 读取新反馈，再次改进，重复

持续直到：
- 用户说他们满意
- 反馈全部为空（一切看起来都好）
- 你不再取得有意义的进展

## 高级：盲对比

对于需要更严格比较两个 skill 版本的情况（例如用户问"新版本真的更好吗？"），有一个盲对比系统。阅读 `agents/comparator.md` 和 `agents/analyzer.md` 了解详情。基本思路是：将两个输出交给一个独立 Agent，不告诉它哪个是哪个，让它判断质量。然后分析为什么获胜者赢了。

这是可选的，需要子 Agent，大多数用户不需要。人工审查循环通常就足够了。

## 描述优化

SKILL.md frontmatter 中的 description 字段是决定 Claude 是否调用 skill 的主要机制。创建或改进 skill 后，提供优化描述以提高触发准确率。

### 第 1 步：生成触发 eval 查询

创建 20 个 eval 查询——应触发和不应触发的混合。保存为 JSON：

```json
[
  {"query": "用户的 prompt", "should_trigger": true},
  {"query": "另一个 prompt", "should_trigger": false}
]
```

查询必须真实，是 Claude Code 或 Claude.ai 用户真正会输入的内容。不是抽象的请求，而是具体、有细节的请求。例如，文件路径、关于用户工作或情况的个人信息、列名和值、公司名、URL。一些背景故事。有些可能是小写或包含缩写、错别字或口语。使用不同长度的混合，专注于边缘情况而非让它们清晰明确（用户会有机会签收的）。

不好的示例：`"Format this data"`、`"Extract text from PDF"`、`"Create a chart"`

好的示例：`"ok so my boss just sent me this xlsx file (its in my downloads, called something like 'Q4 sales final FINAL v2.xlsx') and she wants me to add a column that shows the profit margin as a percentage. The revenue is in column C and costs are in column D i think"`

对于**应触发**查询（8-10 个），要考虑覆盖度。相同意图的不同措辞——一些正式，一些随意。包含用户不明确命名 skill 或文件类型但明显需要它的场景。加入一些不常见的用例，以及该 skill 与另一个竞争但应该胜出的情况。

对于**不应触发**查询（8-10 个），最有价值的是那些"差一点就触发"的——与 skill 共享关键词或概念但实际需要别的东西的查询。考虑相邻领域、模糊措辞（naive 关键词匹配会触发但不该触发）、以及查询触及 skill 做的事但在另一个工具更合适的上下文中的情况。

关键要避免的是：不要让不应触发的查询明显不相关。对 PDF skill 用"Write a fibonacci function"做负面测试太容易了——它什么都测试不了。负面用例应该真正 tricky。

### 第 2 步：与用户审查

使用 HTML 模板向用户展示 eval 集合：

1. 从 `assets/eval_review.html` 读取模板
2. 替换占位符：
   - `__EVAL_DATA_PLACEHOLDER__` → eval 项的 JSON 数组（不要加引号——它是 JS 变量赋值）
   - `__SKILL_NAME_PLACEHOLDER__` → skill 的名称
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → skill 的当前描述
3. 写入临时文件（例如 `/tmp/eval_review_<skill-name>.html`）并打开：`open /tmp/eval_review_<skill-name>.html`
4. 用户可以编辑查询、切换 should-trigger、添加/删除条目，然后点击"Export Eval Set"
5. 文件下载到 `~/Downloads/eval_set.json`——检查 Downloads 文件夹中的最新版本，以防有多个（例如 `eval_set (1).json`）

这一步很重要——糟糕的 eval 查询会导致糟糕的描述。

### 第 3 步：运行优化循环

告诉用户："这需要一些时间——我会在后台运行优化循环并定期检查。"

将 eval 集合保存到工作区，然后在后台运行：

```bash
python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --model <model-id-powering-this-session> \
  --max-iterations 5 \
  --verbose
```

使用系统 prompt 中的模型 ID（当前会话所用的模型），这样触发测试与用户实际体验匹配。

运行期间，定期读取输出来向用户更新当前迭代和分数情况。

这会自动处理完整的优化循环。它将 eval 集合分割为 60% 训练集和 40% 留出测试集，评估当前描述（每个查询运行 3 次以获得可靠的触发率），然后调用 Claude 根据失败情况提出改进。它在训练集和测试集上重新评估每个新描述，最多迭代 5 次。完成后，在浏览器中打开 HTML 报告显示每轮迭代的结果，并返回包含 `best_description` 的 JSON——通过测试集分数而非训练集分数选择，避免过拟合。

### Skill 触发机制原理

理解触发机制有助于设计更好的 eval 查询。Skill 以其 name + description 出现在 Claude 的 `available_skills` 列表中，Claude 根据 description 决定是否查阅 skill。重要的是，Claude 只对自己无法轻松处理的任务查阅 skill——像"read this PDF"这样的简单一步式查询即使 description 完美匹配也可能不触发 skill，因为 Claude 可以直接用基础工具处理。复杂的、多步骤的或专业的查询在 description 匹配时可靠地触发 skill。

这意味着你的 eval 查询应该足够复杂，Claude 实际上能从查阅 skill 中受益。像"read file X"这样的简单查询是糟糕的测试用例——无论描述质量如何，它们都不会触发 skill。

### 第 4 步：应用结果

从 JSON 输出中获取 `best_description` 并更新 skill 的 SKILL.md frontmatter。向用户展示前后对比并报告分数。

### 打包和交付（仅在 `present_files` 工具可用时）

检查你是否有权使用 `present_files` 工具。如果没有，跳过此步骤。如果有，打包 skill 并将 .skill 文件交付给用户：

```bash
python -m scripts.package_skill <path/to/skill-folder>
```

打包后，引导用户找到生成的 `.skill` 文件路径以便他们安装。

## Claude.ai 特定说明

在 Claude.ai 中，核心工作流相同（起草 → 测试 → 审查 → 改进 → 重复），但因为 Claude.ai 没有子 Agent，一些机制会改变。以下是需要调整的地方：

**运行测试用例**：没有子 Agent 意味着没有并行执行。对于每个测试用例，读取 skill 的 SKILL.md，然后按照其指令自己完成测试 prompt。一次做一个。这不如独立子 Agent 严谨（你写了 skill 又运行它，所以你有完整上下文），但这是一个有用的健全性检查——人工审查步骤弥补了这一点。跳过基线运行——直接用 skill 按要求完成任务。

**审查结果**：如果无法打开浏览器（例如 Claude.ai 的虚拟机没有显示器，或你在远程服务器上），完全跳过浏览器审查器。改为直接在对话中呈现结果。对于每个测试用例，显示 prompt 和输出。如果输出是用户需要看到的文件（如 .docx 或 .xlsx），保存到文件系统并告诉他们位置，让他们下载和检查。内联询问反馈："这个看起来怎么样？有什么想改的吗？"

**基准测试**：跳过量化基准测试——它依赖基线比较，没有子 Agent 没有意义。专注于用户的定性反馈。

**迭代循环**：和之前一样——改进 skill，重跑测试用例，询问反馈——只是中间没有浏览器审查器。如果你有文件系统，你仍然可以将结果组织到迭代目录中。

**描述优化**：此部分需要 `claude` CLI 工具（具体是 `claude -p`），仅在 Claude Code 中可用。在 Claude.ai 上跳过。

**盲对比**：需要子 Agent。跳过。

**打包**：`package_skill.py` 脚本在任何有 Python 和文件系统的地方都能工作。在 Claude.ai 上，你可以运行它，用户下载生成的 `.skill` 文件。

**更新现有 skill**：用户可能是要求你更新现有 skill，而非创建新的。此时：
- **保留原始名称。** 注意 skill 的目录名和 `name` frontmatter 字段——不变地使用它们。例如，如果已安装的 skill 是 `research-helper`，输出 `research-helper.skill`（不是 `research-helper-v2`）。
- **编辑前复制到可写位置。** 已安装的 skill 路径可能是只读的。复制到 `/tmp/skill-name/`，在那里编辑，从副本打包。
- **如果手动打包，先在 `/tmp/` 中暂存**，然后复制到输出目录——直接写入可能因权限失败。

## Cowork 特定说明

如果你在 Cowork 中，主要需要注意的是：

- 你有子 Agent，所以主工作流（并行启动测试用例、运行基线、评分等）全部可用。（然而，如果遇到严重的超时问题，OK 的是一次运行一个测试 prompt 而不是并行。）
- 你没有浏览器或显示器，所以在生成 eval 查看器时，使用 `--static <output_path>` 写独立 HTML 文件而不是启动服务器。然后提供一个用户可以点击在浏览器中打开 HTML 的链接。
- 不知为何，Cowork 设置似乎让 Claude 在运行测试后不愿意生成 eval 查看器，所以要重申：无论你在 Cowork 还是 Claude Code 中，运行测试后，你应该始终在你自己审查之前生成 eval 查看器供人工查看示例，使用 `generate_review.py`（不要写自己的自定义 HTML 代码）。抱歉但我要用全大写：在你**自己**评估输入之前，先生成 EVAL 查看器。你要尽快把它们交到人工面前！
- 反馈工作方式不同：因为没有运行中的服务器，查看器的"提交所有审查"按钮会将 `feedback.json` 作为文件下载。然后你可以从那里读取（可能需要先请求访问权限）。
- 打包可用——`package_skill.py` 只需要 Python 和文件系统。
- 描述优化（`run_loop.py` / `run_eval.py`）在 Cowork 中应该也能用，因为它通过子进程使用 `claude -p` 而不是浏览器，但请留到你完全完成 skill 并且用户同意它状态良好之后再做。
- **更新现有 skill**：用户可能是要求你更新现有 skill，而非创建新的。遵循上文 Claude.ai 部分的更新指导。
